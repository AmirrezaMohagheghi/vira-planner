# ADR-0001: مرز تراکنش و قرارداد Unit of Work

- **وضعیت:** تصویب‌شده برای طراحی؛ پیاده‌سازی‌نشده
- **تاریخ:** 2026-11-15
- **دامنه:** لایه‌های Application و Infrastructure در Vira Planner
- **شاخهٔ ثبت:** `foundation/architecture-v0-5`

## ۱. زمینه و مسئله

Vira Planner چند Repository مستقل برای Task، Project، ProjectGroup و تاریخچهٔ ارتباط Task و Project دارد. بعضی عملیات Application باید چند منبع داده را به‌صورت هماهنگ تغییر دهند.

نمونهٔ مهم، انتقال یک Task از Project مبدأ به Project مقصد است. این عملیات دست‌کم شامل به‌روزرسانی `Task.projectId` و ثبت رویداد انتقال در `TaskProjectLinkHistory` است. اگر یکی از این تغییرها ذخیره شود و دیگری شکست بخورد، داده‌ها با یکدیگر ناسازگار خواهند شد.

Repositoryهای مستقل به‌تنهایی تضمین اتمیک‌بودن چنین عملیاتی را فراهم نمی‌کنند. همچنین LocalStorage فعلی تراکنش چندموجودیتی واقعی ندارد و rollback آن best-effort است؛ بنابراین نباید آن را پیاده‌سازی کامل Unit of Work یا atomic transaction معرفی کرد.

## ۲. تصمیم

یک مرز مستقل **Unit of Work** در لایهٔ Application تعریف می‌شود. پیاده‌سازی Infrastructure مسئول فراهم‌کردن تراکنش واقعی و اتصال تمام Repositoryهای یک عملیات به همان تراکنش است.

قرارداد مفهومی نسخهٔ اول:

```js
await unitOfWork.execute(async (repositories) => {
  // تمام خواندن‌ها و نوشتن‌های این عملیات
  // از Repositoryهای متعلق به همین تراکنش انجام می‌شوند.
});
```

این قطعه صرفاً نمایش مفهومی قرارداد است و کد اجرایی یا امضای نهایی TypeScript/JavaScript محسوب نمی‌شود. جزئیات دقیق شکل ورودی callback و دسترسی به Repositoryها هنگام تثبیت قرارداد کد مشخص خواهد شد.

## ۳. الزامات رفتاری

پیاده‌سازی Unit of Work باید الزامات زیر را برآورده کند:

1. **یک تراکنش مشترک:** تمام Repositoryهایی که callback دریافت می‌کند باید به یک تراکنش واحد متصل باشند.
2. **Commit در موفقیت:** اگر callback بدون خطا پایان یابد و Commit موفق باشد، تمام تغییرات عملیات ثبت می‌شوند.
3. **Rollback در شکست:** اگر callback یا Commit شکست بخورد، هیچ‌یک از تغییرات همان تراکنش نباید به‌صورت جزئی باقی بماند.
4. **انتشار خطا:** خطای عملیات یا Commit باید به فراخواننده منتقل شود؛ خطا نباید به موفقیت ظاهری تبدیل شود.
5. **عدم تراکنش تو‌در‌تو:** در نسخهٔ اول، اجرای Unit of Work داخل Unit of Work دیگر پشتیبانی نمی‌شود و باید به‌صورت کنترل‌شده رد شود.
6. **محدودیت طول عمر:** Repositoryها و context تراکنش فقط در طول callback و تکمیل تراکنش معتبرند. استفاده از آن‌ها پس از پایان عملیات باید رد شود.
7. **عدم نشت تراکنش:** هر عملیات مستقل باید context و تراکنش مستقل خود را داشته باشد؛ Repositoryهای متعلق به یک عملیات نباید به عملیات دیگر نشت کنند.
8. **عدم عملیات بیرونی در تراکنش:** درخواست شبکه، فراخوانی AI، تعامل با کاربر و کارهای طولانی خارج از تراکنش انجام می‌شوند. تراکنش باید تا حد امکان کوتاه بماند.
9. **عدم ادعای اتمیک‌بودن بدون پشتوانه:** Adapter فقط زمانی می‌تواند این قرارداد را پیاده‌سازی‌شده اعلام کند که رفتار Commit و Rollback واقعی آن با آزمون اثبات شده باشد.

## ۴. مسئولیت لایه‌ها

### Application

- عملیات چندموجودیتی را در یک فراخوانی Unit of Work هماهنگ می‌کند.
- قواعد کسب‌وکار و ترتیب عملیات را تعیین می‌کند.
- مستقیماً به API یا جزئیات تراکنش پایگاه داده وابسته نمی‌شود.
- از Repositoryهایی استفاده می‌کند که Unit of Work برای همان عملیات فراهم کرده است.

### Infrastructure

- تراکنش واقعی را آغاز، Commit یا Rollback می‌کند.
- Repositoryهای تراکنش‌محور را به همان context متصل می‌کند.
- پس از پایان تراکنش، context و Repositoryهای آن را غیرفعال می‌کند.
- خطاهای ذخیره‌سازی و Commit/Rollback را بدون پنهان‌کردن شکست گزارش می‌کند.

### Domain

- از Unit of Work، Database، Storage و جزئیات تراکنش اطلاعی ندارد.
- مدل‌ها و قواعد دامنه را مستقل از زیرساخت نگه می‌دارد.

## ۵. نمونهٔ عملیات نیازمند تراکنش

### انتقال Task بین دو Project

در یک تراکنش واحد:

1. Task و Project مقصد خوانده و اعتبارسنجی می‌شوند.
2. ارجاع Task به Project مقصد تغییر می‌کند.
3. رویداد `moved` در تاریخچه ثبت می‌شود.
4. هر دو تغییر با هم Commit می‌شوند.

اگر ثبت تاریخچه یا ذخیرهٔ Task شکست بخورد، تغییر دیگر نیز باید Rollback شود.

### حذف دائمی Project

در یک تراکنش واحد:

1. Taskهای متصل به Project پیدا می‌شوند.
2. `projectId` آن Taskها به `null` تغییر می‌کند.
3. Project حذف می‌شود.
4. تمام تغییرها با هم Commit می‌شوند.

شکست هر مرحله باید تمام عملیات را Rollback کند.

### حذف ProjectGroup

در یک تراکنش واحد:

1. Projectهای متعلق به Group پیدا می‌شوند.
2. `groupId` آن Projectها به `null` تغییر می‌کند.
3. Group حذف می‌شود.
4. تمام تغییرها با هم Commit می‌شوند.

Taskها در این عملیات حذف یا مستقیماً تغییر داده نمی‌شوند.

## ۶. راهبرد آزمون و معیار پذیرش

پیش از پذیرش هر پیاده‌سازی، دست‌کم سناریوهای زیر باید آزموده شوند:

- Commit موفق چند Repository در یک تراکنش.
- شکست callback پیش از Commit و بازگشت تمام تغییرها.
- شکست در نوشتن Repository دوم پس از موفقیت نوشتن اول و بازگشت کامل.
- شکست عملیات Commit و بررسی وضعیت نهایی داده‌ها.
- رد اجرای تراکنش تو‌در‌تو.
- رد استفاده از Repository پس از پایان تراکنش.
- مستقل‌بودن context دو عملیات هم‌زمان یا متوالی.
- حفظ خطای اصلی و گزارش مناسب در صورت شکست Rollback.
- اطمینان از اینکه دادهٔ پایدار پس از بازخوانی دقیقاً با نتیجهٔ Commit یا Rollback سازگار است.

تست‌ها باید روی Adapter واقعی و storage پایدار اجرا شوند؛ mock به‌تنهایی برای اثبات atomicity کافی نیست.

## ۷. گزینه‌های زیرساختی و موارد خارج از تصمیم

- **SQLite:** نامزد جدی برای Proof of Concept است، نه انتخاب نهایی این ADR.
- **LocalStorage:** برای قرارداد تراکنش چندموجودیتی کافی نیست و نباید با rollback دستی معادل تراکنش واقعی تلقی شود.
- انتخاب Database، driver/binding، Desktop Shell، Android integration و روش مهاجرت داده در این تصمیم نهایی نمی‌شوند.
- طراحی Backup/Restore، رمزنگاری، Sync و conflict resolution خارج از دامنهٔ این ADR هستند و تصمیم‌های مستقل می‌خواهند.
- مهاجرت Storage فعلی یا تغییر schema در این مرحله مجاز یا موردنیاز نیست.

## ۸. پیامدها

### مزایا

- منطق هماهنگی چندموجودیتی در Application باقی می‌ماند.
- جزئیات پایگاه داده در Infrastructure محصور می‌شوند.
- ناسازگاری ناشی از ذخیره‌شدن بخشی از یک عملیات کاهش می‌یابد.
- امکان آزمون مستقل قرارداد و Adapter فراهم می‌شود.

### هزینه‌ها و محدودیت‌ها

- پیاده‌سازی واقعی به یک Adapter تراکنش‌پذیر نیاز دارد.
- Repositoryها باید بتوانند از context تراکنش مشترک استفاده کنند.
- چرخهٔ عمر context و رفتار شکست Commit/Rollback باید دقیق مدیریت شود.
- انتخاب و آزمون فناوری ذخیره‌سازی همچنان یک گام مستقل است.

## ۹. وضعیت اجرا

این ADR تصمیم طراحی را ثبت می‌کند؛ به معنی وجود پیاده‌سازی نیست.

در زمان تصویب این سند:
- قرارداد سطحی Unit of Work در persistence contracts وجود دارد.
- Repositoryهای Task، Project، ProjectGroup و TaskProjectLinkHistory پیاده‌سازی شده‌اند، اما این موضوع به‌تنهایی تراکنش مشترک ایجاد نمی‌کند.
- تراکنش واقعی، Rollback اتمیک و اتصال پایدار Repositoryها به یک context هنوز پیاده‌سازی و اثبات نشده‌اند.
- LocalStorage فعلی نباید به‌عنوان Adapter تراکنشی معرفی شود.

**گام بعدی:** طراحی دقیق امضای قرارداد و تست‌های مستقل Unit of Work؛ سپس Proof of Concept یک Adapter تراکنشی و ارزیابی آن روی Windows و Android، پیش از هر تصمیم برای مهاجرت داده.
