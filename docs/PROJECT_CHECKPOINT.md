## ۱. خلاصهٔ اجرایی: الان کجا هستیم؟

Vira Planner در حال تبدیل‌شدن از یک نمونهٔ اولیهٔ سادهٔ برنامه‌ریزی به یک **Personal Life Planning Workspace فارسی‌محور** است؛ محیطی یکپارچه برای ثبت و مدیریت وظایف، زمان، تعهدات، اهداف، عادت‌ها، یادداشت‌ها و اسناد شخصی.

| هوش مصنوعی | نیازمندی/طراحی | در فایل اجرایی فعلی اتصال عملیاتی AI مشاهده نشده است |

**جمع‌بندی:** پایهٔ رابط، وظایف، تقویم شمسی و بخشی از زیرساخت داده ساخته شده است. محصول جامع، موتور زمان‌بندی، اسناد و AI هنوز عمدتاً در سطح مشخصات و طراحی هستند. نباید بین «در سند نوشته شده» و «در برنامه کار می‌کند» اشتباه کنیم.

## ۲. چشم‌انداز و هویت محصول

### تعریف محصول

**Vira Planner — Your Personal Life Planning Workspace**

فضایی فارسی‌محور برای مدیریت زندگی شخصی که وظایف، زمان، برنامه‌ها، اهداف، عادت‌ها، یادداشت‌ها و اسناد را به هم متصل می‌کند و به کاربر کمک می‌کند برنامه‌ای واقع‌بینانه و قابل اجرا داشته باشد.

### وعدهٔ اصلی

1. ثبت سریع فکرها، کارها و منابع.
2. روشن‌کردن اولویت‌ها و اقدام بعدی.
3. برنامه‌ریزی بر اساس ظرفیت واقعی، نه پرکردن تمام ساعت‌ها.
4. حفظ زمان استراحت، تعهدات ثابت و buffer.
5. اتصال اسناد و منابع به کارها و پروژه‌های مرتبط.
6. ارائهٔ پیشنهادهای هوشمند، با توضیح و کنترل نهایی کاربر.
7. حفظ حریم خصوصی و امکان استفاده از هستهٔ محصول بدون AI و اینترنت.

### پنج اصل راهبردی

- **Realistic Planning:** برنامه‌ریزی بر اساس ظرفیت و محدودیت‌های واقعی.
- **Connected Knowledge:** پیوند وظایف، پروژه‌ها، اهداف، یادداشت‌ها و اسناد.
- **Controlled AI:** هوش مصنوعی توضیح‌پذیر و تحت کنترل کاربر.
- **Local-first Privacy:** نگهداری محلی داده تا جای ممکن و شفافیت دربارهٔ پردازش بیرونی.
- **Native Persian Experience:** فارسی و RTL واقعی، تقویم شمسی، هفته از شنبه و ورودی زبان طبیعی فارسی.

این موارد جایگاه و جهت‌گیری محصول‌اند؛ میزان موفقیت آن‌ها باید با استفادهٔ واقعی سنجیده شود.

## ۳. اصول قطعی کار روی مخزن

1. همهٔ توسعه‌ها فقط روی شاخهٔ `foundation/architecture-v0-5` انجام شوند.
2. شاخهٔ `main` دست‌نخورده بماند؛ بدون تصمیم صریح جداگانه merge یا تغییر نکند.
3. مخزن قبلاً clone شده است؛ clone مجدد انجام نشود.
4. پیش از تغییر کد یا سند موجود، نسخهٔ فعلی و SHA آن خوانده شود.
5. تغییرات کوچک، هدفمند و قابل بازبینی باشند؛ کد سالم فقط برای افزایش تعداد تست یا تغییر سلیقه‌ای بازنویسی نشود.
6. پیش از هر قابلیت تازه، روشن گفته شود: «از اینجا وارد افزودن قابلیت جدید می‌شویم؛ ...».
7. قبل از هر تغییر، علت، دامنه، اثر احتمالی و روش بررسی توضیح داده شود.
8. هیچ دادهٔ کاربر، فایل یا migration نباید بی‌صدا حذف یا بازنویسی شود.
9. AI نباید بدون تأیید لازم، داده یا برنامهٔ کاربر را به‌طور حساس تغییر دهد.
10. وضعیت پیاده‌سازی، تست، CI و امنیت فقط بر اساس شواهد قابل مشاهده گزارش شود؛ حدس به‌عنوان واقعیت بیان نشود.

## ۶. معماری و زیرساخت ثبت‌شده

مرجع تفصیلی: `docs/ARCHITECTURE.md` (نسخهٔ ثبت‌شده در سند: 0.5-draft).

### اصول معماری

- جداسازی Presentation، Application، Domain و Infrastructure.
- موتور زمان‌بندی deterministic و مستقل از AI.
- کارکرد آفلاین هستهٔ محصول بدون AI.
- حداقل‌سازی وابستگی و هزینه.
- schema version و migration کنترل‌شده.
- آزمون‌پذیری تاریخ، تکرار، اعلان و زمان‌بندی.
- نگهداری کلیدهای API در backend، نه frontend.

### ساختار ماژولار مشاهده‌شده در app.js

کد اصلی از ماژول‌های زیر استفاده می‌کند:
- `src/application/tasks/task-collection.js`
- `src/infrastructure/storage/local-task-storage.js`
- `src/application/tasks/legacy-task-adapter.js`
- `src/domain/calendar/jalali-calendar.js`
- `src/presentation/calendar/calendar-view.js`
- `src/presentation/tasks/task-list-view.js`
- `src/presentation/tasks/task-time-input.js`
- `src/presentation/tasks/task-form-view.js`

### مسیر بارگذاری و ذخیرهٔ وظایف

- Load: دادهٔ ذخیره‌شده خوانده می‌شود، از Legacy به Canonical تبدیل می‌شود، migration اجرا می‌شود و در صورت نیاز aliasهای سازگار برای UI ساخته می‌شوند.
- Save: دادهٔ UI به مدل Canonical تبدیل و از مسیر storage ذخیره می‌شود.
- Collection مسئول هماهنگی عملیات وظیفه و کنترل آمادگی storage است.

### وضعیت ذخیره‌سازی و migration ثبت‌شده در معماری

- کلید سازگار فعلی: `vira-planner-tasks-v1`
- قالب ذخیره‌سازی Canonical: envelope با `schemaVersion: 2` و آرایهٔ `tasks`.
- آرایهٔ خام قدیمی به‌عنوان legacy v1 شناخته می‌شود.
- قالب v2 باید Taskهای Canonical کامل و معتبر داشته باشد.
- schema version از `task.version` مستقل است.
- نسخهٔ ناشناخته/جدیدتر نباید بازنویسی شود.
- شناسه‌های تکراری یا Task نامعتبر باید رد شوند.
- فیلدهای ناشناخته تا جای ممکن حفظ شوند.
- aliasهای UI در مسیر Canonical ذخیره‌سازی باقی نمی‌مانند.
- قبل از migration، مقدار خام قبلی backup می‌شود.
- پس از نوشتن، read-back برای بررسی صحت انجام می‌شود.
- در شکست، بازگردانی best-effort انجام می‌شود و عملیات عادی باید قفل بماند.
- LocalStorage تراکنش چندمرحله‌ای واقعی ندارد؛ نباید atomicity کامل ادعا شود.

### اصلاحات معماری قبلی ثبت‌شده

1. Recovery پس از خطای storage: نگهداری آخرین snapshot موفق، rollback در failed write و قفل‌کردن عملیات ناامن.
2. انتقال Legacy adapter به لایهٔ Application و حذف adapter قدیمی از Domain.
3. سازگاری status/progress: todo=0، in_progress=1..99، completed=100؛ وضعیت cancelled می‌تواند progress بین 0 تا 100 داشته باشد.
4. Adapter roundtrip: اولویت Canonical، حفظ metadata، clone آرایه‌ها و validation.
5. Storage contract: schema v2 envelope، migration آرایهٔ legacy، رد schema نامعتبر، رد duplicate ID، حفظ unknown fields، backup دقیق raw، read-back verify و rollback best-effort.

این موارد سابقهٔ کار ثبت‌شده‌اند؛ قبل از دستکاری دوباره باید کد و تست‌های متناظر بررسی شوند.

## ۱۱. هوش مصنوعی و ایدهٔ چند API

### تصمیم‌های ثبت‌شده
- AI اختیاری است و هستهٔ محصول باید بدون آن کار کند.
- Mistral به‌عنوان provider آغازین انتخاب شده است.
- provider interface باید قابل توسعه باشد.
- کلید API در frontend یا repository قرار نگیرد.
- درخواست‌های حساس از backend امن عبور کنند.
- دادهٔ خصوصی فقط در حد نیاز و با کنترل کاربر ارسال شود.
- هزینه، quota و خطا باید مدیریت شوند.

### ایدهٔ مطرح‌شده: پنج API با fallback خودکار

ایدهٔ کاربر این است که چند provider در یک زنجیره قرار بگیرند: ابتدا provider اصلی درخواست را دریافت کند؛ اگر در دسترس نبود، quota تمام شد یا خطای قابل‌بازیابی داد، سیستم provider بعدی را امتحان کند.

**وضعیت: ایدهٔ ثبت‌شده؛ پیاده‌سازی نشده و جزئیات آن هنوز نیازمند طراحی است.**

پیش از اجرا باید تصمیم بگیریم:
- providerهای واقعاً قابل استفاده و شرایط رایگان هرکدام
- تفاوت مدل‌ها و کیفیت خروجی
- تشخیص quota exhausted، rate limit، timeout و خطای دائمی
- retry و backoff
- اولویت و ترتیب fallback
- سازگاری ورودی/خروجی از طریق adapter
- جلوگیری از ارسال چندبارهٔ عملیات غیر idempotent
- بودجه و سقف هزینه
- حفاظت از کلیدها
- سطح داده‌ای که مجاز به ارسال به هر provider است
- logging بدون افشای محتوای حساس
- نمایش provider فعال و علت fallback
- امکان خاموش‌کردن provider و کنترل کاربر

پنج API رایگان به معنی دسترسی دائمی، کیفیت یکسان یا هزینهٔ صفر تضمین‌شده نیست. شرایط سرویس‌ها باید هنگام اجرا دوباره بررسی شود.

### وضعیت اتصال فعلی
در `app.js` بررسی‌شده اتصال اجرایی AI دیده نشده است. این بخش در حال حاضر نیازمندی/طراحی است.

### 2026-11-12 — پیش‌نویس طراحی برنامهٔ هفتگی و استثناها

- **نوع:** طراحی معماری / تصمیم محصول
- **وضعیت:** پیش‌نویس پیشنهادی؛ پیش از تبدیل به قرارداد نهایی دامنه، نیازمند تأیید قواعد رفتاری کاربر

- **تصمیم پایهٔ پیشنهادی:** الگوی هفتگی باید هم تعهدهای ثابت (Hard constraints) و هم بازه‌ها/ترجیحات انعطاف‌پذیر (Soft constraints) را پشتیبانی کند.
- **تعهد ثابت:** رویدادی با روز و ساعت مشخص مانند دانشگاه یا خواب؛ موتور زمان‌بندی حق جابه‌جایی خودکار آن را ندارد و باید آن بازه را اشغال‌شده بداند.
- **بازهٔ ترجیحی:** پنجره‌ای که کاربر ترجیح می‌دهد فعالیتی مانند مطالعه در آن انجام شود؛ موتور می‌تواند آن را برای جا دادن تعهدهای مهم‌تر جابه‌جا کند، اما باید علت را توضیح دهد و پیشنهاد را پیش از اعمال نمایش دهد.
- **زمان آزاد:** در نسخهٔ نخست می‌تواند از ساعات بیداری/قابل‌برنامه‌ریزی کاربر پس از کسر تعهدهای ثابت و استثناها محاسبه شود؛ لازم نیست تمام زمان باقی‌مانده به وظیفه اختصاص یابد.
- **الگوی هفتگی:** نام، تاریخ شروع و پایان اعتبار، منطقهٔ زمانی، وضعیت فعال/غیرفعال و مجموعهٔ ورودی‌های هفتگی. چند الگو می‌توانند ذخیره شوند (مثلاً ترم و تعطیلات)، اما در هر تاریخ فقط یک الگوی پایه باید به‌طور قطعی اعمال شود تا تعارض دو الگو مبهم نشود.
- **ورودی هفتگی:** شناسه، عنوان، روز هفته با قرارداد شنبه=0 تا جمعه=6، زمان شروع/پایان محلی، نوع fixed/preferred، دسته/نوع فعالیت و در صورت نیاز یادداشت. مدت از اختلاف زمان شروع و پایان به دست می‌آید.
- **استثنا:** تغییر تاریخ‌محور روی الگوی پایه، بدون ویرایش خود الگو؛ عملیات پیشنهادی برای نسخهٔ نخست: لغو یک ورودی در یک تاریخ، جایگزینی آن در همان تاریخ، یا افزودن یک ورودی یک‌باره.
- **اولویت اعمال:** ابتدا الگوی پایهٔ معتبر در آن تاریخ؛ سپس استثناهای همان تاریخ؛ سپس تعهدها/وظایف زمان‌بندی‌شده. استثنا نباید بی‌صدا الگوی اصلی را تغییر دهد.
- **اعتبارسنجی:** پایان باید بعد از شروع باشد؛ ورودی ثابتِ هم‌پوشان در یک الگو باید رد یا با هشدار صریح برای تصمیم کاربر ارائه شود؛ بازه‌های ترجیحی هم‌پوشان می‌توانند مجاز باشند اما باید در امتیازدهی زمان‌بندی مدیریت شوند.
- **زمان و تقویم:** ذخیرهٔ روز هفته و ساعت به‌صورت زمان محلی همراه timezone الگو؛ تبدیل به instant UTC فقط هنگام محاسبهٔ یک تاریخ مشخص. نباید برای یک برنامهٔ هفتگی صرفاً یک UTC offset ثابت ذخیره شود، چون تغییر ساعت تابستانی می‌تواند ساعت محلی را جابه‌جا کند.
- **موارد خارج از تصمیم فعلی:** تکرارهای پیچیده، استثناهای بازه‌ای، چند منطقهٔ زمانی در یک الگو، هم‌پوشانی الگوهای پایه و همگام‌سازی تقویم خارجی تا زمان نیاز واقعی طراحی جداگانه می‌خواهند.
- **معیار پذیرش طراحی:** بتوان یک برنامهٔ ترمی ساخت، تعهد ثابت و ترجیح مطالعه تعریف کرد، یک جلسه را فقط برای یک تاریخ لغو/جایگزین کرد، و برای یک تاریخ مشخص برنامهٔ مؤثر را بدون تغییر الگوی پایه محاسبه کرد.
- **پیش از پیاده‌سازی:** باید قاعدهٔ مجاز بودن override دستی تعهد ثابت و نیز رفتار تغییر الگو در تاریخ‌های آینده تأیید شود. فعلاً کدی تغییر نکرده است.
- **پیگیری گفتگو:** کاربر با ادامهٔ طراحی بر مبنای پشتیبانی هم‌زمان از تعهدهای ثابت و زمان‌های انعطاف‌پذیر موافقت کرد؛ بنابراین تفکیک Hard / Soft در سطح نیازمندی پذیرفته‌شده است. جزئیات قواعد override، تغییر الگوهای آینده و امتیازدهی ترجیحات هنوز نهایی نیستند.
- **تفکیک مفهومی تکمیلی:** «بازهٔ ترجیحی» زمان را مسدود نمی‌کند و فقط در امتیازدهی زمان‌بندی اثر دارد؛ «بلوک منعطف» یک فعالیت برنامه‌ریزی‌شده با مدت است که می‌تواند جابه‌جا شود. این دو نباید در مدل داده یک مفهوم واحد فرض شوند.
- **تصمیم قطعی کاربر دربارهٔ تغییر برنامه:** تغییر یک تعهد ثابت فقط به‌صورت استثنای همان تاریخ ثبت می‌شود؛ الگوی هفتگی پایه با لغو یا جابه‌جایی یک جلسه تغییر نمی‌کند. این تصمیم از تغییرات ناخواستهٔ هفته‌های آینده جلوگیری می‌کند.
- **تصمیم قطعی کاربر دربارهٔ انواع استثنا:** هر الگوی هفتگی می‌تواند برای یک تاریخ مشخص استثنای «لغو جلسه»، «تغییر همان جلسه» یا «جایگزینی/افزودن جلسهٔ مخصوص همان تاریخ» داشته باشد. همهٔ این موارد فقط روی تاریخ هدف اثر می‌گذارند و الگوی پایه را تغییر نمی‌دهند.
- **تصمیم قطعی کاربر دربارهٔ زمان‌بندی مجدد:** وقتی استثنای یک تاریخ زمان آزاد ایجاد می‌کند، موتور می‌تواند وظایف/فعالیت‌های منعطف را برای آن بازه پیشنهاد و برنامهٔ جایگزین را پیش‌نمایش کند؛ هیچ جابه‌جایی بدون تأیید صریح کاربر اعمال نمی‌شود. تعهدهای ثابت همچنان دست‌نخورده‌اند.
- **بازبینی رقبا پیش از تصمیم‌گیری دربارهٔ زمان‌های منعطف (2026-11-12):** مستندات رسمی Motion، Reclaim، Sunsama، SkedPal و Akiflow مرور شد. الگوهای مهم: Motion از مدت، تاریخ شروع، deadline سخت/منعطف، اولویت، chunking، برنامهٔ کاری و رویدادهای ثابت استفاده می‌کند؛ Reclaim از ساعات کاری/شخصی، بازهٔ جابه‌جایی، حداقل مدت، اولویت، عادت‌ها و بافرها استفاده می‌کند و Preview Mode دارد؛ Sunsama زمان‌بندی وظیفه روی تقویم و برنامه‌ریزی روزانه همراه با پیش‌بینی workload و بازبینی را برجسته می‌کند؛ SkedPal از Time Maps برای ساعات ترجیحی، Flexible Plans، بودجهٔ زمانی و حداقل/بافر استفاده می‌کند؛ Akiflow زمان برنامه‌ریزی‌شده، مدت، تکرار، قفل‌کردن زمان و deadline را جداگانه نگه می‌دارد.
- **پیشنهاد طراحی (هنوز تصمیم قطعی نیست):** برای فعالیت منعطف، صرفاً «ساعت ترجیحی» کافی نیست. مدل باید بتواند هدف زمانی (مدت هر نوبت یا مجموع هفتگی)، پنجرهٔ مجاز/ترجیحی، deadline یا انتهای پنجره، حداقل طول هر نوبت و اجازه/عدم اجازهٔ تقسیم فعالیت را جدا کند. این‌ها نباید با تعهد ثابت یک نوع داده تلقی شوند.
- **ملاحظهٔ محصولی:** رفتار پیش‌فرض ویرا نباید مانند بعضی حالت‌های خودکار Motion، deadline سخت را به‌طور پنهانی مجوز برنامه‌ریزی خارج از ساعات مجاز بداند. اگر هیچ جای مناسبی وجود ندارد، بهتر است مورد unscheduled/at-risk نشان داده شود و پیشنهاد با پیش‌نمایش و تأیید کاربر ارائه شود.
