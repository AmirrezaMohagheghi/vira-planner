## ۱. خلاصهٔ اجرایی: الان کجا هستیم؟

Vira Planner در حال تبدیل‌شدن از یک نمونهٔ اولیهٔ سادهٔ برنامه‌ریزی به یک **Personal Life Planning Workspace فارسی‌محور** است؛ محیطی یکپارچه برای ثبت و مدیریت وظایف، زمان، تعهدات، اهداف، عادت‌ها، یادداشت‌ها و اسناد شخصی.

## ۲. چشم‌انداز و هویت محصول

### تعریف محصول

**Vira Planner — Your Personal Life Planning Workspace**

فضایی فارسی‌محور برای مدیریت زندگی شخصی که وظایف، زمان، برنامه‌ها، اهداف، عادت‌ها، یادداشت‌ها و اسناد را به هم متصل می‌کند و به کاربر کمک می‌کند برنامه‌ای واقع‌بینانه و قابل اجرا داشته باشد.

### وعدهٔ اصلی

1. ثبت سریع فکرها، کارها و منابع.
2. روشن‌کردن اولویت‌ها و اقدام بعدی.
3. برنامه‌ریزی بر اساس ظرفیت واقعی، نه پرکردن تمام ساعت‌ها.
4. حفظ زمان استراحت، تعهدات ثابت و buffer.
5. اتصال اسناد و منابع به کارها و پروژه‌های مرتبط.
6. ارائهٔ پیشنهادهای هوشمند، با توضیح و کنترل نهایی کاربر.
7. حفظ حریم خصوصی و امکان استفاده از هستهٔ محصول بدون AI و اینترنت.

### پنج اصل راهبردی

- **Realistic Planning:** برنامه‌ریزی بر اساس ظرفیت و محدودیت‌های واقعی.
- **Connected Knowledge:** پیوند وظایف، پروژه‌ها، اهداف، یادداشت‌ها و اسناد.
- **Controlled AI:** هوش مصنوعی توضیح‌پذیر و تحت کنترل کاربر.
- **Local-first Privacy:** نگهداری محلی داده تا جای ممکن و شفافیت دربارهٔ پردازش بیرونی.
- **Native Persian Experience:** فارسی و RTL واقعی، تقویم شمسی، هفته از شنبه و ورودی زبان طبیعی فارسی.

این موارد جایگاه و جهت‌گیری محصول‌اند؛ میزان موفقیت آن‌ها باید با استفادهٔ واقعی سنجیده شود.

## ۳. اصول قطعی کار روی مخزن

1. همهٔ توسعه‌ها فقط روی شاخهٔ `foundation/architecture-v0-5` انجام شوند.
2. شاخهٔ `main` دست‌نخورده بماند؛ بدون تصمیم صریح جداگانه merge یا تغییر نکند.
3. مخزن قبلاً clone شده است؛ clone مجدد انجام نشود.
4. پیش از تغییر کد یا سند موجود، نسخهٔ فعلی و SHA آن خوانده شود.
5. تغییرات کوچک، هدفمند و قابل بازبینی باشند؛ کد سالم فقط برای افزایش تعداد تست یا تغییر سلیقه‌ای بازنویسی نشود.
6. پیش از هر قابلیت تازه، روشن گفته شود: «از اینجا وارد افزودن قابلیت جدید می‌شویم؛ ...».
7. قبل از هر تغییر، علت، دامنه، اثر احتمالی و روش بررسی توضیح داده شود.
8. هیچ دادهٔ کاربر، فایل یا migration نباید بی‌صدا حذف یا بازنویسی شود.
9. AI نباید بدون تأیید لازم، داده یا برنامهٔ کاربر را به‌طور حساس تغییر دهد.
10. وضعیت پیاده‌سازی، تست، CI و امنیت فقط بر اساس شواهد قابل مشاهده گزارش شود؛ حدس به‌عنوان واقعیت بیان نشود.

## ۶. معماری و زیرساخت ثبت‌شده

مرجع تفصیلی: `docs/ARCHITECTURE.md` (نسخهٔ ثبت‌شده در سند: 0.5-draft).

### اصول معماری

- جداسازی Presentation، Application، Domain و Infrastructure.
- موتور زمان‌بندی deterministic و مستقل از AI.
- کارکرد آفلاین هستهٔ محصول بدون AI.
- حداقل‌سازی وابستگی و هزینه.
- schema version و migration کنترل‌شده.
- آزمون‌پذیری تاریخ، تکرار، اعلان و زمان‌بندی.
- نگهداری کلیدهای API در backend، نه frontend.

### ساختار ماژولار مشاهده‌شده در app.js

کد اصلی از ماژول‌های زیر استفاده می‌کند:
- `src/application/tasks/task-collection.js`
- `src/infrastructure/storage/local-task-storage.js`
- `src/application/tasks/legacy-task-adapter.js`
- `src/domain/calendar/jalali-calendar.js`
- `src/presentation/calendar/calendar-view.js`
- `src/presentation/tasks/task-list-view.js`
- `src/presentation/tasks/task-time-input.js`
- `src/presentation/tasks/task-form-view.js`

### مسیر بارگذاری و ذخیرهٔ وظایف

- Load: دادهٔ ذخیره‌شده خوانده می‌شود، از Legacy به Canonical تبدیل می‌شود، migration اجرا می‌شود و در صورت نیاز aliasهای سازگار برای UI ساخته می‌شوند.
- Save: دادهٔ UI به مدل Canonical تبدیل و از مسیر storage ذخیره می‌شود.
- Collection مسئول هماهنگی عملیات وظیفه و کنترل آمادگی storage است.

### وضعیت ذخیره‌سازی و migration ثبت‌شده در معماری

- کلید سازگار فعلی: `vira-planner-tasks-v1`
- قالب ذخیره‌سازی Canonical: envelope با `schemaVersion: 2` و آرایهٔ `tasks`.
- آرایهٔ خام قدیمی به‌عنوان legacy v1 شناخته می‌شود.
- قالب v2 باید Taskهای Canonical کامل و معتبر داشته باشد.
- schema version از `task.version` مستقل است.
- نسخهٔ ناشناخته/جدیدتر نباید بازنویسی شود.
- شناسه‌های تکراری یا Task نامعتبر باید رد شوند.
- فیلدهای ناشناخته تا جای ممکن حفظ شوند.
- aliasهای UI در مسیر Canonical ذخیره‌سازی باقی نمی‌مانند.
- قبل از migration، مقدار خام قبلی backup می‌شود.
- پس از نوشتن، read-back برای بررسی صحت انجام می‌شود.
- در شکست، بازگردانی best-effort انجام می‌شود و عملیات عادی باید قفل بماند.
- LocalStorage تراکنش چندمرحله‌ای واقعی ندارد؛ نباید atomicity کامل ادعا شود.

### اصلاحات معماری قبلی ثبت‌شده

1. Recovery پس از خطای storage: نگهداری آخرین snapshot موفق، rollback در failed write و قفل‌کردن عملیات ناامن.
2. انتقال Legacy adapter به لایهٔ Application و حذف adapter قدیمی از Domain.
3. سازگاری status/progress: todo=0، in_progress=1..99، completed=100؛ وضعیت cancelled می‌تواند progress بین 0 تا 100 داشته باشد.
4. Adapter roundtrip: اولویت Canonical، حفظ metadata، clone آرایه‌ها و validation.
5. Storage contract: schema v2 envelope، migration آرایهٔ legacy، رد schema نامعتبر، رد duplicate ID، حفظ unknown fields، backup دقیق raw، read-back verify و rollback best-effort.

این موارد سابقهٔ کار ثبت‌شده‌اند؛ قبل از دستکاری دوباره باید کد و تست‌های متناظر بررسی شوند.

## ۱۱. هوش مصنوعی و ایدهٔ چند API

### تصمیم‌های ثبت‌شده
- AI اختیاری است و هستهٔ محصول باید بدون آن کار کند.
- Mistral به‌عنوان provider آغازین انتخاب شده است.
- provider interface باید قابل توسعه باشد.
- کلید API در frontend یا repository قرار نگیرد.
- درخواست‌های حساس از backend امن عبور کنند.
- دادهٔ خصوصی فقط در حد نیاز و با کنترل کاربر ارسال شود.
- هزینه، quota و خطا باید مدیریت شوند.

### ایدهٔ مطرح‌شده: پنج API با fallback خودکار

ایدهٔ کاربر این است که چند provider در یک زنجیره قرار بگیرند: ابتدا provider اصلی درخواست را دریافت کند؛ اگر در دسترس نبود، quota تمام شد یا خطای قابل‌بازیابی داد، سیستم provider بعدی را امتحان کند.

**وضعیت: ایدهٔ ثبت‌شده؛ پیاده‌سازی نشده و جزئیات آن هنوز نیازمند طراحی است.**

پیش از اجرا باید تصمیم بگیریم:
- providerهای واقعاً قابل استفاده و شرایط رایگان هرکدام
- تفاوت مدل‌ها و کیفیت خروجی
- تشخیص quota exhausted، rate limit، timeout و خطای دائمی
- retry و backoff
- اولویت و ترتیب fallback
- سازگاری ورودی/خروجی از طریق adapter
- جلوگیری از ارسال چندبارهٔ عملیات غیر idempotent
- بودجه و سقف هزینه
- حفاظت از کلیدها
- سطح داده‌ای که مجاز به ارسال به هر provider است
- logging بدون افشای محتوای حساس
- نمایش provider فعال و علت fallback
- امکان خاموش‌کردن provider و کنترل کاربر

پنج API رایگان به معنی دسترسی دائمی، کیفیت یکسان یا هزینهٔ صفر تضمین‌شده نیست. شرایط سرویس‌ها باید هنگام اجرا دوباره بررسی شود.

### وضعیت اتصال فعلی
در `app.js` بررسی‌شده اتصال اجرایی AI دیده نشده است. این بخش در حال حاضر نیازمندی/طراحی است.

## ۱۷. دفتر تغییرات و تصمیم‌های جدید

### 2026-11-12 — پیش‌نویس طراحی برنامهٔ هفتگی و استثناها

- **نوع:** طراحی معماری / تصمیم محصول
- **وضعیت:** پیش‌نویس پیشنهادی؛ پیش از تبدیل به قرارداد نهایی دامنه، نیازمند تأیید قواعد رفتاری کاربر
- **ارجاع:** `docs/PRODUCT_SPEC.md` بخش ۳.۴ و `docs/ARCHITECTURE.md` بخش‌های ۴ و ۶؛ این قابلیت از قبل در نیازمندی‌های محصول آمده و قابلیت تازه‌ای به scope اضافه نمی‌کند.
- **تصمیم پایهٔ پیشنهادی:** الگوی هفتگی باید هم تعهدهای ثابت (Hard constraints) و هم بازه‌ها/ترجیحات انعطاف‌پذیر (Soft constraints) را پشتیبانی کند.
- **تعهد ثابت:** رویدادی با روز و ساعت مشخص مانند دانشگاه یا خواب؛ موتور زمان‌بندی حق جابه‌جایی خودکار آن را ندارد و باید آن بازه را اشغال‌شده بداند.
- **بازهٔ ترجیحی:** پنجره‌ای که کاربر ترجیح می‌دهد فعالیتی مانند مطالعه در آن انجام شود؛ موتور می‌تواند آن را برای جا دادن تعهدهای مهم‌تر جابه‌جا کند، اما باید علت را توضیح دهد و پیشنهاد را پیش از اعمال نمایش دهد.
- **زمان آزاد:** در نسخهٔ نخست می‌تواند از ساعات بیداری/قابل‌برنامه‌ریزی کاربر پس از کسر تعهدهای ثابت و استثناها محاسبه شود؛ لازم نیست تمام زمان باقی‌مانده به وظیفه اختصاص یابد.
- **الگوی هفتگی:** نام، تاریخ شروع و پایان اعتبار، منطقهٔ زمانی، وضعیت فعال/غیرفعال و مجموعهٔ ورودی‌های هفتگی. چند الگو می‌توانند ذخیره شوند (مثلاً ترم و تعطیلات)، اما در هر تاریخ فقط یک الگوی پایه باید به‌طور قطعی اعمال شود تا تعارض دو الگو مبهم نشود.
- **ورودی هفتگی:** شناسه، عنوان، روز هفته با قرارداد شنبه=0 تا جمعه=6، زمان شروع/پایان محلی، نوع fixed/preferred، دسته/نوع فعالیت و در صورت نیاز یادداشت. مدت از اختلاف زمان شروع و پایان به دست می‌آید.
- **استثنا:** تغییر تاریخ‌محور روی الگوی پایه، بدون ویرایش خود الگو؛ عملیات پیشنهادی برای نسخهٔ نخست: لغو یک ورودی در یک تاریخ، جایگزینی آن در همان تاریخ، یا افزودن یک ورودی یک‌باره.
- **اولویت اعمال:** ابتدا الگوی پایهٔ معتبر در آن تاریخ؛ سپس استثناهای همان تاریخ؛ سپس تعهدها/وظایف زمان‌بندی‌شده. استثنا نباید بی‌صدا الگوی اصلی را تغییر دهد.
- **اعتبارسنجی:** پایان باید بعد از شروع باشد؛ ورودی ثابتِ هم‌پوشان در یک الگو باید رد یا با هشدار صریح برای تصمیم کاربر ارائه شود؛ بازه‌های ترجیحی هم‌پوشان می‌توانند مجاز باشند اما باید در امتیازدهی زمان‌بندی مدیریت شوند.
- **زمان و تقویم:** ذخیرهٔ روز هفته و ساعت به‌صورت زمان محلی همراه timezone الگو؛ تبدیل به instant UTC فقط هنگام محاسبهٔ یک تاریخ مشخص. نباید برای یک برنامهٔ هفتگی صرفاً یک UTC offset ثابت ذخیره شود، چون تغییر ساعت تابستانی می‌تواند ساعت محلی را جابه‌جا کند.
- **موارد خارج از تصمیم فعلی:** تکرارهای پیچیده، استثناهای بازه‌ای، چند منطقهٔ زمانی در یک الگو، هم‌پوشانی الگوهای پایه و همگام‌سازی تقویم خارجی تا زمان نیاز واقعی طراحی جداگانه می‌خواهند.
- **معیار پذیرش طراحی:** بتوان یک برنامهٔ ترمی ساخت، تعهد ثابت و ترجیح مطالعه تعریف کرد، یک جلسه را فقط برای یک تاریخ لغو/جایگزین کرد، و برای یک تاریخ مشخص برنامهٔ مؤثر را بدون تغییر الگوی پایه محاسبه کرد.
- **پیش از پیاده‌سازی:** باید قاعدهٔ مجاز بودن override دستی تعهد ثابت و نیز رفتار تغییر الگو در تاریخ‌های آینده تأیید شود. فعلاً کدی تغییر نکرده است.
- **پیگیری گفتگو:** کاربر با ادامهٔ طراحی بر مبنای پشتیبانی هم‌زمان از تعهدهای ثابت و زمان‌های انعطاف‌پذیر موافقت کرد؛ بنابراین تفکیک Hard / Soft در سطح نیازمندی پذیرفته‌شده است. جزئیات قواعد override، تغییر الگوهای آینده و امتیازدهی ترجیحات هنوز نهایی نیستند.
- **تفکیک مفهومی تکمیلی:** «بازهٔ ترجیحی» زمان را مسدود نمی‌کند و فقط در امتیازدهی زمان‌بندی اثر دارد؛ «بلوک منعطف» یک فعالیت برنامه‌ریزی‌شده با مدت است که می‌تواند جابه‌جا شود. این دو نباید در مدل داده یک مفهوم واحد فرض شوند.
- **تصمیم قطعی کاربر دربارهٔ تغییر برنامه:** تغییر یک تعهد ثابت فقط به‌صورت استثنای همان تاریخ ثبت می‌شود؛ الگوی هفتگی پایه با لغو یا جابه‌جایی یک جلسه تغییر نمی‌کند. این تصمیم از تغییرات ناخواستهٔ هفته‌های آینده جلوگیری می‌کند.
- **تصمیم قطعی کاربر دربارهٔ انواع استثنا:** هر الگوی هفتگی می‌تواند برای یک تاریخ مشخص استثنای «لغو جلسه»، «تغییر همان جلسه» یا «جایگزینی/افزودن جلسهٔ مخصوص همان تاریخ» داشته باشد. همهٔ این موارد فقط روی تاریخ هدف اثر می‌گذارند و الگوی پایه را تغییر نمی‌دهند.
- **تصمیم قطعی کاربر دربارهٔ زمان‌بندی مجدد:** وقتی استثنای یک تاریخ زمان آزاد ایجاد می‌کند، موتور می‌تواند وظایف/فعالیت‌های منعطف را برای آن بازه پیشنهاد و برنامهٔ جایگزین را پیش‌نمایش کند؛ هیچ جابه‌جایی بدون تأیید صریح کاربر اعمال نمی‌شود. تعهدهای ثابت همچنان دست‌نخورده‌اند.
- **بازبینی رقبا پیش از تصمیم‌گیری دربارهٔ زمان‌های منعطف (2026-11-12):** مستندات رسمی Motion، Reclaim، Sunsama، SkedPal و Akiflow مرور شد. الگوهای مهم: Motion از مدت، تاریخ شروع، deadline سخت/منعطف، اولویت، chunking، برنامهٔ کاری و رویدادهای ثابت استفاده می‌کند؛ Reclaim از ساعات کاری/شخصی، بازهٔ جابه‌جایی، حداقل مدت، اولویت، عادت‌ها و بافرها استفاده می‌کند و Preview Mode دارد؛ Sunsama زمان‌بندی وظیفه روی تقویم و برنامه‌ریزی روزانه همراه با پیش‌بینی workload و بازبینی را برجسته می‌کند؛ SkedPal از Time Maps برای ساعات ترجیحی، Flexible Plans، بودجهٔ زمانی و حداقل/بافر استفاده می‌کند؛ Akiflow زمان برنامه‌ریزی‌شده، مدت، تکرار، قفل‌کردن زمان و deadline را جداگانه نگه می‌دارد.
- **پیشنهاد طراحی (هنوز تصمیم قطعی نیست):** برای فعالیت منعطف، صرفاً «ساعت ترجیحی» کافی نیست. مدل باید بتواند هدف زمانی (مدت هر نوبت یا مجموع هفتگی)، پنجرهٔ مجاز/ترجیحی، deadline یا انتهای پنجره، حداقل طول هر نوبت و اجازه/عدم اجازهٔ تقسیم فعالیت را جدا کند. این‌ها نباید با تعهد ثابت یک نوع داده تلقی شوند.
- **ملاحظهٔ محصولی:** رفتار پیش‌فرض ویرا نباید مانند بعضی حالت‌های خودکار Motion، deadline سخت را به‌طور پنهانی مجوز برنامه‌ریزی خارج از ساعات مجاز بداند. اگر هیچ جای مناسبی وجود ندارد، بهتر است مورد unscheduled/at-risk نشان داده شود و پیشنهاد با پیش‌نمایش و تأیید کاربر ارائه شود.
- **جزئیات تکمیلی بازبینی مستندات رسمی:** Motion مدت کل، chunking، hard/soft deadline، start date، اولویت و custom working hours را از هم جدا می‌کند؛ برای Flexible Hours استثنای یک‌روزه دارد و در حالت Hard Deadline ممکن است خارج از ساعات معمول برنامه‌ریزی کند. Reclaim میان Tasks، Habits، Focus Time و Buffer Time تمایز می‌گذارد و عادت‌ها را به‌صورت زمان منعطفی می‌چیند که با تغییر تقویم سازگار می‌شوند. Sunsama بین Planned Time و Actual Time تمایز دارد، workload threshold روزانه و حالت Focused/Parallel دارد؛ در recurring task زمان شروع می‌تواند fixed یا rough باشد. SkedPal از Time Map ترجیحی، حداقل طول بلوک، buffer، بودجهٔ روزانه/هفتگی و Flexible Plan استفاده می‌کند و اگر از Time Map عبور کند بسته به تنظیمات می‌تواند پیشنهاد دهد یا زمان خارج از ترجیح را به‌کار ببرد. Motion از cadence روزانه، هفتگی، دوهفته‌ای، ماهانه و سفارشی پشتیبانی می‌کند؛ برای برخی نوبت‌های ازدست‌رفته، به‌جای انباشتن خودکار، همان occurrence را overdue نگه می‌دارد و نوبت بعدی طبق الگو ظاهر می‌شود. Motion همچنین می‌تواند تکرار را در پنجرهٔ زمانی سفارشی زمان‌بندی کند.
- **پیشنهاد طراحی برای Vira (هنوز نیازمند تأیید کاربر):** به‌جای یک سیستم تکرار بزرگ و پیچیده در نسخهٔ اول، سه مفهوم را جدا نگه داریم: (۱) تعهد/رویداد تکرارشونده با تاریخ و ساعت ثابت؛ (۲) وظیفهٔ تکرارشونده با نوبت‌های مستقل و تاریخ‌های محاسبه‌شده از الگو؛ (۳) هدف/عادت منعطف با بودجهٔ زمانی روزانه یا هفتگی که موتور آن را در پنجره‌های مجاز زمان‌بندی می‌کند. برای وظیفهٔ تکرارشونده، مبنای محاسبه باید قابل انتخاب باشد: تاریخ برنامه‌ریزی‌شده یا تاریخ تکمیل.
- **پیشنهاد مدیریت نوبت ازدست‌رفته:** occurrence ازدست‌رفته حذف نشود و نوبت‌های آینده نیز به‌طور خودکار عقب نیفتند. آن نوبت با وضعیت «انجام‌نشده/عقب‌افتاده» باقی بماند؛ کاربر بتواند آن را انجام‌شده، ردشده یا برای تاریخ دیگری زمان‌بندی کند. برای هدف منعطف هفتگی، کسری در جمع هفتگی ثبت شود و جبران فقط پیشنهاد شود؛ هدف هفتهٔ بعد خودکار افزایش نیابد. این پیشنهاد با تصمیم قبلی کاربر دربارهٔ عدم جابه‌جایی بدون تأیید سازگار است.
- **محدودهٔ نسخهٔ اولیهٔ پیشنهادی:** روزانه، روزهای مشخص هفته، هر N روز/هفته، ماهانه و پایان تکرار؛ الگوهای پیچیده‌تر (مثل چند قاعدهٔ ترکیبی، تقویم‌های تعطیلات، و استثناهای پیشرفته) به بعد موکول شوند. هر occurrence باید هویت مستقل داشته باشد تا تکمیل یا تغییر یک نوبت، الگوی مادر را ناخواسته تغییر ندهد.
- **منابع رسمی:** Todoist recurring dates https://www.todoist.com/help/todoist/features/introduction-to-recurring-dates-YUYVJJAV ؛ Motion recurring cadences https://www.usemotion.com/help/project-management/task/reference-tasks/recurring-task-cadences ؛ Motion missed recurrence FAQ https://www.usemotion.com/help/project-management/task/task-scheduling-faq ؛ Motion custom scheduling https://www.usemotion.com/help/time-management/auto-scheduling/auto-scheduling-how-to-guide .
- **وضعیت تصمیم:** بررسی رقبا و پیشنهاد ثبت شد؛ منتظر تأیید/اصلاح کاربر هستیم. هیچ کدی تغییر نکرده است.
- **تأیید کاربر دربارهٔ مبنای تکرار وظیفه:** هر وظیفهٔ تکرارشونده باید بتواند بین دو مبنا انتخاب کند: (۱) تقویم‌محور، occurrence بعدی از الگوی اصلی/تاریخ برنامه‌ریزی‌شده محاسبه شود، حتی اگر نوبت قبلی دیر انجام شده باشد؛ (۲) تکمیل‌محور، occurrence بعدی از تاریخ تکمیل واقعی نوبت قبلی محاسبه شود. این انتخاب متعلق به recurrence rule است و با تعهد ثابت یا هدف منعطف هفتگی یکی نیست.

### اصلاح مفهومی مهم دربارهٔ زمان

نمونهٔ اولیهٔ قبلی زمان شروع/پایان را داخل Task قرار می‌داد. در Target Architecture، زمان‌بندی هر نوبت کار به WorkSession منتقل می‌شود تا یک Task بتواند چند نشست مستقل داشته باشد. Task همچنان تاریخ برنامه‌ریزی، Deadline و مدت تخمینی کل را نگه می‌دارد. این تغییر فعلاً تصمیم طراحی است و به معنی تغییر مدل Canonical یا migration اجراشده نیست.

### موارد باز برای طراحی تفصیلی

- قرارداد دقیق فیلدها و statusهای WorkSession و TimeEntry
- چرخهٔ عمر تایمر و بازیابی پس از Refresh/بسته‌شدن برنامه
- سیاست هم‌پوشانی تایمر و اصلاح ثبت دستی
- جزئیات حذف/آرشیو و retention اسناد و نشست‌های تاریخی
- قرارداد دقیق Repositoryها و تراکنش چندموجودیتی
- schema version مقصد و نگاشت بدون اتلاف از مدل فعلی
- semantics کامل Habit، Routine، Recurrence و occurrence exception

### وضعیت آزمون و baseline

- آخرین نتیجهٔ محلی گزارش‌شده از سوی کاربر: ۸۵ تست موفق، صفر شکست.
- smoke test دستی مدت تخمینی: ساخت، ویرایش، Refresh و ماندگاری مقدار با موفقیت گزارش شده است.
- این نتایج، صحت طراحی جدید یا قابلیت‌های هنوز پیاده‌سازی‌نشده را تأیید نمی‌کنند.
- CI و پوشش کد در این مرحله ادعای تأییدشده ندارند.

### قدم بعدی

طراحی تفصیلی قراردادهای WorkSession و TimeEntry و سپس Repository/Unit of Work؛ بعد از آن تعریف migration مقصد. تا پیش از تکمیل این مراحل، کد اجرایی و دادهٔ موجود دست‌نخورده بمانند.

## ۲۰. طراحی تفصیلی WorkSession و TimeEntry — 2026-11-12

- **نوع:** طراحی مدل ثبت زمان و چرخهٔ عمر نشست کاری
- **وضعیت:** پیشنهاد معماری ثبت‌شده؛ هنوز پیاده‌سازی نشده است.
- **اصل کلیدی:** زمان واقعی از بازه‌های ثبت‌شده محاسبه می‌شود، نه از شمارنده‌ای که هر ثانیه در حافظه افزایش می‌یابد.

### تصمیم‌های طراحی پیشنهادی

1. Task مدت تخمینی کل را نگه می‌دارد؛ WorkSession نمایندهٔ یک نوبت کار است؛ TimeEntry زمان واقعی آن نوبت را ثبت می‌کند.
2. وضعیت‌های WorkSession عبارت‌اند از planned، in_progress، completed و cancelled. مکث به معنی بسته‌شدن بازهٔ تایمر است، نه تغییر وضعیت اصلی نشست.
3. هر شروع/ادامهٔ تایمر یک TimeEntry تازه می‌سازد؛ مکث یا پایان، بازهٔ فعال را می‌بندد.
4. TimeEntry سه نوع دارد: بازهٔ تایمری، مدت دستی بدون ساعت دقیق و بازهٔ دقیق ثبت‌شده به‌صورت دستی.
5. در نسخهٔ پایه فقط یک تایمر فعال در کل برنامه مجاز است.
6. پس از Refresh، بازهٔ فعال از storage بازیابی و زمان از timestampها محاسبه می‌شود.
7. پس از بازگشت از بسته‌شدن مرورگر، بازهٔ فعال مشکوک یا طولانی باید به کاربر نمایش داده شود و بدون تأیید بی‌قیدوشرط نهایی نشود.
8. ثبت‌های دقیق هم‌پوشان نباید دوبار شمرده شوند؛ ثبت مدت بدون ساعت دقیق نباید به بازهٔ ساختگی تبدیل شود.
9. زمان واقعی نشست و Task از TimeEntryهای معتبر محاسبه می‌شود؛ اصلاح تخمین آینده خودکار نیست.

### مواردی که پیش از پیاده‌سازی باید نهایی شوند

- آستانه و تجربهٔ تأیید بازهٔ طولانی پس از بازیابی
- سیاست اصلاح/حذف TimeEntry و نگهداری تاریخچه
- رفتار تغییر ساعت سیستم و خواب دستگاه
- قفل بین چند tab و جلوگیری از شروع تایمر هم‌زمان
- قرارداد دقیق timestamp و timezone
- معیار تشخیص و حل هم‌پوشانی ثبت دستی و تایمری

### دامنهٔ تغییر

فقط docs/ARCHITECTURE.md و این Checkpoint به‌روزرسانی می‌شوند. هیچ کد اجرایی، دادهٔ ذخیره‌شده یا رابط کاربری تغییر نمی‌کند.

### تصمیم‌های تکمیلی ثبت زمان — 2026-11-12

- در بازیابی تایمر باز، کاربر باید زمان پایان واقعی را تأیید یا اصلاح کند؛ بازهٔ تأییدنشده به‌طور خودکار در Actual Duration شمرده نمی‌شود.
- اصلاح TimeEntry با رکورد اصلاحی/جایگزین قابل‌ردیابی انجام می‌شود؛ حذف عادی به معنی void کردن از محاسبه است، نه حذف فیزیکی بی‌ردپا.
- در هر لحظه فقط یک تب مالک تایمر فعال است. Web Locks می‌تواند کمک کند، اما localStorage/BroadcastChannel به‌تنهایی قفل اتمیک تضمین نمی‌کنند.
- اگر مالکیت انحصاری قابل تضمین نباشد، شروع تایمر جدید متوقف می‌شود (fail-closed).
- انتخاب adapter و سازوکار قفل چندتب پیش‌نیاز پیاده‌سازی تایمر است.

## ۲۱. تأیید مقصد محصول به‌صورت اپلیکیشن دسکتاپ مستقل — 2026-11-12

- **نوع:** تصمیم محصول / اصلاح الزام معماری و استقرار
- **وضعیت:** مقصد محصول تأیید شده؛ فناوری Desktop Shell و پایگاه داده هنوز انتخاب نشده‌اند.
- **تصمیم صریح کاربر:** Vira Planner باید در نهایت یک اپلیکیشن واقعی و قابل نصب باشد؛ نه وب‌سایت و نه ابزاری که برای استفادهٔ روزمره به VS Code وابسته باشد.
- **توضیح محیط توسعه:** VS Code، Node.js و ابزارهای build فقط برای توسعه و ساخت نسخه‌ها هستند. کاربر نهایی باید بتواند برنامه را از طریق نصب‌کننده نصب کند و از منوی Start/آیکون اجرا کند.
- **وضعیت prototype:** نسخهٔ مرورگری فعلی فقط نمونهٔ اولیهٔ توسعه و تست است؛ این وضعیت با مقصد نهایی محصول تعارض ندارد، به شرط آنکه معماری از همین حالا مسیر انتقال کنترل‌شده را حفظ کند.
- **هدف انتشار اولیه:** Windows desktop. حداقل نسخهٔ پشتیبانی‌شدهٔ Windows و امکان پشتیبانی آینده از سیستم‌عامل‌های دیگر پس از بررسی فنی مشخص می‌شود.
- **الزامات محصول نهایی:** installer مستقل، پنجرهٔ اختصاصی، آیکون، اجرای مستقل از VS Code/ترمینال/مرورگر، ذخیره‌سازی محلی قابل‌اعتماد، مدیریت فایل‌های کاربر، backup/restore و مسیر نسخه‌بندی و به‌روزرسانی.
- **اصل جلوگیری از بازنویسی:** کد موجود بی‌دلیل دور ریخته نمی‌شود. منطق Domain/Application تا حد ممکن مستقل می‌ماند و مرز Presentation، Desktop Shell و Infrastructure با adapter مشخص می‌شود.
- **گزینه‌های فنی:** Tauri نامزد اولیهٔ بررسی و Electron گزینهٔ مقایسه‌ای است؛ هیچ‌کدام هنوز انتخاب قطعی نیستند. SQLite نامزد جدی storage نهایی است؛ انتخاب آن نیز منوط به بررسی migration، backup، تراکنش، امنیت و مدیریت فایل است.
- **اصل داده:** LocalStorage فعلی فقط storage نمونهٔ اولیه است و نباید بدون تصمیم و برنامهٔ migration، storage نهایی اپلیکیشن فرض شود. هیچ دادهٔ موجودی در این مرحله تغییر نکرده است.
- **اصل امنیت:** اپ دسکتاپ مجوز ذخیرهٔ API key در bundle یا کد رابط را نمی‌دهد. راهبرد OS credential store یا backend امن باید جداگانه ارزیابی شود.
- **دامنهٔ این مرحله:** فقط اسناد معماری و checkpoint به‌روزرسانی می‌شوند؛ هیچ کد اجرایی، schema ذخیره‌شده، دادهٔ کاربر، branch اصلی یا رابط فعلی تغییر نمی‌کند.

### معیارهای انتخاب فناوری در مرحلهٔ بعد

1. سازگاری با Windows 10/11 و پیش‌نیازهای نصب
2. اندازهٔ بسته، مصرف منابع و زمان راه‌اندازی
3. امنیت دسترسی به فایل‌ها، شبکه و کلیدها
4. installer، امضای برنامه و به‌روزرسانی
5. کیفیت دسترسی به اعلان‌ها و قابلیت‌های سیستم‌عامل
6. پیچیدگی نگهداری و تست برای توسعه‌دهندهٔ کوچک
7. سازگاری با پایگاه دادهٔ محلی و backup/restore
8. امکان توسعهٔ آینده بدون تعهد زودهنگام به چند سیستم‌عامل

### گام بعدی

ابتدا وابستگی‌های browser-specific موجود در کد را شناسایی می‌کنیم؛ سپس Tauri و Electron و گزینه‌های storage را با معیارهای بالا مقایسه می‌کنیم. پس از تصمیم مستند، یک proof of concept کوچک برای نصب، اجرای مستقل، ذخیره و بازیابی داده ساخته و آزمایش می‌شود. تا آن زمان بازنویسی یا انتقال سراسری کد انجام نمی‌شود.

## ۲۲. ممیزی اولیهٔ کد و بررسی فناوری دسکتاپ — 2026-11-12

- **نوع:** ممیزی read-only و بررسی مستندات رسمی
- **وضعیت:** ممیزی مقدماتی انجام شد؛ انتخاب فناوری هنوز باز است.
- **شاخه:** `foundation/architecture-v0-5`
- **فایل‌های کد تغییرکرده:** هیچ‌کدام.

### یافته‌های مستقیم از مخزن

1. `package.json` فقط اسکریپت تست Node را تعریف می‌کند و dependency خارجی npm ندارد.
2. رابط فعلی با `index.html` و `app.js` به‌صورت ES module اجرا می‌شود.
3. `app.js` مستقیماً به DOM وابسته است و Presentation از `document.createElement` استفاده می‌کند.
4. storage فعلی در `src/infrastructure/storage/local-task-storage.js` به `globalThis.localStorage` متکی است.
5. در فایل‌های بررسی‌شدهٔ Domain و Application، استفادهٔ مستقیم از browser API مشاهده نشد؛ این یک نشانهٔ مثبت است، اما audit کامل هنوز باقی است.
6. بنابراین UI فعلی احتمالاً در WebView قابل استفاده است و بیشترین جداسازی لازم در storage و مرز قابلیت‌های native رخ می‌دهد.

### یافته‌های تحقیق فناوری

- Tauri 2 از WebView2 در Windows استفاده می‌کند؛ مستندات رسمی، Windows 7+ را پشتیبانی‌شده می‌دانند و WebView2 را در Windows 10 نسخهٔ 1803+ موجود اعلام می‌کنند. توسعهٔ Windows به Rust و Microsoft C++ Build Tools نیاز دارد.
- Tauri برای Windows installerهای MSI و NSIS دارد. حالت پیش‌فرض bootstrapper ممکن است هنگام نصب به اینترنت نیاز داشته باشد؛ حالت offline installer حجم قابل‌توجهی اضافه می‌کند. این موضوع باید با نیاز نصب آفلاین کاربر سنجیده شود.
- Electron در مستندات فعلی Windows 10+ را پشتیبانی می‌کند و Chromium/Node را همراه برنامه ارائه می‌کند؛ برای کاربر JavaScript محور، مسیر یادگیری ساده‌تری دارد، اما footprint باید اندازه‌گیری شود.
- SQLite تراکنش‌های ACID، خواندن هم‌زمان و نوشتن سریالی، و API پشتیبان‌گیری آنلاین دارد. در صورت انتخاب WAL باید نسخهٔ SQLite pin شود و نسخهٔ اصلاح‌شدهٔ 3.51.3 یا جدیدتر در نظر گرفته شود.

### نتیجهٔ موقت

- Tauri 2 گزینهٔ اول برای ساخت proof of concept است؛ Electron گزینهٔ مقایسه‌ای باقی می‌ماند.
- SQLite گزینهٔ ترجیحی برای آزمایش storage است؛ هنوز migration یا تعویض LocalStorage تصویب نشده است.
- انتخاب نهایی به آزمایش واقعی روی نسخهٔ Windows هدف، اندازهٔ installer، مصرف RAM، سهولت build، backup/restore و امنیت بستگی دارد.
- هیچ dependency، Rust toolchain، Tauri، Electron یا SQLite به پروژه اضافه نشده است.

### اقدام بعدی

ابتدا نسخهٔ دقیق Windows 10 دستگاه توسعه را مشخص می‌کنیم. سپس proof of concept حداقلی Tauri و مقایسهٔ آن با Electron را طراحی می‌کنیم؛ در این مرحله هیچ‌یک از قابلیت‌های اصلی Planner بازنویسی نمی‌شوند.

## تصمیم تکمیلی: اپلیکیشن دسکتاپ چندسکویی

### تصمیم محصول
Vira Planner باید اپلیکیشن دسکتاپ مستقل و قابل نصب باشد، نه وب‌سایت. معماری از ابتدا برای Windows، macOS و Linux در نظر گرفته می‌شود؛ انتشار مرحله‌ای است و نسخهٔ Windows نخستین هدف اجرایی خواهد بود. این تصمیم محدودهٔ محصول است، نه ادعای آماده‌بودن خروجی‌های این سیستم‌عامل‌ها.

### تصمیم‌های فنی باز
- Tauri 2 گزینهٔ نخست برای نمونهٔ فنی و Electron گزینهٔ جایگزین مقایسه است؛ هیچ‌کدام هنوز انتخاب نهایی نیستند.
- SQLite گزینهٔ اولیهٔ بررسی برای پایگاه دادهٔ محلی است؛ هنوز migration یا انتخاب نهایی انجام نشده است.
- لایه‌های Domain و Application باید مستقل از سیستم‌عامل و Desktop Shell بمانند.
- LocalStorage فعلی نمونهٔ اولیه است و ذخیره‌سازی نهایی دسکتاپ باید با طراحی migration و آزمون بازیابی انتخاب شود.
