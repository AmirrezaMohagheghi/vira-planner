# معماری فنی ویرا

نسخه: 0.5-draft  
هدف: تبدیل نمونهٔ اولیهٔ تک‌فایلی به سامانه‌ای ماژولار، local-first و قابل‌آزمایش.

## ۱. اصول معماری

1. جداسازی رابط کاربری، منطق دامنه، ذخیره‌سازی و اتصال‌های بیرونی
2. موتور زمان‌بندی مستقل از هوش مصنوعی
3. کارکرد آفلاین هستهٔ محصول بدون مدل AI محلی
4. حداقل‌سازی وابستگی‌ها و هزینهٔ اجرا
5. نسخه‌دار بودن مدل داده و مهاجرت کنترل‌شده
6. آزمون‌پذیری منطق تاریخ، تکرار، اعلان و زمان‌بندی
7. امنیت کلیدهای API در سمت سرور

## ۵. ذخیره‌سازی و مهاجرت

نسخهٔ فعلی از LocalStorage با کلید `vira-planner-tasks-v1` استفاده می‌کند. نام کلید برای سازگاری حفظ شده، اما قالب محتوای آن نسخه‌دار است:

```js
{
  schemaVersion: 2,
  tasks: [/* canonical tasks */]
}
```

- آرایهٔ خام قدیمی، قالب v1 محسوب می‌شود.
- قالب v2 فقط Taskهای Canonical کامل و معتبر را می‌پذیرد.
- `schemaVersion` نسخهٔ ساختار ذخیره‌سازی است و با `task.version` تفاوت دارد.
- نسخهٔ ناشناخته یا جدیدتر هرگز بازنویسی نمی‌شود.
- شناسهٔ تکراری یا حتی یک Task نامعتبر، کل مجموعه را رد می‌کند.
- فیلدهای ناشناخته حفظ می‌شوند؛ aliasهای سازگاری UI یعنی `date`, `time`, `category`, `done` در مسیر ذخیره‌سازی Canonical حذف می‌شوند.

### مرز مسئولیت‌ها

1. Infrastructure قالب JSON، نسخه، خواندن/نوشتن، backup و بررسی read-back را مدیریت می‌کند.
2. Application با `legacy-task-adapter` دادهٔ v1 را به مدل Canonical تبدیل و سپس برای UI aliasهای سازگاری را تولید می‌کند.
3. Domain اعتبار Taskهای Canonical را تعیین می‌کند.
4. Collection فقط پس از بارگذاری موفق اجازهٔ تغییر داده می‌دهد.

### مسیر مهاجرت v1 به v2

1. خواندن آرایهٔ خام قدیمی بدون تغییر آن
2. اعتبارسنجی ساختار پایه و یکتایی شناسه‌ها
3. تبدیل Legacy در لایهٔ Application
4. اعتبارسنجی کامل همهٔ Taskها در Domain
5. ذخیرهٔ دقیق raw قبلی در backup
6. نوشتن envelope نسخهٔ ۲
7. خواندن مجدد و بررسی صحت قالب و داده
8. در صورت شکست، تلاش برای بازگرداندن مقدار قبلی و قفل ماندن عملیات عادی

Backup شامل رشتهٔ خام قبلی است. بازیابی، ابتدا محتوای پشتیبان را parse و بررسی می‌کند، مقدار فعلی را در کلید rollback جداگانه نگه می‌دارد و سپس مقدار پشتیبان را جایگزین می‌کند. LocalStorage تراکنش چندمرحله‌ای واقعی ندارد؛ بنابراین این طراحی از حفظ نسخه‌ها و rollback best-effort استفاده می‌کند و ادعای atomicity کامل ندارد.

هیچ migration نباید بی‌صدا دادهٔ ناسازگار را حذف یا با default پنهان کند. در صورت خطا، دادهٔ خام باید حفظ و نوشتن عادی متوقف شود.

انتقال به پایگاه دادهٔ محلی مانند IndexedDB فقط پس از بررسی نیاز واقعی و طراحی مهاجرت مستقل انجام می‌شود.

## ۶. موتور زمان‌بندی

موتور ورودی‌های صریح می‌گیرد:
- تعهدات ثابت (hard constraints)
- ترجیحات (soft constraints)
- وظایف با مدت، اولویت، deadline و dependency
- زمان‌های استراحت و buffer
- ساعات قابل برنامه‌ریزی

خروجی:
- time blocks پیشنهادی
- وظایف زمان‌بندی‌نشده
- تعارض‌ها
- توضیح علت هر تصمیم
- تغییرات نسبت به برنامهٔ فعلی

AI فقط ورودی زبان طبیعی را به ساختار قابل‌اعتبارسنجی تبدیل می‌کند. موتور نباید به پاسخ احتمالی مدل برای تشخیص تداخل یا رعایت محدودیت‌ها متکی باشد.

## ۷. اعلان و صدا

NotificationService باید از منطق وظایف جدا باشد و adapterهای مستقل داشته باشد:
- in-app notifications
- browser notifications
- audio playback
- speech synthesis
- future platform notification adapter

زمان‌بندی اعلان باید از دادهٔ پایدار بازسازی شود؛ اتکا به setTimeoutهای طولانی یا تایمر زندهٔ صفحه کافی نیست. رفتار پس از بسته‌شدن مرورگر به قابلیت واقعی مرورگر/سیستم‌عامل و مجوزهای کاربر وابسته است و باید جداگانه آزمون شود.

## ۱۲. قرارداد مدل داده و ارتباط موجودیت‌ها — Target Architecture v0.6

**وضعیت:** طراحی هدف؛ هنوز پیاده‌سازی نشده است. این بخش جهت طراحی را مشخص می‌کند و جایگزین فوری مدل ذخیره‌شدهٔ فعلی نیست.

### ۱۲.۱ اصول مشترک مدل

1. هر موجودیت پایدار یک شناسهٔ یکتا و مستقل دارد.
2. هر موجودیت مالک داده‌های خودش است؛ نماها و ماژول‌های دیگر فقط از طریق شناسه و قرارداد مشخص به آن ارجاع می‌دهند.
3. حذف یا آرشیو یک موجودیت نباید به‌طور ضمنی موجودیت‌های مستقل دیگر را حذف کند.
4. زمان‌های دقیق به‌صورت timestamp استاندارد و همراه با منطقهٔ زمانی لازم ذخیره می‌شوند؛ تاریخ بدون ساعت به‌صورت date-only با قالب ISO ذخیره می‌شود.
5. زمان نمایش شمسی و محلی‌سازی اعداد مسئولیت Presentation است؛ تبدیل و اعتبارسنجی تاریخ در لایه‌های مشترک باید صریح و آزمون‌پذیر باشد.
6. نام فیلدها و schema ذخیره‌سازی بخشی از قرارداد سازگاری‌اند؛ تغییر نام یا معنای فیلد نیازمند migration است.
7. شناسهٔ داخلی، وضعیت، زمان ایجاد/ویرایش و نسخهٔ موجودیت باید از داده‌های نمایشی UI مستقل بمانند.

### ۱۲.۲ موجودیت‌ها و مالکیت داده

- **Task:** مالک عنوان، توضیح، وضعیت، پیشرفت، اولویت، تاریخ برنامه‌ریزی، deadline، مدت تخمینی، وابستگی‌ها و ارجاع به پروژهٔ اصلی.
- **Project:** مالک مشخصات و چرخهٔ عمر پروژه؛ وظایف به آن ارجاع می‌دهند و دادهٔ وظایف داخل Project کپی نمی‌شود.
- **Goal:** مالک تعریف هدف، معیار سنجش، مقدار هدف/فعلی و وضعیت آن.
- **CalendarEvent:** مالک تعهد یا رویداد مستقل زمانی، مانند کلاس یا جلسهٔ ثابت.
- **WorkSession:** مالک یک نشست کاری مرتبط با دقیقاً یک Task؛ زمان برنامه‌ریزی‌شده و وضعیت همان نشست در این موجودیت نگهداری می‌شود.
- **TimeEntry:** ثبت یک بازهٔ تایمر یا مدت دستی که به یک WorkSession تعلق دارد؛ مبنای محاسبهٔ زمان واقعی است.
- **Document:** مالک فرادادهٔ سند؛ محتوای فایل در لایهٔ نگهداری فایل قرار می‌گیرد و نباید در رکوردهای Task یا Project تکرار شود.
- **Habit / Routine:** مالک تعریف رفتارهای تکرارشونده و هدف‌های منعطف؛ با رویداد ثابت و Task تکرارشونده یکی نیست.
- **RecurrenceRule:** مالک قاعدهٔ تکرار؛ occurrence و exception باید به قاعدهٔ اصلی ارجاع دهند و تغییر یک occurrence نباید الگوی اصلی را بازنویسی کند.
- **Reminder:** مالک تنظیمات و وضعیت یادآوری؛ هدف یادآوری با نوع و شناسهٔ موجودیت مرجع مشخص می‌شود.

### ۱۲.۳ روابط پایه

| رابطه | قرارداد پیشنهادی |
|---|---|
| Project → Task | هر Task در نسخهٔ پایه حداکثر یک Project اصلی دارد؛ Task مستقل نیز مجاز است |
| Goal ↔ Task | چندبه‌چند؛ از رابطهٔ مستقل GoalTaskLink استفاده شود |
| Goal ↔ Project | چندبه‌چند؛ از رابطهٔ مستقل GoalProjectLink استفاده شود |
| Task → WorkSession | یک‌به‌چند؛ هر WorkSession دقیقاً به یک Task تعلق دارد |
| WorkSession → TimeEntry | یک‌به‌چند؛ هر ثبت زمان دقیقاً متعلق به یک نشست است |
| Document ↔ سایر موجودیت‌ها | چندبه‌چند از طریق DocumentLink با نوع و شناسهٔ مقصد |
| Task → Task | وابستگی و زیرکار با ارجاع شناسه‌ای؛ چرخهٔ dependency باید رد شود |
| CalendarEvent → RecurrenceRule | صفر یا یک قاعدهٔ تکرار؛ استثناها مستقل و ارجاع‌دار |
| Reminder → هدف | یک ارجاع نوع‌دار به موجودیت پشتیبانی‌شده |

در نسخهٔ پایه، Task فقط یک Project اصلی خواهد داشت تا پیچیدگی بی‌دلیل ایجاد نشود. اگر نیاز واقعی به حضور یک Task در چند پروژه اثبات شد، این تصمیم با رابطهٔ مستقل تغییر می‌کند؛ نباید چند projectId را به‌صورت آرایه‌ای بدون تعریف معنا اضافه کنیم.

### ۱۲.۴ زمان‌بندی و نمای تقویم

- Task مالک deadline و تاریخ برنامه‌ریزی date-only است؛ داشتن این فیلدها به‌تنهایی بلوک ساعت‌دار ایجاد نمی‌کند.
- WorkSession مالک بازهٔ کاری برنامه‌ریزی‌شده است و به‌صورت بلوک زمانی در تقویم نمایش داده می‌شود.
- CalendarEvent مالک تعهد مستقل ثابت یا تکرارشونده است.
- تقویم یک **Projection** از CalendarEventها، WorkSessionها، وظایف تمام‌روز و markerهای deadline می‌سازد؛ مالک نسخهٔ دوم داده نیست.
- TimeBlock در صورت نیاز به‌عنوان خروجی محاسباتی یا پیشنهاد زمان‌بندی ساخته می‌شود؛ تا وقتی ضرورت ذخیره‌سازی مستقل آن اثبات نشده، نباید نسخهٔ کپی‌شدهٔ زمان WorkSession یا CalendarEvent باشد.
- منطقهٔ زمانی برای زمان دقیق صریح است. تاریخ بدون ساعت نباید با نیمه‌شب ساختگی به timestamp تبدیل شود.
- مدت تخمینی Task از مدت برنامه‌ریزی‌شدهٔ نشست و زمان واقعی ثبت‌شده مستقل است.

### ۱۲.۵ ثبت زمان واقعی

- هر WorkSession می‌تواند چند TimeEntry داشته باشد.
- TimeEntry از نوع timer interval باید زمان شروع و پایان معتبر داشته باشد؛ مدت آن از بازه محاسبه می‌شود.
- TimeEntry دستی باید مدت مثبت و منشأ ثبت مشخص داشته باشد.
- بازه‌های تایمر هم‌پوشان نباید دوبار شمرده شوند؛ سیاست جلوگیری از هم‌پوشانی و تایمر هم‌زمان باید در use case ثبت زمان اعمال و آزمون شود.
- اصلاح ثبت دستی نباید با افزودن دوبارهٔ همان مدت، زمان را دوبرابر کند؛ رکورد اصلاح‌شده باید قابل ردیابی باشد.
- مجموع زمان واقعی از ثبت‌های معتبر نشست محاسبه می‌شود؛ مقدار تجمیعی نباید بدون قاعده به‌عنوان دادهٔ مستقل و متناقض ذخیره شود.
- چرخهٔ عمر تایمر، بازیابی پس از Refresh/بسته‌شدن برنامه و تاریخچهٔ اصلاحات پیش از پیاده‌سازی به طراحی تفصیلی نیاز دارد.

### ۱۲.۶ روابط اسناد

Document فقط یک بار ثبت می‌شود. DocumentLink حداقل شامل شناسهٔ خودش، documentId، نوع مقصد، شناسهٔ مقصد، زمان ایجاد و منشأ ارتباط است. ایجاد و حذف پیوند باید از Application use case عبور کند و وجود هر دو سمت رابطه را بررسی کند.

چون رابطهٔ نوع‌دار به‌تنهایی ممکن است در همهٔ پایگاه‌های داده foreign key مستقیم نداشته باشد، اعتبارسنجی مقصد در لایهٔ Application الزامی است. اگر در آینده پایگاه دادهٔ رابطه‌ای انتخاب شود، برای روابط پرتکرار می‌توان جدول‌های پیوند اختصاصی و محدودیت‌های واقعی foreign key تعریف کرد.

### ۱۲.۷ حذف، آرشیو و پیوندهای یتیم

- حذف دائمی با تأیید صریح و سیاست مشخص انجام می‌شود.
- آرشیو، حذف دائمی نیست و برای موجودیت‌های پشتیبانی‌شده باید امکان بازیابی داشته باشد.
- حذف Project نباید Taskهای آن را بی‌صدا حذف کند؛ ابتدا باید سیاست انتقال، مستقل‌کردن یا رد حذف تعیین شود.
- حذف Task نباید WorkSession و TimeEntryهای تاریخی را بدون سیاست retention از بین ببرد.
- حذف Document باید وضعیت فایل و پیوندها را هماهنگ کند؛ شکست هر مرحله باید قابل تشخیص و بازیابی باشد.
- پاک‌سازی پیوندهای یتیم فقط از طریق عملیات کنترل‌شده و گزارش‌پذیر انجام می‌شود.

## ۱۳. قرارداد Repository و مرز Application

### ۱۳.۱ اصل

Domain نباید LocalStorage، IndexedDB، فایل‌سیستم، HTTP یا API ارائه‌دهنده را بشناسد. Application از قراردادهای Repository استفاده می‌کند و Infrastructure آن‌ها را پیاده‌سازی می‌کند.

### ۱۳.۲ قراردادهای موردنیاز در معماری هدف

- TaskRepository
- ProjectRepository
- GoalRepository
- WorkSessionRepository
- TimeEntryRepository
- CalendarEventRepository
- DocumentRepository
- RecurrenceRepository
- ReminderRepository
- RelationRepository یا repositoryهای اختصاصی هر رابطه

هر Repository باید عملیات متناسب با aggregate خودش را ارائه دهد؛ مانند getById، list با فیلتر مشخص، save و حذف کنترل‌شده. رابط دقیق و نوع خروجی‌ها هنگام طراحی هر ماژول تعیین می‌شود؛ این فهرست الزام به ساخت هم‌زمان همهٔ Repositoryها نیست.

### ۱۳.۳ قواعد دسترسی

1. Presentation فقط Application use caseها را فراخوانی می‌کند.
2. Presentation مستقیماً Repository یا storage adapter را صدا نمی‌زند.
3. تغییر داده از مسیر use case و اعتبارسنجی Domain انجام می‌شود.
4. Repository مسئول نگاشت و ذخیره‌سازی است، نه تصمیم‌های محصولی یا زمان‌بندی.
5. queryهای نمایشی می‌توانند read model بسازند، اما read model مالک دادهٔ اصلی نیست.
6. خروجی Repository نباید مرجع mutable داخلی storage را به بیرون نشت دهد.

### ۱۳.۴ هماهنگی چند موجودیت

Use caseهایی مانند حذف Project، اتصال Document به Task یا تکمیل عملیات چندمرحله‌ای باید هماهنگی تغییرات را در Application مدیریت کنند.

در معماری هدف یک مرز Unit of Work/Transaction برای عملیات چندموجودیتی تعریف می‌شود. با این حال، LocalStorage فعلی تراکنش واقعی چندکلیدی ندارد؛ adapter فعلی فقط می‌تواند backup و rollback best-effort ارائه کند و نباید atomicity کامل ادعا شود. اگر تضمین تراکنش برای عملیات چندموجودیتی لازم شد، انتخاب پایگاه داده‌ای مانند IndexedDB و migration جداگانه باید پیش از پیاده‌سازی تصویب شود.

## ۱۴. راهبرد مهاجرت مدل داده

**اصل محافظه‌کارانه:** مدل فعلی Task و envelope ذخیره‌سازی موجود نباید صرفاً به‌دلیل طراحی جدید فوراً تغییر کند.

1. وضعیت واقعی schema و دادهٔ ذخیره‌شدهٔ فعلی، شامل envelope نسخهٔ ۲ و legacy، پیش از هر migration دوباره بررسی شود.
2. قرارداد نهایی فیلدها و روابط پیش از تعیین شمارهٔ schema بعدی تثبیت شود.
3. migration جدید به‌صورت مرحله‌ای و نسخه‌دار تعریف شود؛ افزایش schemaVersion فقط هنگام ورود واقعی ساختار ذخیره‌شدهٔ جدید انجام شود.
4. migration باید pure/testable باشد: ورودی را دریافت کند و خروجی نسخهٔ جدید را بسازد، بدون side effect پنهان.
5. پیش از نوشتن، کل دادهٔ تبدیل‌شده و روابط آن اعتبارسنجی شوند؛ دادهٔ ناقص یا رابطهٔ یتیم نباید بی‌صدا حذف شود.
6. raw قبلی پیش از نوشتن نسخهٔ جدید در backup مستقل حفظ شود.
7. پس از نوشتن، read-back و اعتبارسنجی کامل انجام شود.
8. در شکست، دادهٔ خام قبلی حفظ شود، عملیات عادی در وضعیت نامطمئن قفل بماند و خطای قابل فهم گزارش شود.
9. اجرای دوبارهٔ migration نباید دادهٔ تکراری بسازد؛ رفتار باید idempotent یا با تشخیص دقیق نسخه محدود شود.
10. فیلدهای ناشناخته تا زمانی که سیاست سازگاری روشن نشده حذف نشوند.
11. schemaVersion از version هر موجودیت مستقل است.
12. مهاجرت به IndexedDB یا backend پروژه‌ای جدا با ارزیابی ریسک، backup و تست بازیابی است؛ بخشی از این طراحی به‌تنهایی مجوز آن مهاجرت نیست.

### آزمون‌های پذیرش migration

- دادهٔ v2 معتبر و خالی
- چند Task با تمام فیلدهای اختیاری
- دادهٔ legacy قدیمی
- شناسهٔ تکراری و رابطهٔ نامعتبر
- فیلد ناشناخته
- نسخهٔ ذخیره‌سازی جدیدتر از نسخهٔ برنامه
- شکست هنگام نوشتن یا read-back
- بازیابی از backup
- اجرای دوبارهٔ migration
- اطمینان از عدم حذف یا تغییر دادهٔ اصلی در صورت شکست

## ۱۵. مرز AI با مدل داده و Application

- AI از طریق Application و ابزارهای محدود و مجاز به داده دسترسی می‌گیرد؛ دسترسی مستقیم به storage ندارد.
- خروجی AI ابتدا یک پیشنهاد ساختاریافته با منشأ، زمان تولید، میزان اطمینان و تغییرات پیشنهادی است.
- پیشنهاد قبل از اعمال باید از اعتبارسنجی Domain و قواعد قطعی عبور کند.
- اعمال تغییرات حساس، جابه‌جایی برنامه، حذف یا ارسال اطلاعات خصوصی تابع تأیید و مجوز کاربر است.
- AI نباید deadline، زمان واقعی، انجام‌شدن کار یا سندی را که منبع معتبری ندارد جعل کند.
- خاموش‌کردن AI نباید عملیات پایهٔ وظایف، تقویم و اسناد محلی را مختل کند.

## ۱۶. ترتیب اجرای این معماری

1. بازبینی این قرارداد در برابر مدل واقعی و تصمیم‌های ثبت‌شدهٔ محصول.
2. تثبیت نام فیلدها و semantics مربوط به Task، WorkSession و CalendarEvent.
3. تعریف قرارداد Repository و عملیات Application برای هر aggregate.
4. طراحی migration و آزمون‌های آن، بدون اجرای migration روی دادهٔ کاربر.
5. پیاده‌سازی مرحله‌ای هر بخش فقط پس از تصویب دامنه و معیار پذیرش آن.

**محدودیت این نسخه:** این Target Architecture نقشهٔ طراحی است؛ هیچ‌یک از Project، Goal، WorkSession، TimeEntry، Document Library یا Repositoryهای نام‌برده‌شده صرفاً با ثبت این سند، پیاده‌سازی‌شده محسوب نمی‌شوند.

## ۱۷. طراحی تفصیلی WorkSession و TimeEntry

**وضعیت:** قرارداد طراحی هدف؛ هنوز پیاده‌سازی نشده است.

### ۱۷.۱ جداسازی مسئولیت‌ها

- Task مالک مدت تخمینی کل کار و Deadline است.
- WorkSession نمایندهٔ یک نوبت مشخص کار روی Task است.
- هر WorkSession دقیقاً به یک Task تعلق دارد.
- یک Task می‌تواند چند WorkSession در روزهای مختلف داشته باشد.
- WorkSession مالک مدت برنامه‌ریزی‌شدهٔ همان نشست است.
- TimeEntry ثبت‌کنندهٔ زمان واقعی است؛ زمان واقعی نشست از TimeEntryهای معتبر محاسبه می‌شود و نباید با مدت تخمینی Task یا مدت برنامه‌ریزی‌شدهٔ نشست یکی فرض شود.

### ۱۷.۲ چرخهٔ عمر WorkSession

وضعیت‌های پیشنهادی:
- planned: نشست ساخته شده و هنوز شروع نشده است.
- in_progress: کار روی نشست شروع شده؛ ممکن است تایمر فعال یا متوقف باشد.
- completed: نشست به پایان رسیده است.
- cancelled: نشست لغو شده است و زمان‌های ثبت‌شدهٔ قبلی آن بدون سیاست retention حذف نمی‌شوند.

«مکث» وضعیت مستقل WorkSession نیست. نشست در وضعیت in_progress باقی می‌ماند، اما در آن لحظه TimeEntry تایمری فعال ندارد. با ادامهٔ کار، یک TimeEntry جدید ساخته می‌شود. بنابراین هر بار شروع/ادامه، بازه‌ای جدا ایجاد می‌کند.

### ۱۷.۳ مدل TimeEntry

نوع‌های پیشنهادی:
- timer_interval: دارای startedAt و endedAt؛ مدت از اختلاف دو timestamp محاسبه می‌شود.
- manual_duration: دارای durationSeconds مثبت و در صورت نیاز occurredOn؛ زمان دقیق شروع/پایان برای آن ادعا نمی‌شود.
- manual_interval: ثبت دستی بازهٔ دقیق شروع و پایان؛ مدت از دو timestamp محاسبه می‌شود.

فیلدهای پایه:
- id
- workSessionId
- kind
- startedAt و endedAt برای بازه‌ها
- durationSeconds برای مدت دستی
- createdAt و updatedAt
- source و در صورت نیاز note

اعتبارسنجی:
1. بازه باید پایان بعد از شروع داشته باشد.
2. مدت دستی باید عدد صحیح مثبت باشد.
3. یک TimeEntry نباید هم‌زمان مدت دستی و بازهٔ تایمری متناقض داشته باشد.
4. هر ثبت باید به WorkSession موجود متصل باشد.
5. مجموع زمان واقعی از ثبت‌های معتبر محاسبه شود؛ مقدار تجمیعی cacheشده فقط با راهبرد سازگاری روشن مجاز است.

### ۱۷.۴ رفتار تایمر

- در شروع، یک TimeEntry تایمری با startedAt ساخته می‌شود و endedAt خالی می‌ماند.
- در مکث، بازهٔ فعال با زمان فعلی بسته می‌شود.
- در ادامه، یک TimeEntry تازه ساخته می‌شود؛ بازهٔ قبلی هرگز بازنویسی نمی‌شود.
- در پایان نشست، بازهٔ فعال بسته و WorkSession تکمیل می‌شود.
- مدت تایمر با timestampهای پایدار محاسبه می‌شود، نه با افزایش شمارنده در هر ثانیه.
- شمارندهٔ بصری UI فقط نمایش محاسبهٔ زمان است؛ منبع حقیقت دادهٔ ذخیره‌شده است.
- فقط یک تایمر فعال در کل برنامه در نسخهٔ پایه مجاز است. این تصمیم از ثبت هم‌زمان و دوباره‌شماری زمان جلوگیری می‌کند؛ امکان چند تایمر هم‌زمان نیازمند نیازسنجی و طراحی مستقل است.

### ۱۷.۵ Refresh، بسته‌شدن مرورگر و بازیابی

- وضعیت بازهٔ فعال باید در storage پایدار ثبت شود؛ حافظهٔ صفحه یا setInterval منبع حقیقت نیست.
- پس از Refresh، برنامه بازهٔ فعال را از storage می‌خواند و زمان سپری‌شده را از timestampها دوباره محاسبه می‌کند.
- اگر برنامه پس از بسته‌شدن مرورگر دوباره باز شود و یک بازهٔ فعال پیدا کند، باید وضعیت بازیابی را آشکارا به کاربر نشان دهد.
- چون مرورگر نمی‌تواند با قطعیت تشخیص دهد کاربر در زمان بسته‌بودن برنامه واقعاً کار کرده یا نه، سیاست محافظه‌کارانه این است که پیش از نهایی‌کردن بازهٔ طولانی یا مشکوک، از کاربر تأیید بگیرد؛ بازه نباید بی‌صدا حذف یا بی‌قیدوشرط نهایی شود.
- تغییر ساعت سیستم، خواب دستگاه و اختلاف ساعت می‌توانند بر timestampها اثر بگذارند؛ مقادیر نامعتبر یا غیرعادی باید شناسایی و برای اصلاح به کاربر نشان داده شوند.
- زمان‌ها به‌صورت timestamp استاندارد ذخیره و در نمایش به منطقهٔ زمانی کاربر تبدیل می‌شوند.

### ۱۷.۶ ثبت دستی و جلوگیری از دوباره‌شماری

- کاربر می‌تواند مدت واقعی را دستی ثبت کند، حتی اگر تایمر استفاده نشده باشد.
- در صورت داشتن ساعت دقیق، ثبت دستی می‌تواند به‌صورت بازهٔ شروع/پایان باشد؛ در غیر این صورت فقط مدت و تاریخ تقریبی ثبت می‌شود.
- بازه‌های دقیق هم‌پوشان نباید دوبار در مجموع زمان واقعی شمرده شوند.
- نسخهٔ پایه یک تایمر فعال سراسری دارد؛ ثبت دستی هم‌پوشان با بازهٔ تایمر باید پیش از ذخیره هشدار داده شود و نیازمند تصمیم صریح کاربر باشد.
- ثبت مدت بدون ساعت دقیق را نباید به یک بازهٔ زمانی ساختگی تبدیل کرد.
- اصلاح ثبت باید به‌جای افزودن دوبارهٔ همان زمان، همان ثبت را اصلاح کند یا با یک رکورد اصلاحی قابل ردیابی همراه باشد. سیاست تاریخچهٔ کامل اصلاحات پیش از پیاده‌سازی نهایی می‌شود.

### ۱۷.۷ محاسبه و گزارش

- Actual Duration نشست = مجموع مدت TimeEntryهای معتبر و بدون هم‌پوشانی آن نشست.
- Actual Duration وظیفه = مجموع زمان واقعی نشست‌های متعلق به آن وظیفه.
- اختلاف مدت برنامه‌ریزی‌شده و واقعی برای گزارش و پیشنهاد تخمین آینده قابل استفاده است.
- اصلاح خودکار Estimated Duration یا برنامهٔ آینده بدون اطلاع و تأیید کاربر ممنوع است.
- زمان واقعی یک منبع ثبت‌شده است؛ وضعیت completed به‌تنهایی نباید زمان واقعی فرضی ایجاد کند.

### ۱۷.۸ آزمون‌های پذیرش

- شروع، مکث، ادامه و پایان یک نشست با چند بازه
- Refresh هنگام تایمر فعال و بازیابی درست
- بستن و بازکردن مرورگر با بازهٔ فعال
- توقف تایمر و اطمینان از اینکه زمان مکث محاسبه نمی‌شود
- ثبت دستی مدت بدون زمان دقیق
- ثبت دستی بازهٔ دقیق
- جلوگیری از تایمر فعال دوم
- تشخیص بازه‌های هم‌پوشان
- تغییر ساعت سیستم یا timestamp نامعتبر
- نشست لغوشده/تکمیل‌شده با ثبت‌های قبلی
- جمع زمان نشست‌ها در Task بدون دوباره‌شماری
- شکست ذخیره‌سازی و حفظ آخرین دادهٔ معتبر

**محدودیت:** این قرارداد هنوز طراحی است. هیچ تایمر، WorkSession یا TimeEntry اجرایی با ثبت این سند ایجاد نشده است.

### ۱۷.۹ تصمیم‌های تکمیلی: بازیابی، اصلاحات و چند تب

#### بازیابی پس از بازگشت به برنامه

1. اگر هنگام بارگذاری برنامه یک TimeEntry تایمری با endedAt خالی وجود داشته باشد، برنامه وارد وضعیت recovery می‌شود و شروع تایمر تازه را تا تعیین تکلیف متوقف می‌کند.
2. UI زمان شروع و مدت سپری‌شدهٔ تخمینی را نمایش می‌دهد و از کاربر می‌خواهد زمان واقعی پایان را تعیین کند.
3. گزینه‌ها باید دست‌کم شامل تأیید ادامهٔ بازه تا زمان انتخاب‌شده، اصلاح زمان پایان، یا ردکردن بخش تأییدنشده باشند.
4. بخش تأییدنشده نباید بی‌صدا در Actual Duration شمرده شود. ردکردن آن نیز نباید رکورد را بدون ردپا نابود کند؛ باید به‌صورت voided/rejected یا وضعیت حسابرسی مشابه نگهداری شود.
5. برای بازه‌های بسیار طولانی یا غیرعادی هشدار برجسته‌تری نمایش داده می‌شود؛ اما هیچ آستانهٔ زمانی جایگزین تأیید کاربر نیست.
6. پس از تعیین تکلیف بازهٔ باز، فقط آن‌گاه امکان شروع تایمر جدید فراهم می‌شود.

#### اصلاح و حذف TimeEntry

1. TimeEntry ثبت‌شده پس از تأیید نباید بی‌ردپا ویرایش یا حذف فیزیکی شود.
2. اصلاح از طریق یک رکورد اصلاحی یا نسخهٔ جایگزین انجام می‌شود که به رکورد اصلی ارجاع دارد.
3. رکورد اصلی و دلیل/زمان اصلاح برای audit نگهداری می‌شود؛ محاسبهٔ Actual Duration فقط رکورد معتبر و نهایی را لحاظ می‌کند.
4. حذف از دید کاربر به معنی خارج‌کردن از محاسبه (void) است، نه نابودی فوری داده.
5. پاک‌سازی فیزیکی فقط تحت سیاست retention و عملیات صریح و قابل‌بازیابی مجاز است.
6. اگر کاربر فقط یک مدت بدون ساعت دقیق ثبت کرده باشد، اصلاح آن نباید برایش ساعت شروع و پایان ساختگی ایجاد کند.

#### هماهنگی بین چند تب

1. در هر لحظه حداکثر یک مالک فعال تایمر در سطح برنامه وجود دارد.
2. تب مالک، شناسهٔ نشست و شناسهٔ TimeEntry فعال را در وضعیت پایدار نگه می‌دارد و رویداد تغییر را به تب‌های دیگر اطلاع می‌دهد.
3. تب‌های دیگر وضعیت تایمر را فقط‌خواندنی نمایش می‌دهند و اجازهٔ شروع تایمر دوم ندارند.
4. Web Locks API می‌تواند قفل انحصاری بین تب‌ها را در مرورگرهای پشتیبان فراهم کند؛ اما قرارداد برنامه نباید به آن به‌عنوان تنها لایهٔ صحت داده وابسته باشد.
5. localStorage و BroadcastChannel به‌تنهایی تضمین اتمیک در رقابت هم‌زمان دو تب ایجاد نمی‌کنند؛ پیام‌رسانی صرف، قفل محسوب نمی‌شود.
6. اگر adapter ذخیره‌سازی نتواند مالکیت انحصاری را با اطمینان برقرار کند، رفتار امن fail-closed است: شروع تایمر جدید مسدود و راهنمایی قابل فهم نمایش داده می‌شود.
7. انتخاب نهایی مکانیزم قفل باید پیش از پیاده‌سازی تایمر و همراه با adapter ذخیره‌سازی انجام شود؛ برای تضمین تراکنشی، IndexedDB با transaction مناسب گزینهٔ جدی‌تری از چند کلید localStorage است.

**معیار پذیرش:** دو تب که هم‌زمان برای شروع تایمر اقدام می‌کنند نباید بتوانند دو TimeEntry فعال معتبر ایجاد کنند. پس از بسته‌شدن تب مالک نیز بازیابی باید بدون گم‌شدن یا دوباره‌شماری داده انجام شود.

## ۱۸. مقصد استقرار محصول: اپلیکیشن دسکتاپ مستقل

- **وضعیت:** الزام محصولی تأییدشده؛ فناوری و جزئیات پیاده‌سازی هنوز انتخاب نشده‌اند.
- **تصمیم قطعی محصول:** خروجی نهایی Vira Planner یک اپلیکیشن دسکتاپ واقعی و قابل نصب است؛ وب‌سایت یا صفحه‌ای که کاربر برای استفادهٔ روزمره مجبور باشد آن را در مرورگر باز کند، محصول نهایی محسوب نمی‌شود.
- **محیط توسعه:** VS Code فقط ابزار توسعه است. کاربر نهایی برای اجرای برنامه نباید به VS Code، Node.js، ترمینال یا نصب ابزارهای توسعه نیاز داشته باشد.
- **نمونهٔ اولیه:** اجرای مرورگری فعلی صرفاً محیط موقت توسعه و اعتبارسنجی است. وجود `index.html` یا اجرای محلی در مرورگر به معنی هدف‌بودن وب‌اپلیکیشن نیست.
- **هدف انتشار اولیه:** اپلیکیشن قابل نصب برای Windows؛ حداقل نسخهٔ دقیق ویندوز و دامنهٔ پشتیبانی باید در مرحلهٔ انتخاب فناوری با شواهد سازگاری تعیین شود. پشتیبانی از macOS/Linux هدف احتمالی بعدی است، نه تعهد فعلی.
- **الزامات تجربهٔ نصب و اجرا:** بستهٔ نصب مستقل، آیکون و نام برنامه، پنجرهٔ اختصاصی، اجرای مستقل از ابزار توسعه، مسیر روشن ذخیرهٔ داده، و امکان بازکردن/بستن برنامه بدون از دست‌رفتن داده.
- **اصل معماری:** منطق Domain و Application باید تا حد امکان مستقل از Desktop Shell باقی بمانند. Presentation و Infrastructure از طریق interface/adapter به قابلیت‌های سیستم‌عامل و پایگاه داده متصل می‌شوند تا انتخاب یا تعویض shell باعث بازنویسی منطق اصلی نشود.

### ۱۸.۱ انتخاب Desktop Shell — هنوز تصمیم‌گیری نشده

گزینه‌هایی مانند Tauri و Electron باید پیش از تثبیت بررسی شوند. معیارهای مقایسه:
1. سازگاری واقعی با نسخه‌های هدف Windows و پیش‌نیازهای نصب
2. اندازهٔ خروجی، مصرف RAM/CPU و سرعت راه‌اندازی
3. امنیت مرز بین رابط، دسترسی فایل و قابلیت‌های سیستم‌عامل
4. بلوغ ابزارهای build، signing، installer و به‌روزرسانی
5. دسترسی به اعلان‌های سیستم، فایل‌ها، پنجره‌ها و قابلیت‌های موردنیاز
6. پیچیدگی توسعه و نگهداری برای تیم/توسعه‌دهندهٔ کوچک
7. امکان تست خودکار و عیب‌یابی روی دستگاه کاربر
8. هزینهٔ واقعی نگهداری و مسیر انتشار نسخه‌های بعدی

**Tauri گزینهٔ پیشنهادی اولیه برای ارزیابی است، نه انتخاب مصوب.** Electron نیز باید به‌عنوان گزینهٔ مقایسه‌ای سنجیده شود. تا پیش از بررسی سازگاری، packaging و نیازهای واقعی، shell را قطعی نمی‌کنیم.

### ۱۸.۲ راهبرد ذخیره‌سازی دسکتاپ — هنوز تصمیم‌گیری نشده

- محصول نهایی باید local-first باشد و داده‌های اصلی کاربر را در فضای محلی تحت کنترل او نگه دارد.
- پایگاه دادهٔ رابطه‌ای محلی مانند SQLite نامزد جدی است؛ اما انتخاب نهایی به بررسی تراکنش‌ها، migration، backup/restore، رمزنگاری در حالت سکون، دسترسی هم‌زمان، بازیابی پس از crash و بسته‌بندی وابسته است.
- LocalStorage فعلی فقط بخشی از نمونهٔ اولیه و سازگاری موجود است؛ نباید بدون تصمیم معماری به‌عنوان storage نهایی اپ دسکتاپ تثبیت شود.
- IndexedDB نیز به‌عنوان گزینهٔ واسط/موقت برای prototype قابل بررسی است، اما انتخاب آن به‌تنهایی نیاز محصول به فایل‌سیستم و دیتابیس desktop را حل نمی‌کند.
- مسیر مهاجرت باید داده‌های فعلی را حفظ کند: export/backup خام، تبدیل نسخه‌دار، اعتبارسنجی، read-back، گزارش خطا و rollback. هیچ جایگزینی بدون آزمون مهاجرت روی نسخهٔ کپی داده انجام نمی‌شود.
- فایل‌های اصلی PDF و سایر اسناد باید در فضای فایل محلی مدیریت شوند؛ دیتابیس فراداده و پیوندها را نگه می‌دارد و باید سیاست مسیر، نام، حذف، backup و فایل گمشده مشخص شود.

### ۱۸.۳ امنیت و اتصال‌های بیرونی در اپ دسکتاپ

- دسکتاپ بودن برنامه به معنی امن‌بودن خودکار API key نیست؛ کلید محرمانه نباید داخل bundle، کد frontend یا فایل تنظیمات قابل‌خواندن ذخیره شود.
- گزینه‌های نگهداری کلید باید شامل OS credential store یا backend امن باشد؛ انتخاب به مدل استفاده از provider و تهدیدهای امنیتی وابسته است.
- اگر کاربر کلید شخصی provider را وارد کند، باید دربارهٔ محل ذخیره، سطح حفاظت، ارسال داده و امکان حذف کلید توضیح روشن ببیند.
- هر قابلیت cloud/AI اختیاری می‌ماند؛ هستهٔ مدیریت وظایف، زمان و اسناد باید بدون اتصال AI قابل استفاده باشد.
- دسترسی به فایل‌ها، اعلان‌ها، میکروفون و شبکه باید حداقلی، قابل توضیح و در صورت نیاز با رضایت کاربر فعال شود.

## ۱۹. ممیزی اولیهٔ کد و ارزیابی گزینه‌های Desktop — 2026-11-12

### ۱۹.۱ شواهد ممیزی مخزن فعلی

ممیزی read-only روی شاخهٔ توسعه انجام شد. فایل‌های اجرایی تغییر نکردند.

- `package.json` فقط اسکریپت `node --test` دارد و در حال حاضر dependency خارجی npm تعریف نکرده است.
- ورودی رابط `index.html` است و `app.js` به‌عنوان ES module بارگذاری می‌شود.
- `app.js` مستقیماً از `document.querySelector`، event listenerها و `scrollIntoView` استفاده می‌کند.
- ماژول‌های Presentation برای ساخت عناصر رابط از `document.createElement` استفاده می‌کنند؛ بنابراین UI فعلی به DOM وابسته است.
- `src/infrastructure/storage/local-task-storage.js` به‌طور پیش‌فرض `globalThis.localStorage` را دریافت می‌کند؛ ذخیره‌سازی فعلی browser storage است.
- در فایل‌های بررسی‌شدهٔ Domain و Application، وابستگی مستقیم به APIهای مرورگر مشاهده نشد؛ این نشانهٔ خوبی برای حفظ منطق اصلی است، اما ممیزی کامل تمام مسیرهای اجرا و وابستگی‌های ضمنی هنوز انجام نشده است.
- ساختار فعلی به‌صورت سادهٔ HTML/CSS/JavaScript ماژولار است و framework بزرگ frontend یا package dependency خارجی ندارد.

### ۱۹.۲ نتیجهٔ معماری از ممیزی

1. UI موجود را می‌توان در یک WebView دسکتاپ نمایش داد؛ لازم نیست به‌خاطر desktop شدن فوراً UI را از نو نوشت.
2. وابستگی DOM در Presentation طبیعی است و می‌تواند در WebView ادامه پیدا کند؛ اما دسترسی به فایل‌های سیستم‌عامل، اعلان native، credential store و database باید از طریق bridge/adapter محدود و قابل‌آزمون انجام شود.
3. بزرگ‌ترین مرز فنی که باید جدا شود، storage است: Application باید با قرارداد Repository کار کند و پیاده‌سازی فعلی LocalStorage فقط adapter نمونهٔ اولیه باقی بماند.
4. نباید APIهای native را مستقیماً در منطق Domain یا use caseها پخش کنیم.
5. پیش از افزودن shell، باید یک بررسی دقیق‌تر از همهٔ استفاده‌های browser API و رفتار ذخیره‌سازی در تست‌ها انجام شود.

### ۱۹.۴ ارزیابی مقدماتی و تصمیم باز

- **Tauri 2 نامزد اول برای proof of concept است** چون UI فعلی با WebView سازگار است و می‌توان منطق رابط را حفظ کرد؛ اما نیاز به Rust و ابزارهای native هزینهٔ یادگیری و راه‌اندازی دارد.
- **Electron گزینهٔ جایگزین جدی است** چون برای کاربر JavaScript/Node محور، مسیر توسعه احتمالاً ساده‌تر است؛ اما Chromium و Node همراه برنامه می‌آیند و باید اندازهٔ نصب، مصرف منابع و سطح دسترسی main/renderer سنجیده شود.
- هنوز هیچ‌کدام انتخاب نهایی نیستند. معیار تعیین‌کننده باید یک نمونهٔ واقعی روی Windows هدف باشد، نه صرفاً شهرت یا ادعای سبک‌بودن یک فناوری.
- پیش از تصمیم، نسخه/build دقیق Windows 10 دستگاه توسعه و حداقل سیستم‌عامل هدف انتشار باید مشخص شود. اگر قرار است Windows 10 قدیمی‌تر از 1803 پشتیبانی شود، فرض پیش‌فرض WebView2 نصب‌شده برای Tauri کافی نیست و installer باید runtime را مدیریت کند.

### ۱۹.۵ ارزیابی مقدماتی SQLite

SQLite نامزد اصلی storage محلی رابطه‌ای باقی می‌ماند، زیرا:
- transactionهای ACID و rollback را پشتیبانی می‌کند؛
- چند reader هم‌زمان را می‌پذیرد و writeها را به‌صورت سریالی مدیریت می‌کند؛
- Online Backup API برای ساخت snapshot از دیتابیس فعال دارد؛
- WAL می‌تواند هم‌زمانی reader و writer را بهتر کند، اما خود WAL هم فایل و قواعد checkpoint/recovery دارد و برای فایل‌سیستم شبکه‌ای مناسب نیست.

نکتهٔ نگهداری مهم: مستندات رسمی SQLite یک اشکال نادر WAL را گزارش کرده‌اند که در SQLite 3.51.3 و نسخه‌های بعدی رفع شده است. اگر WAL انتخاب شود، نسخهٔ SQLite باید pin و بررسی شود و صرفاً به نسخهٔ پیش‌فرض یک dependency ناشناخته اعتماد نکنیم.

منابع رسمی:
- https://www.sqlite.org/transactional.html
- https://www.sqlite.org/lang_transaction.html
- https://www.sqlite.org/backup.html
- https://www.sqlite.org/wal.html

**وضعیت:** SQLite گزینهٔ ترجیحی برای prototype storage است، نه مجوز مهاجرت فوری. انتخاب driver/bridge، رمزنگاری، مسیر فایل، backup و migration باید در طراحی بعدی تثبیت شوند.

### ۱۹.۶ گام بعدی فنی

1. تعیین نسخهٔ دقیق Windows 10 دستگاه توسعه و نسخهٔ حداقلی هدف.
2. طراحی یک proof of concept بسیار کوچک و جدا از قابلیت‌های اصلی: پنجرهٔ مستقل، ذخیرهٔ یک رکورد در SQLite، بستن/بازکردن برنامه و بازیابی رکورد.
3. ساخت همان سناریوی حداقلی با Tauri و Electron یا دست‌کم نمونهٔ قابل‌اندازه‌گیری برای هر دو.
4. مقایسهٔ installer size، زمان اجرا، RAM پس از بازشدن، سهولت build روی دستگاه واقعی و مسیر backup.
5. انتخاب shell و storage فقط پس از نتیجهٔ آزمون و ثبت ADR.

تا پیش از این آزمون، migration یا تغییر گستردهٔ کد انجام نمی‌شود.

- ترتیب اجرایی انتشار می‌تواند مرحله‌ای باشد: ابتدا Windows، سپس macOS و Linux پس از آزمون و آماده‌سازی بسته‌های هر پلتفرم.
- توسعهٔ فعلی روی Windows انجام می‌شود؛ سیستم توسعهٔ فعلی، محدودهٔ پلتفرم‌های مقصد را محدود نمی‌کند.

### اصول چندسکویی
1. Domain و Application نباید به APIهای اختصاصی Windows یا WebView وابسته شوند.
2. دسترسی به فایل، اعلان سیستم، پنجره، ذخیره‌سازی و قابلیت‌های سیستم‌عامل از طریق adapterهای Infrastructure انجام شود.
3. مسیرها، نام فایل‌ها، مجوزها، منطقهٔ زمانی و رفتار اعلان‌ها باید در هر سیستم‌عامل جداگانه آزمون شوند.
4. دادهٔ کاربر باید قابل پشتیبان‌گیری و انتقال بین نسخه‌های پشتیبانی‌شده باشد؛ تفاوت سیستم‌عامل نباید قالب داده را بی‌دلیل تغییر دهد.
5. معماری چندسکویی به معنی تضمین پشتیبانی از تمام نسخه‌های تاریخی سیستم‌عامل‌ها نیست؛ حداقل نسخه‌ها و معماری پردازنده برای هر انتشار باید در ماتریس سازگاری اعلام و آزمون شوند.

### گزینه‌های Desktop Shell

- **Electron:** گزینهٔ جایگزین برای مقایسه؛ مدل توسعهٔ JavaScript/Node.js برای تیم فعلی آشناتر است، اما بستهٔ نهایی معمولاً بزرگ‌تر است چون Chromium و Node.js را همراه می‌آورد.

### پایگاه دادهٔ محلی

### ۱۷.۱۰ قرارداد تکمیلی ثبت زمان — تصمیم‌های تصویب‌شده در 2026-11-13

**وضعیت: تصویب‌شده برای طراحی مدل دامنه؛ هنوز پیاده‌سازی نشده است.**

#### A. ذخیره‌سازی زمان و منطقهٔ زمانی
- زمان شروع و پایان هر بازهٔ دقیق به‌صورت instant استاندارد UTC و رشتهٔ ISO 8601 با پسوند `Z` ذخیره می‌شود.
- شناسهٔ منطقهٔ زمانی IANA در لحظهٔ ایجاد TimeEntry (مانند `Europe/Berlin`) به‌عنوان metadata ثبت می‌شود تا گزارش و audit به تغییر timezone فعلی دستگاه وابسته نباشد.
- ثبت دستیِ صرفاً مبتنی بر تاریخ، date-only باقی می‌ماند و به timestamp نیمه‌شب تبدیل نمی‌شود.

#### B. ساعت و محاسبهٔ مدت
- timestampهای UTC منبع حقیقت پایدار برای بازیابی و محاسبهٔ بازه هستند.
- `performance.now()` فقط برای نمایش روان شمارنده و اندازه‌گیری گذر زمان در همان اجرای زنده استفاده می‌شود؛ مقدار آن ذخیره نمی‌شود.
- پس از reload/restart یا بازگشت از sleep، زمان از timestampهای پایدار دوباره محاسبه می‌شود.
- اگر پایان قبل از شروع باشد یا تغییر ساعت سیستم مدت نامعتبر/غیرعادی بسازد، بازه خودکار نهایی نمی‌شود و به فرایند recovery/تصحیح می‌رود.

#### C. مالکیت تایمر بین تب‌ها و پنجره‌ها
- در محیطی که Web Locks API در دسترس است، یک lock انحصاری نام‌گذاری‌شده برای تایمر سراسری گرفته و تا pause/finish یا خروج context نگه داشته می‌شود.
- اگر Web Locks یا تضمین مالکیت انحصاری در محیط مقصد موجود نباشد، شروع تایمر جدید fail-closed می‌شود؛ localStorage و BroadcastChannel به‌تنهایی جایگزین قفل اتمیک نیستند.
- Web Locks فقط هماهنگی contextها را فراهم می‌کند و جایگزین storage تراکنشی، persistence و recovery نیست.
- پشتیبانی واقعی در WebView دسکتاپ باید پیش از فعال‌سازی تایمر چندپنجره‌ای آزمون شود.

#### D. سیاست هم‌پوشانی
- هیچ دو بازهٔ زمانی دقیق و تأییدشده‌ای در سطح کل برنامه نباید هم‌پوشانی داشته باشند؛ حتی اگر به Taskهای متفاوت تعلق داشته باشند.
- بازهٔ دقیقِ در حال recovery تا تعیین تکلیف، مانع شروع بازهٔ دقیق دیگری می‌شود؛ از دوباره‌شماری جلوگیری می‌کند.
- ثبت دستیِ مدت بدون ساعت دقیق در bucket جداگانهٔ `manual_duration` نگهداری و در گزارش جدا نمایش داده می‌شود؛ با مجموع بازه‌های دقیق جمع نمی‌شود، مگر اینکه کاربر صریحاً آن را به بازهٔ زمانی مشخص تبدیل/جایگزین کند.
- ثبت دستی با start/end دقیق مشمول همان قانون عدم هم‌پوشانی است.

#### E. Recovery و هشدار بازهٔ طولانی
- بسته‌شدن تب یا برنامه، بازهٔ باز را به‌طور خودکار به زمان فعلی نمی‌بندد؛ بازه برای recovery باز می‌ماند و تأیید پایان/تصحیح با کاربر است.
- تا قبل از تأیید، مدت بازه در مجموع زمان واقعی منظور نمی‌شود و بازهٔ unresolved مانع شروع تایمر دقیق دیگری است.
- اگر مدت پیشنهادی بازیابی‌شده از ۱۲ ساعت بیشتر باشد، هشدار ویژه نشان داده می‌شود؛ ۱۲ ساعت فقط آستانهٔ هشدار UX است، نه مجوز تأیید خودکار.
- اگر قفل در context زنده از دست برود، آن context حق ادامهٔ نوشتن/تغییر تایمر را ندارد؛ وضعیت پایدار برای recovery بررسی می‌شود و نباید یک پایان ساختگی ثبت کند.

#### F. مرز پیاده‌سازی و persistence
- مرحلهٔ نخست فقط مدل دامنهٔ خالص و تست‌های آن را پیاده‌سازی می‌کند؛ UI تایمر، lock adapter و persistence واقعی در مراحل بعدی‌اند.
- تا زمان داشتن storage adapter با عملیات اتمیک/تراکنشی، تایمر چندتب/چندپنجره‌ای روی LocalStorage فعلی فعال نمی‌شود.
- انتخاب فناوری persistence (مانند IndexedDB یا SQLite) تصمیم معماری جداگانه و هنوز باز است.

#### G. ترتیب اجرای بعدی
1. تعریف قرارداد داده و validation برای WorkSession و TimeEntry.
2. تعریف use-caseهای خالص و transitionهای مجاز lifecycle.
3. نوشتن تست‌های دامنه برای ورودی نامعتبر، transitionها، duration، overlap، recovery و manual-duration.
4. سپس طراحی persistence و coordination adapter در سند/مرحلهٔ مستقل.


### ۱۷.۱۱ قرارداد دادهٔ WorkSession و TimeEntry — نسخهٔ نخست مدل دامنه

**وضعیت:** قرارداد مدل دامنه برای مرحلهٔ نخست تصویب و تثبیت شد؛ persistence و UI همچنان خارج از این مرحله‌اند.

#### WorkSession

هر WorkSession متعلق به دقیقاً یک Task است و وضعیت یک نوبت کاری را نگه می‌دارد؛ مدت واقعی از TimeEntryها به دست می‌آید و در WorkSession کپی نمی‌شود.

| فیلد | نوع | قاعده |
|---|---|---|
| `id` | string | شناسهٔ یکتا و غیرخالی |
| `taskId` | string | شناسهٔ Task مالک؛ غیرخالی |
| `status` | enum | `planned`, `in_progress`, `completed`, `cancelled` |
| `plannedDurationSeconds` | integer/null | مدت برنامه‌ریزی‌شده؛ در صورت وجود عدد صحیح مثبت |
| `startedAt` | UTC ISO timestamp/null | زمان اولین ورود به وضعیت در حال انجام؛ با pause/resume تغییر نمی‌کند |
| `completedAt` | UTC ISO timestamp/null | فقط در وضعیت completed مقدار دارد |
| `cancelledAt` | UTC ISO timestamp/null | فقط در وضعیت cancelled مقدار دارد |
| `createdAt`, `updatedAt` | UTC ISO timestamp | زمان ایجاد و آخرین تغییر |
| `version` | integer | عدد صحیح مثبت برای نسخهٔ موجودیت |

قواعد وضعیت:
- `planned`: هر سه فیلد `startedAt`, `completedAt`, `cancelledAt` برابر null هستند.
- `in_progress`: `startedAt` مقدار دارد و دو فیلد پایان null هستند.
- `completed`: `startedAt` و `completedAt` مقدار دارند، `cancelledAt` برابر null است و پایان قبل از شروع نیست.
- `cancelled`: `cancelledAt` مقدار دارد و `completedAt` برابر null است؛ نشست می‌تواند پیش از شروع یا پس از شروع لغو شود.
- pause وضعیت مستقل نیست؛ نشست در حالت `in_progress` می‌ماند و صرفاً TimeEntry باز وجود ندارد.

#### TimeEntry

| فیلد | نوع | قاعده |
|---|---|---|
| `id` | string | شناسهٔ یکتا و غیرخالی |
| `workSessionId` | string | ارجاع غیرخالی به WorkSession مالک |
| `kind` | enum | `timer_interval`, `manual_interval`, `manual_duration` |
| `startedAt`, `endedAt` | UTC ISO timestamp/null | برای بازهٔ دقیق؛ پایان می‌تواند فقط برای تایمر باز null باشد |
| `durationSeconds` | integer/null | فقط برای `manual_duration`؛ عدد صحیح مثبت |
| `occurredOn` | ISO date/null | تاریخ اختیاری ثبت مدت دستی؛ هرگز به نیمه‌شب تبدیل نمی‌شود |
| `timeZoneId` | IANA timezone | شناسهٔ معتبر منطقهٔ زمانی در لحظهٔ ثبت |
| `status` | enum | `open`, `confirmed`, `rejected` |
| `source` | enum | `timer` یا `manual` و باید با kind سازگار باشد |
| `note` | string/null | توضیح اختیاری |
| `createdAt`, `updatedAt` | UTC ISO timestamp | زمان ایجاد و آخرین تغییر |

قواعد نوع و وضعیت:
- `timer_interval`: شروع دقیق دارد؛ در وضعیت `open` پایان null است؛ در وضعیت `confirmed` پایان دقیق و بعد از شروع دارد. رد کردن بازهٔ بازیابی‌نشده مجاز است و آن را وارد محاسبه نمی‌کند.
- `manual_interval`: شروع و پایان دقیق و معتبر دارد و هنگام ثبت دستی با وضعیت `confirmed` ایجاد می‌شود.
- `manual_duration`: زمان شروع/پایان ندارد، مدت مثبت دارد و در صورت مشخص بودن، `occurredOn` یک تاریخ معتبر ISO است؛ منبع آن `manual` است.
- `source=timer` فقط برای `timer_interval` و `source=manual` برای دو نوع دستی معتبر است.
- مدت بازهٔ دقیق فقط از تفاضل timestampهای UTC محاسبه می‌شود؛ `manual_duration` در bucket جداگانه باقی می‌ماند.
- فقط TimeEntry تأییدشده در زمان واقعی دقیق منظور می‌شود؛ `open` و `rejected` شمرده نمی‌شوند.
- هر TimeEntry دقیق باید IANA timezone معتبر داشته باشد. timestampها رشتهٔ canonical UTC با پسوند `Z` هستند.
- ارجاع به Task/WorkSession و یکتایی IDها در سطح مجموعه و use case بررسی می‌شود، نه در اعتبارسنجی منفرد یک شیء.

#### مرز این مرحله

در این مرحله فقط factory/validation و توابع خالص دامنه همراه تست ساخته می‌شوند. transitionهای lifecycle، عملیات اصلاح تاریخچه، هماهنگی تایمر، Web Locks، persistence، migration و UI مراحل مستقل بعدی‌اند. این قرارداد به‌تنهایی به معنی فعال‌شدن تایمر یا تغییر schema ذخیره‌شده نیست.

## ۲۰. اصل معماری تکامل‌پذیر و بازبودن مسیر ایده‌های آینده

**وضعیت:** اصل راهبردی مورد تأیید کاربر؛ جزئیات مرزبندی و پیاده‌سازی باید با ممیزی و نیاز واقعی تعیین شوند.

### ۲۰.۱ چشم‌انداز فعلی، نه سقف نهایی محصول
- مشخصات فعلی محصول، توصیف بهترین چشم‌انداز شناخته‌شده در زمان حاضر است؛ فهرست بسته و تغییرناپذیر قابلیت‌ها یا تعریف نهایی و ابدی محصول نیست.
- ممکن است در آینده ایده‌ها، نیازها، شیوه‌های تعامل یا قابلیت‌های تازه‌ای مطرح شوند که اکنون قابل پیش‌بینی نیستند.
- معماری باید امکان ارزیابی و افزودن این ایده‌ها را بدون بازنویسی غیرضروری هسته و بدون شکستن داده‌ها و قابلیت‌های موجود فراهم کند.
- ایدهٔ جدید ابتدا ثبت و از نظر ارزش، سازگاری، هزینه و اثر بر مدل داده و مرزها بررسی می‌شود؛ این اصل به معنی تعهد به ساخت هر ایده یا پیش‌بینی همهٔ آن‌ها از امروز نیست.

### ۲۰.۲ انعطاف بدون مهندسی بیش‌ازحد
- هدف، معماری قابل تکامل است، نه معماری‌ای که از روز اول برای هر سناریوی فرضی abstraction، plugin system، event bus یا framework عمومی بسازد.
- ساده‌ترین طراحی‌ای انتخاب شود که نیاز واقعی فعلی را درست پوشش دهد، اما در نقاطی که تغییر محتمل و پرهزینه است، مرز روشن و قابل تعویض داشته باشد.
- انتزاع زمانی ایجاد شود که تفاوت واقعی پیاده‌سازی، نیاز به تعویض، مالکیت مستقل داده یا تغییر مستقل مسئولیت آن را توجیه کند.
- کمی تکرار محدود و روشن، در صورت بهتر بودن از abstraction اشتباه و coupling پنهان، مجاز است.
- تصمیم‌های پرهزینه و دشوار برای بازگشت باید با شواهد، آزمایش و ثبت ADR اتخاذ شوند؛ تصمیم‌های قابل بازگشت تا حد ممکن مرحله‌ای گرفته شوند.

### ۲۰.۳ ماژولار بودن به‌عنوان ابزار، نه هدف مستقل
- مستقل‌سازی بر اساس انسجام مسئولیت، مالکیت داده، قواعد دامنه، دلایل تغییر و نیاز به آزمون یا جایگزینی انجام می‌شود؛ نه صرفاً بر اساس تعداد قابلیت‌ها یا فایل‌ها.
- بخش‌هایی که با هم تغییر می‌کنند و یک مسئولیت منسجم دارند می‌توانند در یک ماژول باقی بمانند.
- ماژول‌ها باید رابط عمومی کوچک و روشن داشته باشند؛ دسترسی به جزئیات خصوصی یا تغییر مستقیم دادهٔ تحت مالکیت ماژول دیگر ممنوع است، مگر از مسیر قرارداد مشخص.
- جهت وابستگی‌ها باید روشن و بدون چرخه باشد. لایه‌ها و ماژول‌های دامنه نباید به UI، پایگاه داده یا provider خاص AI وابسته شوند.
- جهت فعلی، یک برنامهٔ واحد با مرزهای داخلی سالم (modular monolith) است؛ microservices یا جداسازی فرایندها فقط با دلیل عملیاتی و شواهد آینده بررسی می‌شوند.

### ۲۰.۴ آزمون هر ایدهٔ جدید
پیش از افزودن ایدهٔ جدید، این پرسش‌ها بررسی شوند:
1. چه مسئله یا ارزشی را حل می‌کند و آیا با اصول محصول سازگار است؟
2. داده و قواعد آن متعلق به کدام بخش‌اند؟ آیا واقعاً مسئولیت مستقلی دارد؟
3. کدام قراردادها و ماژول‌های موجود را تحت تأثیر قرار می‌دهد؟
4. آیا می‌توان آن را بدون شکستن قابلیت‌های قبلی اضافه، آزمایش و در صورت نیاز بازگردانی کرد؟
5. چه نیاز تازه‌ای به امنیت، حریم خصوصی، ذخیره‌سازی، عملکرد، آفلاین یا سیستم‌عامل ایجاد می‌کند؟
6. آیا مرز یا abstraction پیشنهادی نیاز واقعی دارد یا صرفاً برای احتمال نامشخص آینده ساخته می‌شود؟

### ۲۰.۵ اثر بر ممیزی فعلی
ممیزی زیرساخت باید علاوه بر آمادگی برای قابلیت‌های شناخته‌شده، هزینه و ریسک تغییرات آینده را هم ارزیابی کند: coupling، cohesion، وابستگی‌های چرخه‌ای، مالکیت داده، قراردادهای عمومی، نقاط اتصال به providerها و adapterها، نسخه‌بندی schema و امکان migration. خروجی ممیزی باید کمبودهای لازم برای امروز را از ظرفیت‌های توسعه‌پذیری مفید و زیرساخت‌های فرضی/زودهنگام جدا کند.

## ۲۱. پیشنهاد قابلیت خودبهبوددهی کنترل‌شده (Self-Improvement)

**وضعیت:** پیشنهاد مفهومی در حال بررسی؛ هنوز تصمیم نهایی محصول، معماری اجرایی یا مجوز خودمختاری نیست و هیچ بخشی پیاده‌سازی نشده است.

### ۲۱.۱ هدف
در آینده بررسی شود که Vira Planner بتواند فراتر از پاسخ‌گویی به درخواست مستقیم، به‌صورت دوره‌ای عملکرد خودش و تجربهٔ استفاده را ارزیابی کند، فرصت‌های بهبود را بیابد، پیشنهاد بسازد و برخی آزمایش‌های محدود را انجام دهد. منظور از «پیشرفت» لزوماً آموزش یا تغییر خودکار وزن‌های مدل هوش مصنوعی نیست؛ می‌تواند شامل بهبود workflow، پیشنهاد قابلیت، اصلاح مستندات، تست، تنظیمات یا آماده‌سازی تغییر نرم‌افزار باشد.

### ۲۱.۲ چرخهٔ پیشنهادی
1. مشاهدهٔ داده‌ها و بازخوردهایی که کاربر اجازه داده است؛ جمع‌آوری حداقلی و privacy-first.
2. تشخیص مسئله یا فرصت بهبود و ثبت شواهد و میزان اطمینان.
3. تولید پیشنهاد همراه با دلیل، اثر، هزینه و ریسک.
4. اولویت‌بندی بر اساس ارزش، امنیت، هزینه و سازگاری با اصول محصول.
5. آزمایش در محیط جدا و غیرتولیدی با دادهٔ آزمایشی؛ اجرای تست‌ها و ارزیابی مستقل.
6. ارائهٔ گزارش و تغییرات قابل بازبینی؛ انتشار فقط از مسیر کنترل‌شده.
7. پایش نتیجه و امکان rollback؛ اگر شواهد کافی نیست، پیشنهاد رد یا متوقف شود.

### ۲۱.۳ سطوح اختیار پیشنهادی
- **مجاز به‌صورت خودکار پس از طراحی و آزمون:** تحلیل محلیِ مجاز، کشف الگو، تهیهٔ گزارش و پیشنهاد، ساخت پیش‌نویس، اجرای تست در sandbox محدود.
- **نیازمند تأیید کاربر:** تغییر کد اصلی، تغییر schema یا migration، نصب dependency، ارسال داده به سرویس بیرونی، فعال‌کردن قابلیت جدید و انتشار نسخه.
- **ممنوع بدون مجوز مستقل و صریح:** تغییر سطح دسترسی یا سیاست امنیتی خودش، دسترسی به کلیدها/اسرار، حذف داده یا audit log، اجرای کد دلخواه روی سیستم واقعی، دور زدن محدودیت هزینه/شبکه یا انتشار مستقیم تغییر پرریسک.
- کاربر باید بتواند چرخه را متوقف کند، دسترسی‌ها را پس بگیرد و گزارش فعالیت و rollback را ببیند.

### ۲۱.۴ شروط ایمنی و اعتبار
- اختیارها باید در لایهٔ policy/tool enforcement محدود شوند؛ صرفاً به قول یا prompt مدل تکیه نشود.
- کد تولیدشده و محتوای بیرونی غیرقابل اعتماد فرض شوند و فقط در sandbox با حداقل دسترسی آزمایش شوند.
- معیار ارزیابی مستقل از عامل تغییر‌دهنده باشد؛ عامل نباید بتواند تست یا معیار موفقیت خودش را برای سبز نشان‌دادن تغییر دست‌کاری کند.
- محدودیت زمان، تعداد تکرار، مصرف توکن/هزینه، شبکه و ابزارها اعمال شود.
- تغییرات ثبت‌شده، قابل مقایسه و تا حد ممکن قابل بازگشت باشند.
- خودبهبوددهی نباید دادهٔ خصوصی را بدون رضایت از دستگاه خارج کند یا از رفتار کاربر نتیجه‌گیری نامطمئن را به‌عنوان واقعیت ثبت کند.

### ۲۱.۵ مرز فعلی
این قابلیت در نقشهٔ راه نزدیک قرار نمی‌گیرد و نباید پایه‌های فعلی را منحرف کند. فعلاً فقط باید معماری عمومی را از قفل‌شدن بی‌دلیل به یک provider یا workflow خاص حفظ کنیم. طراحی اجرایی زمانی آغاز می‌شود که هستهٔ محصول، ذخیره‌سازی امن، مجوزها، audit trail، تست‌ها و محیط آزمایشی قابل اتکا باشند.

## اصل مصوب مالکیت Task و ارتباط آن با Project

**وضعیت: تصویب‌شده در 2026-11-14**

### تصمیم
یک Task موجودیت مستقلی است و برای معتبر بودن یا ادامهٔ حیات خود به Project وابسته نیست. هر Task می‌تواند بدون اتصال به هیچ Project ایجاد، برنامه‌ریزی، اجرا، تکمیل، لغو یا آرشیو شود. در صورت نیاز، می‌تواند به یک Project متصل شود.

### مالکیت و مسئولیت
- ماژول Tasks مالک Task و قواعد چرخهٔ عمر آن است.
- ماژول Projects مالک Project و قواعد چرخهٔ عمر آن است.
- اتصال Task به Project یک رابطه/ارجاع است؛ Project مالک Task نمی‌شود.
- Planning، Calendar، Time Tracking، Analytics و AI می‌توانند به Task یا Project ارجاع دهند، اما این ارجاع به معنی مالکیت آن موجودیت‌ها نیست.
- تغییر یا حذف Project نباید به‌صورت ضمنی به معنی حذف Taskهای مرتبط تلقی شود؛ سیاست دقیق هنگام حذف Project باید جداگانه مشخص شود.

### پیامدهای طراحی
- ارتباط Task با Project باید اختیاری باشد؛ برای نمونه، در مدل مفهومی می‌توان از یک ارجاع اختیاری مانند `projectId` استفاده کرد. این نام صرفاً بیان مفهومی است و به معنی تصویب تغییر کد یا schema فعلی نیست.
- رابط کاربری آینده باید امکان مشاهدهٔ Taskهای مستقل و Taskهای مرتبط با Project را فراهم کند.
- Use caseهای Tasks باید بدون نیاز به بارگذاری یا ایجاد Project کار کنند.
- قواعد اعتبارسنجی Tasks نباید به وجود یک Project وابستگی اجباری داشته باشند.
- اتصال، جداسازی یا تغییر Project مرتبط باید از مسیر Application API و با اعتبارسنجی مرجع انجام شود.

### تصمیم تکمیلی مصوب: تعداد Projectهای مرتبط با هر Task

**وضعیت: تصویب‌شده در 2026-11-14**

- هر Task در هر لحظه می‌تواند به حداکثر یک Project متصل باشد.
- اتصال به Project همچنان اختیاری است؛ Task مستقل و بدون Project معتبر باقی می‌ماند.
- Task می‌تواند از Project فعلی جدا و در صورت نیاز به Project دیگری منتقل شود.
- اتصال هم‌زمان یک Task به چند Project در مدل نسخهٔ اول پشتیبانی نمی‌شود.
- این تصمیم دربارهٔ cardinality رابطه است و به‌تنهایی دربارهٔ تاریخچهٔ انتقال یا رفتار حذف/آرشیو Project تصمیمی نمی‌گیرد.

### تصمیم تکمیلی مصوب: چرخهٔ عمر Project

**وضعیت: تصویب‌شده در 2026-11-14**

چرخهٔ عمر Project سه عملیات متمایز دارد:

1. **Archive (بایگانی):** پروژه از فهرست پروژه‌های فعال خارج می‌شود، اما داده‌ها و ارتباط Taskهای آن حفظ می‌شوند. پروژه در صورت نیاز قابل بازگردانی است.
2. **Delete (انتقال به سطل زباله):** پروژه به وضعیت حذف‌شدهٔ قابل‌بازیابی منتقل می‌شود. ارتباط Taskها با پروژه در این وضعیت حفظ می‌شود تا بازیابی پروژه، رابطه‌های قبلی را نیز بازگرداند.
3. **Permanent Delete (حذف دائمی):** خود Project و داده‌های متعلق به آن برای همیشه حذف می‌شوند. Taskهای مرتبط حذف نمی‌شوند؛ فقط ارجاع آن‌ها به Project حذف‌شده قطع می‌شود و Taskها مستقل باقی می‌مانند.

### الزامات و ملاحظات طراحی
- Archive، Delete و Permanent Delete باید عملیات و وضعیت‌های متمایز باشند؛ نباید به‌صورت یک حذف مبهم پیاده‌سازی شوند.
- Restore پروژه از سطل زباله باید ارتباط‌های Task–Project حفظ‌شده را بازیابی کند.
- حذف دائمی Project نباید cascade delete روی Taskها ایجاد کند.
- اجرای حذف دائمی باید فقط پس از اقدام آگاهانه و صریح کاربر انجام شود؛ جزئیات تأیید و حفاظت در برابر حذف تصادفی در طراحی UX و امنیت تعیین می‌شود.
- سیاست نگهداری مدت‌دار اقلام سطل زباله، پاک‌سازی خودکار و نسخه‌های پشتیبان هنوز تعیین نشده است.

### تصمیم تکمیلی مصوب: تاریخچهٔ ارتباط Task و Project

**وضعیت: تصویب‌شده در 2026-11-14**

- ویرا باید رویدادهای مهم تغییر ارتباط Task و Project را ثبت کند؛ از جمله اتصال Task به Project، جداکردن آن و انتقال از یک Project به Project دیگر.
- هر رویداد باید حداقل زمان وقوع، Task مربوط، Project مبدأ (در صورت وجود)، Project مقصد (در صورت وجود) و عامل انجام‌دهنده را مشخص کند.
- عامل می‌تواند کاربر یا یک قابلیت/عامل هوش مصنوعی مجاز باشد؛ منشأ تغییر باید قابل تشخیص بماند.
- تاریخچه باید در آینده برای کاربر قابل مشاهده و قابل فهم باشد.
- این تصمیم به معنی ساخت سیستم کامل Version Control یا ثبت تمام تغییرات همهٔ فیلدهای Task نیست؛ دامنهٔ فعلی فقط رویدادهای مهم رابطهٔ Task–Project است.
- جزئیات فنی ذخیره‌سازی، سیاست نگهداری و طراحی رابط مشاهدهٔ تاریخچه در مراحل مربوط تعیین می‌شوند.

در این مرحله تاریخچهٔ کامل همهٔ تغییرات Task تصویب نشده است و نباید بدون تصمیم جداگانه به دامنه افزوده شود.

## تصمیم معماری: مدل Grouping مستقل برای Projectها — 2026-11-14

**وضعیت: تصمیم طراحی نسخهٔ اول؛ پیش‌فرض کم‌ریسک و قابل بازنگری در صورت نیاز واقعی**

### اصول و ساختار
- Projectها مستقل و هم‌سطح‌اند؛ Project والد/فرزند یا Sub-project در مدل پایه وجود ندارد.
- Group یک موجودیت مستقل با مالکیت در ماژول Projects است و فقط برای دسته‌بندی و سازمان‌دهی Projectها استفاده می‌شود؛ Group مالک Project یا Task نیست.
- هر Project در نسخهٔ اول حداکثر به یک Group اختیاری متصل می‌شود. Project بدون Group کاملاً معتبر است.
- Groupها در نسخهٔ اول تو‌در‌تو نیستند.
- Task به Group متصل نمی‌شود؛ اگر Task به Project متصل باشد، دسته‌بندی آن از مسیر Project قابل مشاهده است.
- Group صرفاً ساختار سازمان‌دهی است و نباید وارد قواعد زمان‌بندی، مالکیت Task یا چرخهٔ عمر مستقل Task شود.

### مدل دادهٔ مفهومی
- `ProjectGroup`: شناسهٔ پایدار، نام، ترتیب نمایش و زمان‌های ایجاد/ویرایش.
- `Project.groupId`: ارجاع اختیاری به یک `ProjectGroup`؛ نبود مقدار به معنی بدون گروه بودن Project است.
- نام و شناسهٔ Group مستقل از نام Project هستند؛ تغییر نام Group نباید نیازمند تغییر Projectهای عضو باشد.
- ترتیب Groupها با فیلد ترتیب مستقل مدیریت می‌شود؛ ترتیب Projectها درون Group یا فهرست کلی، سیاست Presentation/Application است و نباید با ترتیب Groupها یکی فرض شود.
- این قرارداد، مدل هدف است و تا زمان پیاده‌سازی و migration نباید به‌عنوان schema اجرایی موجود تلقی شود.

### عملیات و چرخهٔ عمر نسخهٔ اول
- عملیات پایه: ایجاد، تغییر نام، مرتب‌سازی و حذف Group.
- Archive/Trash/Restore مستقل برای Group در نسخهٔ اول ساخته نمی‌شود؛ در صورت نیاز واقعی بعدی قابل افزودن است.
- حذف Group فقط رابطهٔ دسته‌بندی را حذف می‌کند: Projectهای عضو باقی می‌مانند و بدون Group می‌شوند؛ Taskها نیز بدون تغییر باقی می‌مانند.
- حذف Group نباید Project یا Task را cascade-delete کند.
- Projectهای Archive یا Trash شده همچنان ارجاع گروهی خود را حفظ می‌کنند تا در صورت Restore، دسته‌بندی نیز حفظ شود؛ حذف دائمی Project فقط همان Project را از Group خارج می‌کند.
- حذف Group باید از طریق Application use case انجام شود تا detach شدن Projectهای عضو صریح، آزمون‌پذیر و سازگار باشد.

### محدودیت‌های آگاهانهٔ نسخهٔ اول
- یک Project هم‌زمان در چند Group قرار نمی‌گیرد.
- Groupهای تو‌در‌تو، Groupهای هوشمند/خودکار، رنگ و آیکون سفارشی، قوانین عضویت و آرشیو مستقل Group خارج از دامنهٔ نسخهٔ اول‌اند.
- این محدودیت‌ها برای ساده نگه‌داشتن مدل پایه‌اند؛ اگر شواهد استفادهٔ واقعی نیاز دیگری نشان داد، توسعه از مسیر migration و تصمیم معماری انجام می‌شود.

## قرارداد یکپارچهٔ دامنه: Task، Project و ProjectGroup — 2026-11-14

**وضعیت: قرارداد هدف نسخهٔ اول؛ مستند شده و هنوز به‌طور کامل در کد پیاده‌سازی نشده است.**  
این بخش، تصمیم‌های مالکیت، رابطه و چرخهٔ عمر ثبت‌شده در بخش‌های پیشین را در یک قرارداد واحد جمع می‌کند. اگر بین یادداشت‌های قدیمی‌تر و این بخش تفاوتی وجود داشت، این قرارداد یکپارچه مرجع طراحی نسخهٔ اول است.

### ۱. مالکیت موجودیت‌ها

| موجودیت | مالک دامنه | مسئولیت |
|---|---|---|
| Task | Tasks | کار قابل انجام، وضعیت، پیشرفت، اولویت، زمان‌ها و جزئیات اجرایی |
| Project | Projects | هدف/دامنهٔ کاری سطح بالاتر، مشخصات و چرخهٔ عمر پروژه |
| ProjectGroup | Projects | دسته‌بندی اختیاری Projectها برای سازمان‌دهی و نمایش |
| TaskProjectLinkHistory | Tasks / Application boundary | ثبت رویدادهای مهم اتصال، جداسازی و انتقال Task بین Projectها |

- هر موجودیت شناسهٔ پایدار و چرخهٔ عمر مستقل خود را دارد.
- Project ظرف مالکیتی Task نیست؛ Task دادهٔ مستقل خود را دارد و فقط با شناسه به Project ارجاع می‌دهد.
- ProjectGroup نیز مالک Project نیست؛ رابطهٔ آن صرفاً دسته‌بندی است.
- هیچ ماژولی نباید با دست‌کاری مستقیم دادهٔ داخلی ماژول دیگر، قواعد دامنه را دور بزند. تغییر روابط از Application use case عبور می‌کند.

### ۲. مدل مفهومی و روابط

**Task**
- مالک عنوان، توضیح، وضعیت، پیشرفت، اولویت، تاریخ برنامه‌ریزی، deadline، مدت تخمینی، وابستگی‌ها و سایر ویژگی‌های خود است.
- `projectId` اختیاری است؛ نبود آن یعنی Task مستقل است.
- هر Task در هر لحظه حداکثر به یک Project متصل می‌شود.
- Task به ProjectGroup ارجاع مستقیم ندارد.

**Project**
- دارای شناسه، مشخصات و وضعیت چرخهٔ عمر مستقل است.
- `groupId` اختیاری است؛ نبود آن یعنی Project در فهرست بدون گروه نمایش داده می‌شود.
- هر Project حداکثر به یک ProjectGroup تعلق دارد.
- Projectها در نسخهٔ اول هم‌سطح‌اند؛ parentId و ساختار Sub-project وجود ندارد.

**ProjectGroup**
- دارای شناسهٔ پایدار، نام، ترتیب نمایش و زمان‌های ایجاد/ویرایش است.
- در نسخهٔ اول parentId ندارد و تو‌در‌تو نیست.
- حذف یا تغییر نام آن نباید محتوای Project یا Task را تغییر دهد.

رابطهٔ مفهومی:

`Task (0..1) → Project (0..1) → ProjectGroup`

این نمایش به معنی زنجیرهٔ مالکیت نیست؛ فقط دو ارجاع اختیاری و مستقل را نشان می‌دهد. Task بدون Project و Project بدون Group هر دو حالت معتبرند.

### ۳. قواعد سازگاری رابطه‌ها

1. مقدار غیرتهی `Task.projectId` باید به Project موجود و قابل ارجاع اشاره کند.
2. مقدار غیرتهی `Project.groupId` باید به ProjectGroup موجود اشاره کند.
3. تغییر Project یک Task باید به‌صورت یک عملیات Application انجام شود: بررسی Task و Project مقصد، تغییر ارجاع و ثبت رویداد تاریخچه در یک مرز عملیاتی سازگار.
4. Attach، Detach و Move برای Task رویدادهای تاریخچه‌اند؛ Move شامل Project مبدأ و مقصد است.
5. actor تاریخچه باید نوع عامل را مشخص کند: کاربر یا قابلیت/عامل AI مجاز. AI فقط از Application API و مجوزهای تعریف‌شده اقدام می‌کند.
6. حذف Group، ابتدا عضویت Projectهایش را خالی می‌کند و سپس Group را حذف می‌کند؛ Projectها و Taskها باقی می‌مانند.
7. حذف دائمی Project، ارجاع Taskهای مرتبط را خالی می‌کند؛ خود Taskها باقی می‌مانند. عضویت Group نیز همراه Project از بین می‌رود.
8. Archive یا انتقال Project به Trash رابطه‌های Task–Project و Project–Group را حفظ می‌کند تا Restore همان روابط را برگرداند.
9. دادهٔ تاریخی نباید به‌عنوان رابطهٔ زنده تفسیر شود؛ تاریخچه توضیح می‌دهد چه اتفاقی افتاده، نه اینکه وضعیت فعلی را تعیین کند.

### ۴. چرخهٔ عمر Project

وضعیت‌های مفهومی نسخهٔ اول:
- `active`: در فهرست فعال و قابل استفادهٔ عادی.
- `archived`: از فهرست فعال خارج شده، اما قابل Restore است.
- `trashed`: حذف نرم و قابل بازیابی.

Permanent Delete یک وضعیت ماندگار نیست؛ فرمانی برگشت‌ناپذیر است که رکورد Project را حذف و ارجاع‌های زنده را پاک می‌کند.

قواعد عملیاتی:
- Archive و Trash رابطه‌های موجود را حفظ می‌کنند.
- Restore از Archive یا Trash وضعیت را به حالت فعال برمی‌گرداند و روابط حفظ‌شده را نگه می‌دارد.
- پیش‌فرض نسخهٔ اول: ایجاد رابطهٔ جدید یا انتقال Task به Project غیر فعال (archived/trashed) مجاز نیست؛ کاربر ابتدا باید Project را Restore کند. Detach کردن Task از چنین Projectی مجاز است.
- Permanent Delete فقط با اقدام صریح و آگاهانهٔ کاربر انجام می‌شود.
- مدت نگهداری Trash و پاک‌سازی خودکار هنوز تعیین نشده و در نسخهٔ اول نباید بدون سیاست روشن به‌صورت خودکار اجرا شود.

### ۵. چرخهٔ عمر ProjectGroup

- عملیات نسخهٔ اول: Create، Rename، Reorder و Delete.
- Group وضعیت Archive/Trash مستقل ندارد.
- Delete فقط دسته‌بندی را حذف می‌کند؛ Projectهای عضو بدون Group می‌شوند.
- Groupهای تو‌در‌تو و عضویت چندگانهٔ Project خارج از دامنهٔ نسخهٔ اول‌اند.

### ۶. قرارداد تاریخچهٔ Task–Project

هر رویداد حداقل شامل این داده‌های مفهومی است:
- شناسهٔ رویداد و زمان وقوع
- شناسهٔ Task
- نوع رویداد: `attached`، `detached` یا `moved`
- شناسهٔ Project مبدأ و مقصد، در صورت وجود
- actor type و شناسهٔ عامل در صورت وجود

تاریخچه، ثبت سبک رویدادهای رابطه است و Version Control همهٔ فیلدهای Task نیست. عنوان یا محتوای کامل Project در رویداد کپی نمی‌شود. رفتار نمایش رویدادهایی که Project آن‌ها بعداً Permanent Delete شده، و سیاست نگهداری تاریخچه باید در طراحی persistence مشخص شود؛ ارجاع تاریخی نباید دوباره به‌عنوان رابطهٔ زنده احیا شود.

### ۷. مرز Application API

عملیات دامنه از طریق use caseهای روشن انجام می‌شوند؛ نام‌های زیر قرارداد مفهومی‌اند و الزاماً نام فایل یا تابع نهایی نیستند:

**Tasks**
- CreateTask / UpdateTask / DeleteTask (طبق چرخهٔ عمر مستقل Task)
- AttachTaskToProject / DetachTaskFromProject / MoveTaskToProject

**Projects**
- CreateProject / UpdateProject
- ArchiveProject / RestoreProject
- TrashProject / RestoreProjectFromTrash
- PermanentlyDeleteProject
- AssignProjectToGroup / RemoveProjectFromGroup

**Project Groups**
- CreateProjectGroup / RenameProjectGroup / ReorderProjectGroups / DeleteProjectGroup

Use caseهای مرتبط با چند موجودیت باید تمام اعتبارسنجی‌ها را پیش از commit انجام دهند و در صورت شکست، وضعیت نیمه‌کاره یا رابطهٔ یتیم باقی نگذارند. جزئیات تراکنش و persistence وابسته به انتخاب پایگاه داده و در مرحلهٔ زیرساخت طراحی می‌شود.

### ۸. خارج از دامنهٔ نسخهٔ اول

- Task در چند Project یا Project در چند Group
- Projectهای تو‌در‌تو و Groupهای تو‌در‌تو
- Groupهای هوشمند، قوانین عضویت خودکار و فیلترهای ذخیره‌شده
- آرشیو/سطل زبالهٔ مستقل برای Group
- Version Control کامل برای همهٔ فیلدهای Task و Project
- همکاری چندکاربره، مالکیت چندحسابی و همگام‌سازی چنددستگاهی

### ۹. معیارهای پذیرش طراحی

- Task بدون Project قابل ایجاد، ویرایش و مدیریت است.
- Project بدون Group قابل ایجاد و مدیریت است.
- هیچ Task بیش از یک Project و هیچ Project بیش از یک Group فعال ندارد.
- Archive/Trash کردن Project، Taskها و ارتباط‌های آن‌ها را حفظ می‌کند.
- Restore، ارتباط‌های پیشین را حفظ می‌کند.
- Permanent Delete کردن Project، Taskها را حذف نمی‌کند و ارجاع زندهٔ آن‌ها را پاک می‌کند.
- Delete کردن Group، Projectها و Taskها را حذف نمی‌کند.
- همهٔ تغییرات رابطهٔ Task–Project از Application API عبور می‌کنند و تاریخچهٔ لازم را ثبت می‌کنند.
- مدل Domain به UI، مرورگر، LocalStorage یا provider خارجی وابسته نیست.

**یادداشت اجرایی:** این قرارداد هنوز مجوز تغییر کد نیست. گام بعدی، تطبیق آن با ساختار فعلی فایل‌های Domain و تست‌ها، سپس طراحی/پیاده‌سازی در یک تغییر کد محدود و با تأیید جداگانه است.

## پیاده‌سازی Application رابطهٔ Task و Project — 2026-11-14

**وضعیت: use caseهای پایه پیاده‌سازی شده‌اند؛ persistence تاریخچه و هماهنگی چندموجودیتی هنوز انجام نشده است.**

فایل `src/application/projects/task-project-relationships.js` مرز Application برای سه عملیات رابطه را فراهم می‌کند:

- `attachTaskToProject(task, project, options)`: اتصال Task مستقل به Project فعال.
- `detachTaskFromProject(task, options)`: جداسازی Task؛ حتی اگر Project فعلی archived یا trashed باشد.
- `moveTaskToProject(task, destinationProject, options)`: انتقال Task متصل به Project فعال دیگری.

هر عملیات تغییردهنده، Task جدید و یک رویداد تاریخچه با شناسه، زمان، Task ID، نوع رویداد، Project مبدأ/مقصد و actor برمی‌گرداند. actor در این مرحله یکی از `user` یا `ai` است. این برچسب به‌تنهایی مجوز دسترسی ایجاد نمی‌کند؛ احراز مجوز و سیاست اجرای AI در لایه‌های بالاتر باقی می‌ماند.

رفتارهای بدون تغییر، مانند detach کردن Task مستقل یا انتقال به همان Project، idempotent هستند و رویداد تکراری تولید نمی‌کنند. اتصال و انتقال به Project غیر فعال رد می‌شود. مدل Task و Project ورودی mutate نمی‌شوند.

**محدودیت آگاهانه:** این use caseها روی رکوردهای ورودی کار می‌کنند و خودشان repository، persistence یا تراکنش چندموجودیتی ندارند. فراخواننده باید نتیجهٔ Task و event را در مرحلهٔ Persistence به‌صورت سازگار ذخیره کند. وجود Project در مخزن و یکتایی Taskها در repository نیز تا زمان یکپارچه‌سازی persistence مسئولیت caller است.

## ۲۰. پلتفرم‌های نسخهٔ اول و معماری چندسکویی — تصمیم محصولی 2026-11-14

**وضعیت: محدودهٔ محصول تأیید شده؛ جزئیات فناوری و پیاده‌سازی هنوز نیازمند ارزیابی و آزمون‌اند.**

### ۲۰.۱ محدودهٔ پلتفرم
- نسخهٔ اول برای دو پلتفرم ساخته می‌شود: اپلیکیشن دسکتاپ Windows و اپلیکیشن Android.
- macOS و iOS خارج از محدودهٔ فعلی توسعه‌اند. معماری باید تا حد معقول امکان افزودن آن‌ها در آینده را حفظ کند، اما این امکان مجوز افزودن پیچیدگی یا هزینه به نسخهٔ اول نیست.
- محصول باید روی هر دو پلتفرم تجربهٔ نصب و اجرای مستقل داشته باشد؛ ابزارهای توسعه برای کاربر نهایی لازم نیستند.
- رابط می‌تواند از اجزای مشترک استفاده کند، اما چیدمان و تعاملات باید Adaptive و متناسب با دسکتاپ یا موبایل باشند.

### ۲۰.۲ هستهٔ مشترک و مرز پلتفرم
- Domain و Application، قواعد محصول، اعتبارسنجی و موتور برنامه‌ریزی را در قالب هستهٔ مشترک و مستقل از UI و سیستم‌عامل نگه می‌دارند.
- Presentation برای Windows و Android می‌تواند از کد و اجزای مشترک استفاده کند، اما باید الگوهای تعاملی هر فرم‌فکتور را رعایت کند.
- قابلیت‌های وابسته به سیستم‌عامل از طریق Platform Adapter ارائه می‌شوند؛ از جمله ذخیره‌سازی، فایل‌ها، اعلان‌ها، Secure Storage و چرخهٔ عمر برنامه.
- Desktop Shell و Mobile Shell باید جداگانه از نظر بلوغ، سازگاری، اندازهٔ خروجی، مصرف منابع، امنیت و فرایند build/release ارزیابی شوند. انتخاب یک فناوری مشترک مانند Tauri یا هر گزینهٔ دیگر هنوز مصوب نیست.
- هیچ فرضی دربارهٔ سازگاری کامل افزونه‌ها یا APIهای یک shell در Windows و Android مجاز نیست؛ هر قابلیت باید روی هر دو پلتفرم آزمون شود.

### ۲۰.۳ ذخیره‌سازی محلی
- هر دستگاه نسخهٔ محلی و مستقل داده‌های خود را نگه می‌دارد و عملیات اصلی بدون اینترنت قابل استفاده است.
- SQLite نامزد اصلی ارزیابی برای ذخیره‌سازی محلی ساخت‌یافته است، نه تصمیم اجرایی قطعی. سازگاری binding/driver، migration، backup/restore، رمزنگاری در حالت سکون، crash recovery و packaging باید برای Windows و Android اثبات شود.
- قرارداد Repository و Unit of Work باید از فناوری پایگاه داده مستقل باشد؛ Application نباید API اختصاصی SQLite یا جزئیات یک shell را بشناسد.
- Platform Storage Adapter امکان استفاده از پیاده‌سازی مناسب هر پلتفرم را می‌دهد، بدون آنکه مدل دامنه یا use caseها دو شاخه شوند.
- LocalStorage فعلی prototype است و نباید بدون migration نسخه‌دار، backup و read-back validation حذف یا جایگزین شود.
- IndexedDB تنها در صورت وجود هدف وب آینده قابل بررسی است و بخشی از تعهد نسخهٔ اول Windows/Android نیست.

### ۲۰.۴ همگام‌سازی اختیاری
- Sync بین Windows و Android قابلیت اختیاری است؛ کاربر می‌تواند آن را فعال یا غیرفعال کند. خاموش‌بودن Sync نباید مانع استفادهٔ مستقل هر دستگاه شود.
- هیچ داده‌ای صرفاً به دلیل نصب یا اجرای برنامه به سرویس Sync ارسال نمی‌شود؛ فعال‌سازی باید آگاهانه، قابل توضیح و قابل لغو باشد.
- Sync با کپی یا همگام‌سازی مستقیم فایل پایگاه داده پیاده‌سازی نمی‌شود؛ یک Sync Engine مستقل، تغییرات سطح موجودیت/رویداد را با سرویس Sync مبادله می‌کند.
- پیش از فعال‌سازی Sync باید شناسه‌های پایدار، شناسهٔ دستگاه، Change Log یا مدل تغییرات، idempotency، tombstone برای حذف‌ها، نسخهٔ schema، سیاست conflict resolution و رفتار قطع/وصل شبکه طراحی شوند.
- همگام‌سازی باید آگاه از حریم خصوصی باشد؛ رمزنگاری انتقال الزامی است و رمزنگاری سرتاسری و مدیریت کلید باید در threat model و طراحی امنیتی مستقل تعیین و آزموده شود. صرف TLS را نباید معادل رمزنگاری سرتاسری دانست.
- Backend، مدل حساب، نگهداری کلید، سیاست بازیابی حساب و هزینهٔ عملیاتی Sync هنوز انتخاب نشده‌اند.

### ۲۰.۵ ترتیب و معیار پذیرش
1. حفظ و تکمیل هستهٔ مشترک و قراردادهای Application.
2. ارزیابی و اثبات ذخیره‌سازی محلی و migration امن روی Windows و Android.
3. ساخت و آزمون نسخهٔ Windows.
4. ساخت و آزمون نسخهٔ Android با همان قراردادهای Domain/Application.
5. طراحی و پیاده‌سازی Sync اختیاری پس از پایدارشدن ذخیره‌سازی محلی.

معیارهای پذیرش چندسکویی: هر دو نسخه بدون اینترنت برای قابلیت‌های اصلی کار کنند؛ داده پس از بسته‌شدن/راه‌اندازی مجدد باقی بماند؛ Backup/Restore آزموده شود؛ migration بدون از دست‌رفتن داده انجام شود؛ خاموش‌بودن Sync هیچ درخواست یا انتقال دادهٔ Sync ایجاد نکند؛ و با فعال‌بودن Sync، تکرار پیام یا قطع شبکه باعث ثبت دوباره یا حذف ناخواستهٔ داده نشود.

### ۲۱.۱ اصول طراحی

1. Domain و Application به API یک دیتابیس، LocalStorage، فایل‌سیستم یا API سیستم‌عامل وابسته نیستند.
2. Application از قراردادهای محدود و مشخص Repository و Unit of Work استفاده می‌کند؛ Infrastructure پیاده‌سازی آن‌ها را فراهم می‌کند.
3. همهٔ قراردادهای I/O از ابتدا asynchronous و Promise-based هستند تا پیاده‌سازی‌های محلی و آینده بدون تغییر شکل قرارداد پشتیبانی شوند.
4. Repository مسئول خواندن و نوشتن داده است، نه اجرای قواعد چرخهٔ عمر یا تصمیم‌گیری دامنه.
5. اعتبارسنجی، مجوزها و قواعد تغییر روابط در Domain/Application باقی می‌مانند.
6. Repositoryهای مورد استفاده در یک عملیات چندموجودیتی باید از همان محدودهٔ Unit of Work دریافت شوند.
7. هیچ تضمین atomicity نباید برای Adapter فاقد تراکنش واقعی ادعا شود.

### ۲۱.۲ قراردادهای Repository

قراردادهای مفهومی نسخهٔ اول:

**TaskRepository**
- `getById(id)`: بازیابی یک Task یا مقدار تهی.
- `list(query?)`: فهرست Taskها با فیلترهای محدود و تعریف‌شده.
- `listByProjectId(projectId)`: بازیابی Taskهای مرتبط با Project؛ برای عملیات چرخهٔ عمر Project لازم است.
- `save(task)`: ایجاد یا به‌روزرسانی رکورد با شناسهٔ پایدار؛ ذخیرهٔ دوبارهٔ همان نسخه نباید رکورد تکراری بسازد.

**ProjectRepository**
- `getById(id)`
- `list(query?)`
- `listByGroupId(groupId)`
- `save(project)`

**ProjectGroupRepository**
- `getById(id)`
- `list(query?)`
- `save(group)`

**TaskProjectLinkHistoryRepository**
- `append(event)`: افزودن رویداد جدید؛ شناسهٔ رویداد باید یکتا باشد.
- `listByTask(taskId)`: بازیابی رویدادهای رابطه برای یک Task، با ترتیب پایدار و قابل تعریف.

قواعد مشترک:
- شناسهٔ تکراری نباید باعث ایجاد رکورد دوم شود؛ semantics ذخیره‌سازی باید برای هر Adapter یکسان و مستند باشد.
- Queryها محدود و نوع‌دارند؛ Application به query language یا API عمومی دیتابیس دسترسی نمی‌گیرد.
- تاریخچه append-only است؛ قرارداد عمومی برای ویرایش یا حذف رویدادهای ثبت‌شده ارائه نمی‌شود.
- Repository چرخهٔ عمر موجودیت را تعیین نمی‌کند. Archive، Trash، Restore و Permanent Delete از use caseهای Application عبور می‌کنند.
- حذف فیزیکی فقط درون عملیات Application مجاز و پس از اجرای سیاست چرخهٔ عمر است؛ API حذف عمومی برای Presentation ارائه نمی‌شود.
- Task مستقل مجاز است؛ بنابراین `projectId` می‌تواند تهی باشد. هیچ Repository یا موجودیت TaskGroup جداگانه‌ای تعریف نمی‌شود.

### ۲۱.۳ قرارداد Unit of Work

شکل مفهومی:

```js
await unitOfWork.execute(async (repositories) => {
  await repositories.tasks.save(updatedTask);
  await repositories.taskProjectHistory.append(historyEvent);
});
```

- callback فقط Repositoryهای متعلق به همان transaction را دریافت می‌کند.
- همهٔ عملیات داخل callback باید در یک مرز تراکنش مشترک اجرا شوند.
- در صورت موفقیت callback، Adapter عملیات را commit می‌کند و نتیجه را برمی‌گرداند.
- در صورت throw یا reject شدن callback یا شکست commit، Adapter باید rollback واقعی انجام دهد و خطا را به caller منتقل کند.
- Repositoryهای transaction-scoped نباید پس از پایان callback نگهداری یا استفاده شوند.
- Nested transaction در نسخهٔ اول پشتیبانی نمی‌شود؛ تلاش برای اجرای تو‌در‌تو باید با خطای مشخص رد شود.
- خطاها نباید بلعیده شوند یا به نتیجهٔ موفق تبدیل شوند.
- این قرارداد تضمین رفتاری مورد انتظار را تعریف می‌کند؛ پیاده‌سازی آن فقط روی Adapter دارای transaction واقعی می‌تواند atomicity کامل ارائه کند.

### ۲۱.۴ عملیات چندموجودیتی الزامی

**انتقال Task از Project A به Project B**
1. بازیابی و اعتبارسنجی Task و Project مقصد در Application.
2. اجرای قواعد رابطه و چرخهٔ عمر Project.
3. ذخیرهٔ Task با `projectId` جدید.
4. افزودن رویداد `moved` به تاریخچه.
5. commit هر دو تغییر در یک Unit of Work.

اگر هر بخش شکست بخورد، نه تغییر Task و نه رویداد تاریخچه نباید به‌تنهایی باقی بماند.

**حذف دائمی Project**
1. بازیابی Project و Taskهای مرتبط.
2. اجرای سیاست Permanent Delete و بررسی مجوز/تأیید در Application.
3. پاک‌کردن `projectId` در Taskهای مرتبط؛ Taskها حذف نمی‌شوند.
4. حذف رکورد Project طبق سیاست چرخهٔ عمر.
5. ثبت تغییرات لازم برای سازگاری و قابلیت ردیابی؛ طراحی Change Log مربوط به Sync در مرحلهٔ مستقل انجام می‌شود.
6. commit همهٔ تغییرات در یک Unit of Work.

**حذف ProjectGroup**
1. بازیابی Group و Projectهای عضو.
2. تهی‌کردن `groupId` در Projectهای عضو.
3. حذف رکورد Group.
4. commit همهٔ تغییرات در یک Unit of Work.

Archive یا Trash کردن Project با Permanent Delete متفاوت است و نباید رابطه‌های زنده را پاک کند.

### ۲۱.۵ Storage Adapter و مرز پلتفرم

- Infrastructure یک پیاده‌سازی Repository و Unit of Work ارائه می‌کند که جزئیات ذخیره‌سازی را پشت قراردادها پنهان می‌کند.
- Composition Root یا نقطهٔ مونتاژ برنامه، Adapter مناسب را انتخاب و به Application تزریق می‌کند.
- Application نباید تشخیص دهد که برنامه روی Windows یا Android اجرا می‌شود و نباید مستقیماً به `window.localStorage`، فایل‌سیستم یا API بومی دسترسی داشته باشد.
- Platform Adapter مسئول جزئیات مختص سیستم‌عامل، مسیر و مجوز فایل، Secure Storage و یکپارچگی با چرخهٔ عمر برنامه است.
- Adapter باید semantics یکسانی برای Repositoryها و Unit of Work فراهم کند؛ تفاوت‌های واقعی پلتفرم باید مستند و آزموده شوند.
- LocalStorage فعلی به‌عنوان پیاده‌سازی prototype/legacy شناخته می‌شود. تا وقتی تراکنش واقعی ندارد، نباید به‌عنوان پیاده‌سازی کامل Unit of Work معرفی شود.
- Backup، Restore، serialization، schema validation و migration در Infrastructure قرار می‌گیرند؛ migrationها باید مستقل، آزمون‌پذیر، نسخه‌دار و همراه با حفظ دادهٔ خام و بررسی read-back باشند.

### ۲۱.۶ هم‌زمانی و آمادگی برای Sync

- در نسخهٔ local-first، Adapter باید دست‌کم از نوشتن هم‌زمان ناسازگار در یک فرایند جلوگیری کند و در صورت پشتیبانی مدل، کنترل نسخهٔ خوش‌بینانه را اعمال کند.
- تعارض میان چند دستگاه، مسئولیت Sync Engine آینده است و نباید با تراکنش محلی Unit of Work یکی گرفته شود.
- Repositoryها مستقیماً با سرویس ابری ارتباط نمی‌گیرند.
- شناسهٔ دستگاه، Change Log، tombstone، idempotency، conflict resolution و رمزنگاری Sync در طراحی مستقل Sync تعریف می‌شوند؛ این قرارداد به‌تنهایی به معنی پیاده‌سازی Sync نیست.
- وجود فیلد version در همهٔ موجودیت‌ها نباید فرض شود؛ پیش از استفاده از optimistic concurrency باید مدل فعلی Task، Project و ProjectGroup و semantics نسخهٔ آن‌ها جداگانه بررسی شود.

### ۲۱.۷ معیارهای پذیرش قرارداد

1. Application می‌تواند Task، Project، ProjectGroup و تاریخچه را فقط از طریق قراردادهای تعریف‌شده بخواند و بنویسد.
2. انتقال Task و ثبت تاریخچه در یک transaction موفق یا ناموفق می‌شوند.
3. Permanent Delete کردن Project، Taskها را حفظ و ارجاع آن‌ها را تهی می‌کند.
4. حذف Group، Projectها و Taskها را حفظ و فقط عضویت Group را پاک می‌کند.
5. خطاهای ذخیره‌سازی و commit به Application گزارش می‌شوند و موفقیت کاذب ایجاد نمی‌شود.
6. Repositoryهای transaction-scoped پس از پایان Unit of Work قابل استفاده نیستند.
7. هستهٔ Domain/Application بدون وابستگی به API اختصاصی Windows، Android یا دیتابیس قابل آزمون است.
8. Adapter فاقد تراکنش واقعی، صریحاً به‌عنوان محدودیت شناخته می‌شود و atomicity کامل را ادعا نمی‌کند.

### ۲۱.۸ ترتیب پیاده‌سازی و ریسک گذار

1. تطبیق قراردادها با مدل‌های واقعی Domain و use caseهای فعلی.
2. تعریف interfaceهای async و آزمون‌های قراردادی Repository و Unit of Work.
3. ساخت یک proof of concept برای Adapter و اثبات تراکنش واقعی روی Windows و Android.
4. مقایسهٔ گزینه‌های ذخیره‌سازی، از جمله SQLite، بر اساس سازگاری binding/driver، transaction، migration، backup/restore، امنیت، packaging و نگهداری؛ در این مرحله انتخاب فناوری قطعی می‌شود.
5. انتقال تدریجی callsiteهای فعلی از توابع sync و LocalStorage به قراردادهای async، با حفظ مسیر migration و backup.
6. افزودن persistence برای Project، ProjectGroup و تاریخچه، سپس اجرای آزمون‌های integration و بازیابی داده.

**ریسک اصلی گذار:** تغییر قراردادهای فعلی از عملیات ساده و عمدتاً sync به قراردادهای async و transaction-scoped، نیازمند refactor کنترل‌شدهٔ Application و تست‌های integration است. این طراحی به‌تنهایی مجوز تغییر کد، حذف LocalStorage یا انتخاب SQLite نیست.

**یادداشت سازگاری مستندات:** در بخش ۵ این سند هنوز شرح قدیمی schemaVersion 2 دیده می‌شود؛ ممیزی کد فعلی نسخهٔ 3 را مشاهده کرده است. اصلاح شرح مهاجرت و schemaVersion باید در یک اصلاح مستنداتی مستقل و پس از تطبیق کامل با کد انجام شود.
