# معماری فنی ویرا

نسخه: 0.5-draft  
هدف: تبدیل نمونهٔ اولیهٔ تک‌فایلی به سامانه‌ای ماژولار، local-first و قابل‌آزمایش.

## ۱. اصول معماری

1. جداسازی رابط کاربری، منطق دامنه، ذخیره‌سازی و اتصال‌های بیرونی
2. موتور زمان‌بندی مستقل از هوش مصنوعی
3. کارکرد آفلاین هستهٔ محصول بدون مدل AI محلی
4. حداقل‌سازی وابستگی‌ها و هزینهٔ اجرا
5. نسخه‌دار بودن مدل داده و مهاجرت کنترل‌شده
6. آزمون‌پذیری منطق تاریخ، تکرار، اعلان و زمان‌بندی
7. امنیت کلیدهای API در سمت سرور

## ۵. ذخیره‌سازی و مهاجرت

نسخهٔ فعلی از LocalStorage با کلید `vira-planner-tasks-v1` استفاده می‌کند. نام کلید برای سازگاری حفظ شده، اما قالب محتوای آن نسخه‌دار است:

```js
{
  schemaVersion: 2,
  tasks: [/* canonical tasks */]
}
```

- آرایهٔ خام قدیمی، قالب v1 محسوب می‌شود.
- قالب v2 فقط Taskهای Canonical کامل و معتبر را می‌پذیرد.
- `schemaVersion` نسخهٔ ساختار ذخیره‌سازی است و با `task.version` تفاوت دارد.
- نسخهٔ ناشناخته یا جدیدتر هرگز بازنویسی نمی‌شود.
- شناسهٔ تکراری یا حتی یک Task نامعتبر، کل مجموعه را رد می‌کند.
- فیلدهای ناشناخته حفظ می‌شوند؛ aliasهای سازگاری UI یعنی `date`, `time`, `category`, `done` در مسیر ذخیره‌سازی Canonical حذف می‌شوند.

### مرز مسئولیت‌ها

1. Infrastructure قالب JSON، نسخه، خواندن/نوشتن، backup و بررسی read-back را مدیریت می‌کند.
2. Application با `legacy-task-adapter` دادهٔ v1 را به مدل Canonical تبدیل و سپس برای UI aliasهای سازگاری را تولید می‌کند.
3. Domain اعتبار Taskهای Canonical را تعیین می‌کند.
4. Collection فقط پس از بارگذاری موفق اجازهٔ تغییر داده می‌دهد.

### مسیر مهاجرت v1 به v2

1. خواندن آرایهٔ خام قدیمی بدون تغییر آن
2. اعتبارسنجی ساختار پایه و یکتایی شناسه‌ها
3. تبدیل Legacy در لایهٔ Application
4. اعتبارسنجی کامل همهٔ Taskها در Domain
5. ذخیرهٔ دقیق raw قبلی در backup
6. نوشتن envelope نسخهٔ ۲
7. خواندن مجدد و بررسی صحت قالب و داده
8. در صورت شکست، تلاش برای بازگرداندن مقدار قبلی و قفل ماندن عملیات عادی

Backup شامل رشتهٔ خام قبلی است. بازیابی، ابتدا محتوای پشتیبان را parse و بررسی می‌کند، مقدار فعلی را در کلید rollback جداگانه نگه می‌دارد و سپس مقدار پشتیبان را جایگزین می‌کند. LocalStorage تراکنش چندمرحله‌ای واقعی ندارد؛ بنابراین این طراحی از حفظ نسخه‌ها و rollback best-effort استفاده می‌کند و ادعای atomicity کامل ندارد.

هیچ migration نباید بی‌صدا دادهٔ ناسازگار را حذف یا با default پنهان کند. در صورت خطا، دادهٔ خام باید حفظ و نوشتن عادی متوقف شود.

انتقال به پایگاه دادهٔ محلی مانند IndexedDB فقط پس از بررسی نیاز واقعی و طراحی مهاجرت مستقل انجام می‌شود.

## ۶. موتور زمان‌بندی

موتور ورودی‌های صریح می‌گیرد:
- تعهدات ثابت (hard constraints)
- ترجیحات (soft constraints)
- وظایف با مدت، اولویت، deadline و dependency
- زمان‌های استراحت و buffer
- ساعات قابل برنامه‌ریزی

خروجی:
- time blocks پیشنهادی
- وظایف زمان‌بندی‌نشده
- تعارض‌ها
- توضیح علت هر تصمیم
- تغییرات نسبت به برنامهٔ فعلی

AI فقط ورودی زبان طبیعی را به ساختار قابل‌اعتبارسنجی تبدیل می‌کند. موتور نباید به پاسخ احتمالی مدل برای تشخیص تداخل یا رعایت محدودیت‌ها متکی باشد.

## ۷. اعلان و صدا

NotificationService باید از منطق وظایف جدا باشد و adapterهای مستقل داشته باشد:
- in-app notifications
- browser notifications
- audio playback
- speech synthesis
- future platform notification adapter

زمان‌بندی اعلان باید از دادهٔ پایدار بازسازی شود؛ اتکا به setTimeoutهای طولانی یا تایمر زندهٔ صفحه کافی نیست. رفتار پس از بسته‌شدن مرورگر به قابلیت واقعی مرورگر/سیستم‌عامل و مجوزهای کاربر وابسته است و باید جداگانه آزمون شود.

## ۱۲. قرارداد مدل داده و ارتباط موجودیت‌ها — Target Architecture v0.6

**وضعیت:** طراحی هدف؛ هنوز پیاده‌سازی نشده است. این بخش جهت طراحی را مشخص می‌کند و جایگزین فوری مدل ذخیره‌شدهٔ فعلی نیست.

### ۱۲.۱ اصول مشترک مدل

1. هر موجودیت پایدار یک شناسهٔ یکتا و مستقل دارد.
2. هر موجودیت مالک داده‌های خودش است؛ نماها و ماژول‌های دیگر فقط از طریق شناسه و قرارداد مشخص به آن ارجاع می‌دهند.
3. حذف یا آرشیو یک موجودیت نباید به‌طور ضمنی موجودیت‌های مستقل دیگر را حذف کند.
4. زمان‌های دقیق به‌صورت timestamp استاندارد و همراه با منطقهٔ زمانی لازم ذخیره می‌شوند؛ تاریخ بدون ساعت به‌صورت date-only با قالب ISO ذخیره می‌شود.
5. زمان نمایش شمسی و محلی‌سازی اعداد مسئولیت Presentation است؛ تبدیل و اعتبارسنجی تاریخ در لایه‌های مشترک باید صریح و آزمون‌پذیر باشد.
6. نام فیلدها و schema ذخیره‌سازی بخشی از قرارداد سازگاری‌اند؛ تغییر نام یا معنای فیلد نیازمند migration است.
7. شناسهٔ داخلی، وضعیت، زمان ایجاد/ویرایش و نسخهٔ موجودیت باید از داده‌های نمایشی UI مستقل بمانند.

### ۱۲.۲ موجودیت‌ها و مالکیت داده

- **Task:** مالک عنوان، توضیح، وضعیت، پیشرفت، اولویت، تاریخ برنامه‌ریزی، deadline، مدت تخمینی، وابستگی‌ها و ارجاع به پروژهٔ اصلی.
- **Project:** مالک مشخصات و چرخهٔ عمر پروژه؛ وظایف به آن ارجاع می‌دهند و دادهٔ وظایف داخل Project کپی نمی‌شود.
- **Goal:** مالک تعریف هدف، معیار سنجش، مقدار هدف/فعلی و وضعیت آن.
- **CalendarEvent:** مالک تعهد یا رویداد مستقل زمانی، مانند کلاس یا جلسهٔ ثابت.
- **WorkSession:** مالک یک نشست کاری مرتبط با دقیقاً یک Task؛ زمان برنامه‌ریزی‌شده و وضعیت همان نشست در این موجودیت نگهداری می‌شود.
- **TimeEntry:** ثبت یک بازهٔ تایمر یا مدت دستی که به یک WorkSession تعلق دارد؛ مبنای محاسبهٔ زمان واقعی است.
- **Document:** مالک فرادادهٔ سند؛ محتوای فایل در لایهٔ نگهداری فایل قرار می‌گیرد و نباید در رکوردهای Task یا Project تکرار شود.
- **Habit / Routine:** مالک تعریف رفتارهای تکرارشونده و هدف‌های منعطف؛ با رویداد ثابت و Task تکرارشونده یکی نیست.
- **RecurrenceRule:** مالک قاعدهٔ تکرار؛ occurrence و exception باید به قاعدهٔ اصلی ارجاع دهند و تغییر یک occurrence نباید الگوی اصلی را بازنویسی کند.
- **Reminder:** مالک تنظیمات و وضعیت یادآوری؛ هدف یادآوری با نوع و شناسهٔ موجودیت مرجع مشخص می‌شود.

### ۱۲.۳ روابط پایه

| رابطه | قرارداد پیشنهادی |
|---|---|
| Project → Task | هر Task در نسخهٔ پایه حداکثر یک Project اصلی دارد؛ Task مستقل نیز مجاز است |
| Goal ↔ Task | چندبه‌چند؛ از رابطهٔ مستقل GoalTaskLink استفاده شود |
| Goal ↔ Project | چندبه‌چند؛ از رابطهٔ مستقل GoalProjectLink استفاده شود |
| Task → WorkSession | یک‌به‌چند؛ هر WorkSession دقیقاً به یک Task تعلق دارد |
| WorkSession → TimeEntry | یک‌به‌چند؛ هر ثبت زمان دقیقاً متعلق به یک نشست است |
| Document ↔ سایر موجودیت‌ها | چندبه‌چند از طریق DocumentLink با نوع و شناسهٔ مقصد |
| Task → Task | وابستگی و زیرکار با ارجاع شناسه‌ای؛ چرخهٔ dependency باید رد شود |
| CalendarEvent → RecurrenceRule | صفر یا یک قاعدهٔ تکرار؛ استثناها مستقل و ارجاع‌دار |
| Reminder → هدف | یک ارجاع نوع‌دار به موجودیت پشتیبانی‌شده |

در نسخهٔ پایه، Task فقط یک Project اصلی خواهد داشت تا پیچیدگی بی‌دلیل ایجاد نشود. اگر نیاز واقعی به حضور یک Task در چند پروژه اثبات شد، این تصمیم با رابطهٔ مستقل تغییر می‌کند؛ نباید چند projectId را به‌صورت آرایه‌ای بدون تعریف معنا اضافه کنیم.

### ۱۲.۴ زمان‌بندی و نمای تقویم

- Task مالک deadline و تاریخ برنامه‌ریزی date-only است؛ داشتن این فیلدها به‌تنهایی بلوک ساعت‌دار ایجاد نمی‌کند.
- WorkSession مالک بازهٔ کاری برنامه‌ریزی‌شده است و به‌صورت بلوک زمانی در تقویم نمایش داده می‌شود.
- CalendarEvent مالک تعهد مستقل ثابت یا تکرارشونده است.
- تقویم یک **Projection** از CalendarEventها، WorkSessionها، وظایف تمام‌روز و markerهای deadline می‌سازد؛ مالک نسخهٔ دوم داده نیست.
- TimeBlock در صورت نیاز به‌عنوان خروجی محاسباتی یا پیشنهاد زمان‌بندی ساخته می‌شود؛ تا وقتی ضرورت ذخیره‌سازی مستقل آن اثبات نشده، نباید نسخهٔ کپی‌شدهٔ زمان WorkSession یا CalendarEvent باشد.
- منطقهٔ زمانی برای زمان دقیق صریح است. تاریخ بدون ساعت نباید با نیمه‌شب ساختگی به timestamp تبدیل شود.
- مدت تخمینی Task از مدت برنامه‌ریزی‌شدهٔ نشست و زمان واقعی ثبت‌شده مستقل است.

### ۱۲.۵ ثبت زمان واقعی

- هر WorkSession می‌تواند چند TimeEntry داشته باشد.
- TimeEntry از نوع timer interval باید زمان شروع و پایان معتبر داشته باشد؛ مدت آن از بازه محاسبه می‌شود.
- TimeEntry دستی باید مدت مثبت و منشأ ثبت مشخص داشته باشد.
- بازه‌های تایمر هم‌پوشان نباید دوبار شمرده شوند؛ سیاست جلوگیری از هم‌پوشانی و تایمر هم‌زمان باید در use case ثبت زمان اعمال و آزمون شود.
- اصلاح ثبت دستی نباید با افزودن دوبارهٔ همان مدت، زمان را دوبرابر کند؛ رکورد اصلاح‌شده باید قابل ردیابی باشد.
- مجموع زمان واقعی از ثبت‌های معتبر نشست محاسبه می‌شود؛ مقدار تجمیعی نباید بدون قاعده به‌عنوان دادهٔ مستقل و متناقض ذخیره شود.
- چرخهٔ عمر تایمر، بازیابی پس از Refresh/بسته‌شدن برنامه و تاریخچهٔ اصلاحات پیش از پیاده‌سازی به طراحی تفصیلی نیاز دارد.

### ۱۲.۶ روابط اسناد

Document فقط یک بار ثبت می‌شود. DocumentLink حداقل شامل شناسهٔ خودش، documentId، نوع مقصد، شناسهٔ مقصد، زمان ایجاد و منشأ ارتباط است. ایجاد و حذف پیوند باید از Application use case عبور کند و وجود هر دو سمت رابطه را بررسی کند.

چون رابطهٔ نوع‌دار به‌تنهایی ممکن است در همهٔ پایگاه‌های داده foreign key مستقیم نداشته باشد، اعتبارسنجی مقصد در لایهٔ Application الزامی است. اگر در آینده پایگاه دادهٔ رابطه‌ای انتخاب شود، برای روابط پرتکرار می‌توان جدول‌های پیوند اختصاصی و محدودیت‌های واقعی foreign key تعریف کرد.

### ۱۲.۷ حذف، آرشیو و پیوندهای یتیم

- حذف دائمی با تأیید صریح و سیاست مشخص انجام می‌شود.
- آرشیو، حذف دائمی نیست و برای موجودیت‌های پشتیبانی‌شده باید امکان بازیابی داشته باشد.
- حذف Project نباید Taskهای آن را بی‌صدا حذف کند؛ ابتدا باید سیاست انتقال، مستقل‌کردن یا رد حذف تعیین شود.
- حذف Task نباید WorkSession و TimeEntryهای تاریخی را بدون سیاست retention از بین ببرد.
- حذف Document باید وضعیت فایل و پیوندها را هماهنگ کند؛ شکست هر مرحله باید قابل تشخیص و بازیابی باشد.
- پاک‌سازی پیوندهای یتیم فقط از طریق عملیات کنترل‌شده و گزارش‌پذیر انجام می‌شود.

## ۱۳. قرارداد Repository و مرز Application

### ۱۳.۱ اصل

Domain نباید LocalStorage، IndexedDB، فایل‌سیستم، HTTP یا API ارائه‌دهنده را بشناسد. Application از قراردادهای Repository استفاده می‌کند و Infrastructure آن‌ها را پیاده‌سازی می‌کند.

### ۱۳.۲ قراردادهای موردنیاز در معماری هدف

- TaskRepository
- ProjectRepository
- GoalRepository
- WorkSessionRepository
- TimeEntryRepository
- CalendarEventRepository
- DocumentRepository
- RecurrenceRepository
- ReminderRepository
- RelationRepository یا repositoryهای اختصاصی هر رابطه

هر Repository باید عملیات متناسب با aggregate خودش را ارائه دهد؛ مانند getById، list با فیلتر مشخص، save و حذف کنترل‌شده. رابط دقیق و نوع خروجی‌ها هنگام طراحی هر ماژول تعیین می‌شود؛ این فهرست الزام به ساخت هم‌زمان همهٔ Repositoryها نیست.

### ۱۳.۳ قواعد دسترسی

1. Presentation فقط Application use caseها را فراخوانی می‌کند.
2. Presentation مستقیماً Repository یا storage adapter را صدا نمی‌زند.
3. تغییر داده از مسیر use case و اعتبارسنجی Domain انجام می‌شود.
4. Repository مسئول نگاشت و ذخیره‌سازی است، نه تصمیم‌های محصولی یا زمان‌بندی.
5. queryهای نمایشی می‌توانند read model بسازند، اما read model مالک دادهٔ اصلی نیست.
6. خروجی Repository نباید مرجع mutable داخلی storage را به بیرون نشت دهد.

### ۱۳.۴ هماهنگی چند موجودیت

Use caseهایی مانند حذف Project، اتصال Document به Task یا تکمیل عملیات چندمرحله‌ای باید هماهنگی تغییرات را در Application مدیریت کنند.

در معماری هدف یک مرز Unit of Work/Transaction برای عملیات چندموجودیتی تعریف می‌شود. با این حال، LocalStorage فعلی تراکنش واقعی چندکلیدی ندارد؛ adapter فعلی فقط می‌تواند backup و rollback best-effort ارائه کند و نباید atomicity کامل ادعا شود. اگر تضمین تراکنش برای عملیات چندموجودیتی لازم شد، انتخاب پایگاه داده‌ای مانند IndexedDB و migration جداگانه باید پیش از پیاده‌سازی تصویب شود.

## ۱۴. راهبرد مهاجرت مدل داده

**اصل محافظه‌کارانه:** مدل فعلی Task و envelope ذخیره‌سازی موجود نباید صرفاً به‌دلیل طراحی جدید فوراً تغییر کند.

1. وضعیت واقعی schema و دادهٔ ذخیره‌شدهٔ فعلی، شامل envelope نسخهٔ ۲ و legacy، پیش از هر migration دوباره بررسی شود.
2. قرارداد نهایی فیلدها و روابط پیش از تعیین شمارهٔ schema بعدی تثبیت شود.
3. migration جدید به‌صورت مرحله‌ای و نسخه‌دار تعریف شود؛ افزایش schemaVersion فقط هنگام ورود واقعی ساختار ذخیره‌شدهٔ جدید انجام شود.
4. migration باید pure/testable باشد: ورودی را دریافت کند و خروجی نسخهٔ جدید را بسازد، بدون side effect پنهان.
5. پیش از نوشتن، کل دادهٔ تبدیل‌شده و روابط آن اعتبارسنجی شوند؛ دادهٔ ناقص یا رابطهٔ یتیم نباید بی‌صدا حذف شود.
6. raw قبلی پیش از نوشتن نسخهٔ جدید در backup مستقل حفظ شود.
7. پس از نوشتن، read-back و اعتبارسنجی کامل انجام شود.
8. در شکست، دادهٔ خام قبلی حفظ شود، عملیات عادی در وضعیت نامطمئن قفل بماند و خطای قابل فهم گزارش شود.
9. اجرای دوبارهٔ migration نباید دادهٔ تکراری بسازد؛ رفتار باید idempotent یا با تشخیص دقیق نسخه محدود شود.
10. فیلدهای ناشناخته تا زمانی که سیاست سازگاری روشن نشده حذف نشوند.
11. schemaVersion از version هر موجودیت مستقل است.
12. مهاجرت به IndexedDB یا backend پروژه‌ای جدا با ارزیابی ریسک، backup و تست بازیابی است؛ بخشی از این طراحی به‌تنهایی مجوز آن مهاجرت نیست.

### آزمون‌های پذیرش migration

- دادهٔ v2 معتبر و خالی
- چند Task با تمام فیلدهای اختیاری
- دادهٔ legacy قدیمی
- شناسهٔ تکراری و رابطهٔ نامعتبر
- فیلد ناشناخته
- نسخهٔ ذخیره‌سازی جدیدتر از نسخهٔ برنامه
- شکست هنگام نوشتن یا read-back
- بازیابی از backup
- اجرای دوبارهٔ migration
- اطمینان از عدم حذف یا تغییر دادهٔ اصلی در صورت شکست

## ۱۵. مرز AI با مدل داده و Application

- AI از طریق Application و ابزارهای محدود و مجاز به داده دسترسی می‌گیرد؛ دسترسی مستقیم به storage ندارد.
- خروجی AI ابتدا یک پیشنهاد ساختاریافته با منشأ، زمان تولید، میزان اطمینان و تغییرات پیشنهادی است.
- پیشنهاد قبل از اعمال باید از اعتبارسنجی Domain و قواعد قطعی عبور کند.
- اعمال تغییرات حساس، جابه‌جایی برنامه، حذف یا ارسال اطلاعات خصوصی تابع تأیید و مجوز کاربر است.
- AI نباید deadline، زمان واقعی، انجام‌شدن کار یا سندی را که منبع معتبری ندارد جعل کند.
- خاموش‌کردن AI نباید عملیات پایهٔ وظایف، تقویم و اسناد محلی را مختل کند.

## ۱۶. ترتیب اجرای این معماری

1. بازبینی این قرارداد در برابر مدل واقعی و تصمیم‌های ثبت‌شدهٔ محصول.
2. تثبیت نام فیلدها و semantics مربوط به Task، WorkSession و CalendarEvent.
3. تعریف قرارداد Repository و عملیات Application برای هر aggregate.
4. طراحی migration و آزمون‌های آن، بدون اجرای migration روی دادهٔ کاربر.
5. پیاده‌سازی مرحله‌ای هر بخش فقط پس از تصویب دامنه و معیار پذیرش آن.

**محدودیت این نسخه:** این Target Architecture نقشهٔ طراحی است؛ هیچ‌یک از Project، Goal، WorkSession، TimeEntry، Document Library یا Repositoryهای نام‌برده‌شده صرفاً با ثبت این سند، پیاده‌سازی‌شده محسوب نمی‌شوند.

## ۱۷. طراحی تفصیلی WorkSession و TimeEntry

**وضعیت:** قرارداد طراحی هدف؛ هنوز پیاده‌سازی نشده است.

### ۱۷.۱ جداسازی مسئولیت‌ها

- Task مالک مدت تخمینی کل کار و Deadline است.
- WorkSession نمایندهٔ یک نوبت مشخص کار روی Task است.
- هر WorkSession دقیقاً به یک Task تعلق دارد.
- یک Task می‌تواند چند WorkSession در روزهای مختلف داشته باشد.
- WorkSession مالک مدت برنامه‌ریزی‌شدهٔ همان نشست است.
- TimeEntry ثبت‌کنندهٔ زمان واقعی است؛ زمان واقعی نشست از TimeEntryهای معتبر محاسبه می‌شود و نباید با مدت تخمینی Task یا مدت برنامه‌ریزی‌شدهٔ نشست یکی فرض شود.

### ۱۷.۲ چرخهٔ عمر WorkSession

وضعیت‌های پیشنهادی:
- planned: نشست ساخته شده و هنوز شروع نشده است.
- in_progress: کار روی نشست شروع شده؛ ممکن است تایمر فعال یا متوقف باشد.
- completed: نشست به پایان رسیده است.
- cancelled: نشست لغو شده است و زمان‌های ثبت‌شدهٔ قبلی آن بدون سیاست retention حذف نمی‌شوند.

«مکث» وضعیت مستقل WorkSession نیست. نشست در وضعیت in_progress باقی می‌ماند، اما در آن لحظه TimeEntry تایمری فعال ندارد. با ادامهٔ کار، یک TimeEntry جدید ساخته می‌شود. بنابراین هر بار شروع/ادامه، بازه‌ای جدا ایجاد می‌کند.

### ۱۷.۳ مدل TimeEntry

نوع‌های پیشنهادی:
- timer_interval: دارای startedAt و endedAt؛ مدت از اختلاف دو timestamp محاسبه می‌شود.
- manual_duration: دارای durationSeconds مثبت و در صورت نیاز occurredOn؛ زمان دقیق شروع/پایان برای آن ادعا نمی‌شود.
- manual_interval: ثبت دستی بازهٔ دقیق شروع و پایان؛ مدت از دو timestamp محاسبه می‌شود.

فیلدهای پایه:
- id
- workSessionId
- kind
- startedAt و endedAt برای بازه‌ها
- durationSeconds برای مدت دستی
- createdAt و updatedAt
- source و در صورت نیاز note

اعتبارسنجی:
1. بازه باید پایان بعد از شروع داشته باشد.
2. مدت دستی باید عدد صحیح مثبت باشد.
3. یک TimeEntry نباید هم‌زمان مدت دستی و بازهٔ تایمری متناقض داشته باشد.
4. هر ثبت باید به WorkSession موجود متصل باشد.
5. مجموع زمان واقعی از ثبت‌های معتبر محاسبه شود؛ مقدار تجمیعی cacheشده فقط با راهبرد سازگاری روشن مجاز است.

### ۱۷.۴ رفتار تایمر

- در شروع، یک TimeEntry تایمری با startedAt ساخته می‌شود و endedAt خالی می‌ماند.
- در مکث، بازهٔ فعال با زمان فعلی بسته می‌شود.
- در ادامه، یک TimeEntry تازه ساخته می‌شود؛ بازهٔ قبلی هرگز بازنویسی نمی‌شود.
- در پایان نشست، بازهٔ فعال بسته و WorkSession تکمیل می‌شود.
- مدت تایمر با timestampهای پایدار محاسبه می‌شود، نه با افزایش شمارنده در هر ثانیه.
- شمارندهٔ بصری UI فقط نمایش محاسبهٔ زمان است؛ منبع حقیقت دادهٔ ذخیره‌شده است.
- فقط یک تایمر فعال در کل برنامه در نسخهٔ پایه مجاز است. این تصمیم از ثبت هم‌زمان و دوباره‌شماری زمان جلوگیری می‌کند؛ امکان چند تایمر هم‌زمان نیازمند نیازسنجی و طراحی مستقل است.

### ۱۷.۵ Refresh، بسته‌شدن مرورگر و بازیابی

- وضعیت بازهٔ فعال باید در storage پایدار ثبت شود؛ حافظهٔ صفحه یا setInterval منبع حقیقت نیست.
- پس از Refresh، برنامه بازهٔ فعال را از storage می‌خواند و زمان سپری‌شده را از timestampها دوباره محاسبه می‌کند.
- اگر برنامه پس از بسته‌شدن مرورگر دوباره باز شود و یک بازهٔ فعال پیدا کند، باید وضعیت بازیابی را آشکارا به کاربر نشان دهد.
- چون مرورگر نمی‌تواند با قطعیت تشخیص دهد کاربر در زمان بسته‌بودن برنامه واقعاً کار کرده یا نه، سیاست محافظه‌کارانه این است که پیش از نهایی‌کردن بازهٔ طولانی یا مشکوک، از کاربر تأیید بگیرد؛ بازه نباید بی‌صدا حذف یا بی‌قیدوشرط نهایی شود.
- تغییر ساعت سیستم، خواب دستگاه و اختلاف ساعت می‌توانند بر timestampها اثر بگذارند؛ مقادیر نامعتبر یا غیرعادی باید شناسایی و برای اصلاح به کاربر نشان داده شوند.
- زمان‌ها به‌صورت timestamp استاندارد ذخیره و در نمایش به منطقهٔ زمانی کاربر تبدیل می‌شوند.

### ۱۷.۶ ثبت دستی و جلوگیری از دوباره‌شماری

- کاربر می‌تواند مدت واقعی را دستی ثبت کند، حتی اگر تایمر استفاده نشده باشد.
- در صورت داشتن ساعت دقیق، ثبت دستی می‌تواند به‌صورت بازهٔ شروع/پایان باشد؛ در غیر این صورت فقط مدت و تاریخ تقریبی ثبت می‌شود.
- بازه‌های دقیق هم‌پوشان نباید دوبار در مجموع زمان واقعی شمرده شوند.
- نسخهٔ پایه یک تایمر فعال سراسری دارد؛ ثبت دستی هم‌پوشان با بازهٔ تایمر باید پیش از ذخیره هشدار داده شود و نیازمند تصمیم صریح کاربر باشد.
- ثبت مدت بدون ساعت دقیق را نباید به یک بازهٔ زمانی ساختگی تبدیل کرد.
- اصلاح ثبت باید به‌جای افزودن دوبارهٔ همان زمان، همان ثبت را اصلاح کند یا با یک رکورد اصلاحی قابل ردیابی همراه باشد. سیاست تاریخچهٔ کامل اصلاحات پیش از پیاده‌سازی نهایی می‌شود.

### ۱۷.۷ محاسبه و گزارش

- Actual Duration نشست = مجموع مدت TimeEntryهای معتبر و بدون هم‌پوشانی آن نشست.
- Actual Duration وظیفه = مجموع زمان واقعی نشست‌های متعلق به آن وظیفه.
- اختلاف مدت برنامه‌ریزی‌شده و واقعی برای گزارش و پیشنهاد تخمین آینده قابل استفاده است.
- اصلاح خودکار Estimated Duration یا برنامهٔ آینده بدون اطلاع و تأیید کاربر ممنوع است.
- زمان واقعی یک منبع ثبت‌شده است؛ وضعیت completed به‌تنهایی نباید زمان واقعی فرضی ایجاد کند.

### ۱۷.۸ آزمون‌های پذیرش

- شروع، مکث، ادامه و پایان یک نشست با چند بازه
- Refresh هنگام تایمر فعال و بازیابی درست
- بستن و بازکردن مرورگر با بازهٔ فعال
- توقف تایمر و اطمینان از اینکه زمان مکث محاسبه نمی‌شود
- ثبت دستی مدت بدون زمان دقیق
- ثبت دستی بازهٔ دقیق
- جلوگیری از تایمر فعال دوم
- تشخیص بازه‌های هم‌پوشان
- تغییر ساعت سیستم یا timestamp نامعتبر
- نشست لغوشده/تکمیل‌شده با ثبت‌های قبلی
- جمع زمان نشست‌ها در Task بدون دوباره‌شماری
- شکست ذخیره‌سازی و حفظ آخرین دادهٔ معتبر

**محدودیت:** این قرارداد هنوز طراحی است. هیچ تایمر، WorkSession یا TimeEntry اجرایی با ثبت این سند ایجاد نشده است.

### ۱۷.۹ تصمیم‌های تکمیلی: بازیابی، اصلاحات و چند تب

#### بازیابی پس از بازگشت به برنامه

1. اگر هنگام بارگذاری برنامه یک TimeEntry تایمری با endedAt خالی وجود داشته باشد، برنامه وارد وضعیت recovery می‌شود و شروع تایمر تازه را تا تعیین تکلیف متوقف می‌کند.
2. UI زمان شروع و مدت سپری‌شدهٔ تخمینی را نمایش می‌دهد و از کاربر می‌خواهد زمان واقعی پایان را تعیین کند.
3. گزینه‌ها باید دست‌کم شامل تأیید ادامهٔ بازه تا زمان انتخاب‌شده، اصلاح زمان پایان، یا ردکردن بخش تأییدنشده باشند.
4. بخش تأییدنشده نباید بی‌صدا در Actual Duration شمرده شود. ردکردن آن نیز نباید رکورد را بدون ردپا نابود کند؛ باید به‌صورت voided/rejected یا وضعیت حسابرسی مشابه نگهداری شود.
5. برای بازه‌های بسیار طولانی یا غیرعادی هشدار برجسته‌تری نمایش داده می‌شود؛ اما هیچ آستانهٔ زمانی جایگزین تأیید کاربر نیست.
6. پس از تعیین تکلیف بازهٔ باز، فقط آن‌گاه امکان شروع تایمر جدید فراهم می‌شود.

#### اصلاح و حذف TimeEntry

1. TimeEntry ثبت‌شده پس از تأیید نباید بی‌ردپا ویرایش یا حذف فیزیکی شود.
2. اصلاح از طریق یک رکورد اصلاحی یا نسخهٔ جایگزین انجام می‌شود که به رکورد اصلی ارجاع دارد.
3. رکورد اصلی و دلیل/زمان اصلاح برای audit نگهداری می‌شود؛ محاسبهٔ Actual Duration فقط رکورد معتبر و نهایی را لحاظ می‌کند.
4. حذف از دید کاربر به معنی خارج‌کردن از محاسبه (void) است، نه نابودی فوری داده.
5. پاک‌سازی فیزیکی فقط تحت سیاست retention و عملیات صریح و قابل‌بازیابی مجاز است.
6. اگر کاربر فقط یک مدت بدون ساعت دقیق ثبت کرده باشد، اصلاح آن نباید برایش ساعت شروع و پایان ساختگی ایجاد کند.

#### هماهنگی بین چند تب

1. در هر لحظه حداکثر یک مالک فعال تایمر در سطح برنامه وجود دارد.
2. تب مالک، شناسهٔ نشست و شناسهٔ TimeEntry فعال را در وضعیت پایدار نگه می‌دارد و رویداد تغییر را به تب‌های دیگر اطلاع می‌دهد.
3. تب‌های دیگر وضعیت تایمر را فقط‌خواندنی نمایش می‌دهند و اجازهٔ شروع تایمر دوم ندارند.
4. Web Locks API می‌تواند قفل انحصاری بین تب‌ها را در مرورگرهای پشتیبان فراهم کند؛ اما قرارداد برنامه نباید به آن به‌عنوان تنها لایهٔ صحت داده وابسته باشد.
5. localStorage و BroadcastChannel به‌تنهایی تضمین اتمیک در رقابت هم‌زمان دو تب ایجاد نمی‌کنند؛ پیام‌رسانی صرف، قفل محسوب نمی‌شود.
6. اگر adapter ذخیره‌سازی نتواند مالکیت انحصاری را با اطمینان برقرار کند، رفتار امن fail-closed است: شروع تایمر جدید مسدود و راهنمایی قابل فهم نمایش داده می‌شود.
7. انتخاب نهایی مکانیزم قفل باید پیش از پیاده‌سازی تایمر و همراه با adapter ذخیره‌سازی انجام شود؛ برای تضمین تراکنشی، IndexedDB با transaction مناسب گزینهٔ جدی‌تری از چند کلید localStorage است.

**معیار پذیرش:** دو تب که هم‌زمان برای شروع تایمر اقدام می‌کنند نباید بتوانند دو TimeEntry فعال معتبر ایجاد کنند. پس از بسته‌شدن تب مالک نیز بازیابی باید بدون گم‌شدن یا دوباره‌شماری داده انجام شود.

## ۱۸. مقصد استقرار محصول: اپلیکیشن دسکتاپ مستقل

- **وضعیت:** الزام محصولی تأییدشده؛ فناوری و جزئیات پیاده‌سازی هنوز انتخاب نشده‌اند.
- **تصمیم قطعی محصول:** خروجی نهایی Vira Planner یک اپلیکیشن دسکتاپ واقعی و قابل نصب است؛ وب‌سایت یا صفحه‌ای که کاربر برای استفادهٔ روزمره مجبور باشد آن را در مرورگر باز کند، محصول نهایی محسوب نمی‌شود.
- **محیط توسعه:** VS Code فقط ابزار توسعه است. کاربر نهایی برای اجرای برنامه نباید به VS Code، Node.js، ترمینال یا نصب ابزارهای توسعه نیاز داشته باشد.
- **نمونهٔ اولیه:** اجرای مرورگری فعلی صرفاً محیط موقت توسعه و اعتبارسنجی است. وجود `index.html` یا اجرای محلی در مرورگر به معنی هدف‌بودن وب‌اپلیکیشن نیست.
- **هدف انتشار اولیه:** اپلیکیشن قابل نصب برای Windows؛ حداقل نسخهٔ دقیق ویندوز و دامنهٔ پشتیبانی باید در مرحلهٔ انتخاب فناوری با شواهد سازگاری تعیین شود. پشتیبانی از macOS/Linux هدف احتمالی بعدی است، نه تعهد فعلی.
- **الزامات تجربهٔ نصب و اجرا:** بستهٔ نصب مستقل، آیکون و نام برنامه، پنجرهٔ اختصاصی، اجرای مستقل از ابزار توسعه، مسیر روشن ذخیرهٔ داده، و امکان بازکردن/بستن برنامه بدون از دست‌رفتن داده.
- **اصل معماری:** منطق Domain و Application باید تا حد امکان مستقل از Desktop Shell باقی بمانند. Presentation و Infrastructure از طریق interface/adapter به قابلیت‌های سیستم‌عامل و پایگاه داده متصل می‌شوند تا انتخاب یا تعویض shell باعث بازنویسی منطق اصلی نشود.

### ۱۸.۱ انتخاب Desktop Shell — هنوز تصمیم‌گیری نشده

گزینه‌هایی مانند Tauri و Electron باید پیش از تثبیت بررسی شوند. معیارهای مقایسه:
1. سازگاری واقعی با نسخه‌های هدف Windows و پیش‌نیازهای نصب
2. اندازهٔ خروجی، مصرف RAM/CPU و سرعت راه‌اندازی
3. امنیت مرز بین رابط، دسترسی فایل و قابلیت‌های سیستم‌عامل
4. بلوغ ابزارهای build، signing، installer و به‌روزرسانی
5. دسترسی به اعلان‌های سیستم، فایل‌ها، پنجره‌ها و قابلیت‌های موردنیاز
6. پیچیدگی توسعه و نگهداری برای تیم/توسعه‌دهندهٔ کوچک
7. امکان تست خودکار و عیب‌یابی روی دستگاه کاربر
8. هزینهٔ واقعی نگهداری و مسیر انتشار نسخه‌های بعدی

**Tauri گزینهٔ پیشنهادی اولیه برای ارزیابی است، نه انتخاب مصوب.** Electron نیز باید به‌عنوان گزینهٔ مقایسه‌ای سنجیده شود. تا پیش از بررسی سازگاری، packaging و نیازهای واقعی، shell را قطعی نمی‌کنیم.

### ۱۸.۲ راهبرد ذخیره‌سازی دسکتاپ — هنوز تصمیم‌گیری نشده

- محصول نهایی باید local-first باشد و داده‌های اصلی کاربر را در فضای محلی تحت کنترل او نگه دارد.
- پایگاه دادهٔ رابطه‌ای محلی مانند SQLite نامزد جدی است؛ اما انتخاب نهایی به بررسی تراکنش‌ها، migration، backup/restore، رمزنگاری در حالت سکون، دسترسی هم‌زمان، بازیابی پس از crash و بسته‌بندی وابسته است.
- LocalStorage فعلی فقط بخشی از نمونهٔ اولیه و سازگاری موجود است؛ نباید بدون تصمیم معماری به‌عنوان storage نهایی اپ دسکتاپ تثبیت شود.
- IndexedDB نیز به‌عنوان گزینهٔ واسط/موقت برای prototype قابل بررسی است، اما انتخاب آن به‌تنهایی نیاز محصول به فایل‌سیستم و دیتابیس desktop را حل نمی‌کند.
- مسیر مهاجرت باید داده‌های فعلی را حفظ کند: export/backup خام، تبدیل نسخه‌دار، اعتبارسنجی، read-back، گزارش خطا و rollback. هیچ جایگزینی بدون آزمون مهاجرت روی نسخهٔ کپی داده انجام نمی‌شود.
- فایل‌های اصلی PDF و سایر اسناد باید در فضای فایل محلی مدیریت شوند؛ دیتابیس فراداده و پیوندها را نگه می‌دارد و باید سیاست مسیر، نام، حذف، backup و فایل گمشده مشخص شود.

### ۱۸.۳ امنیت و اتصال‌های بیرونی در اپ دسکتاپ

- دسکتاپ بودن برنامه به معنی امن‌بودن خودکار API key نیست؛ کلید محرمانه نباید داخل bundle، کد frontend یا فایل تنظیمات قابل‌خواندن ذخیره شود.
- گزینه‌های نگهداری کلید باید شامل OS credential store یا backend امن باشد؛ انتخاب به مدل استفاده از provider و تهدیدهای امنیتی وابسته است.
- اگر کاربر کلید شخصی provider را وارد کند، باید دربارهٔ محل ذخیره، سطح حفاظت، ارسال داده و امکان حذف کلید توضیح روشن ببیند.
- هر قابلیت cloud/AI اختیاری می‌ماند؛ هستهٔ مدیریت وظایف، زمان و اسناد باید بدون اتصال AI قابل استفاده باشد.
- دسترسی به فایل‌ها، اعلان‌ها، میکروفون و شبکه باید حداقلی، قابل توضیح و در صورت نیاز با رضایت کاربر فعال شود.

## ۱۹. ممیزی اولیهٔ کد و ارزیابی گزینه‌های Desktop — 2026-11-12

### ۱۹.۱ شواهد ممیزی مخزن فعلی

ممیزی read-only روی شاخهٔ توسعه انجام شد. فایل‌های اجرایی تغییر نکردند.

- `package.json` فقط اسکریپت `node --test` دارد و در حال حاضر dependency خارجی npm تعریف نکرده است.
- ورودی رابط `index.html` است و `app.js` به‌عنوان ES module بارگذاری می‌شود.
- `app.js` مستقیماً از `document.querySelector`، event listenerها و `scrollIntoView` استفاده می‌کند.
- ماژول‌های Presentation برای ساخت عناصر رابط از `document.createElement` استفاده می‌کنند؛ بنابراین UI فعلی به DOM وابسته است.
- `src/infrastructure/storage/local-task-storage.js` به‌طور پیش‌فرض `globalThis.localStorage` را دریافت می‌کند؛ ذخیره‌سازی فعلی browser storage است.
- در فایل‌های بررسی‌شدهٔ Domain و Application، وابستگی مستقیم به APIهای مرورگر مشاهده نشد؛ این نشانهٔ خوبی برای حفظ منطق اصلی است، اما ممیزی کامل تمام مسیرهای اجرا و وابستگی‌های ضمنی هنوز انجام نشده است.
- ساختار فعلی به‌صورت سادهٔ HTML/CSS/JavaScript ماژولار است و framework بزرگ frontend یا package dependency خارجی ندارد.

### ۱۹.۲ نتیجهٔ معماری از ممیزی

1. UI موجود را می‌توان در یک WebView دسکتاپ نمایش داد؛ لازم نیست به‌خاطر desktop شدن فوراً UI را از نو نوشت.
2. وابستگی DOM در Presentation طبیعی است و می‌تواند در WebView ادامه پیدا کند؛ اما دسترسی به فایل‌های سیستم‌عامل، اعلان native، credential store و database باید از طریق bridge/adapter محدود و قابل‌آزمون انجام شود.
3. بزرگ‌ترین مرز فنی که باید جدا شود، storage است: Application باید با قرارداد Repository کار کند و پیاده‌سازی فعلی LocalStorage فقط adapter نمونهٔ اولیه باقی بماند.
4. نباید APIهای native را مستقیماً در منطق Domain یا use caseها پخش کنیم.
5. پیش از افزودن shell، باید یک بررسی دقیق‌تر از همهٔ استفاده‌های browser API و رفتار ذخیره‌سازی در تست‌ها انجام شود.

### ۱۹.۴ ارزیابی مقدماتی و تصمیم باز

- **Tauri 2 نامزد اول برای proof of concept است** چون UI فعلی با WebView سازگار است و می‌توان منطق رابط را حفظ کرد؛ اما نیاز به Rust و ابزارهای native هزینهٔ یادگیری و راه‌اندازی دارد.
- **Electron گزینهٔ جایگزین جدی است** چون برای کاربر JavaScript/Node محور، مسیر توسعه احتمالاً ساده‌تر است؛ اما Chromium و Node همراه برنامه می‌آیند و باید اندازهٔ نصب، مصرف منابع و سطح دسترسی main/renderer سنجیده شود.
- هنوز هیچ‌کدام انتخاب نهایی نیستند. معیار تعیین‌کننده باید یک نمونهٔ واقعی روی Windows هدف باشد، نه صرفاً شهرت یا ادعای سبک‌بودن یک فناوری.
- پیش از تصمیم، نسخه/build دقیق Windows 10 دستگاه توسعه و حداقل سیستم‌عامل هدف انتشار باید مشخص شود. اگر قرار است Windows 10 قدیمی‌تر از 1803 پشتیبانی شود، فرض پیش‌فرض WebView2 نصب‌شده برای Tauri کافی نیست و installer باید runtime را مدیریت کند.

### ۱۹.۵ ارزیابی مقدماتی SQLite

SQLite نامزد اصلی storage محلی رابطه‌ای باقی می‌ماند، زیرا:
- transactionهای ACID و rollback را پشتیبانی می‌کند؛
- چند reader هم‌زمان را می‌پذیرد و writeها را به‌صورت سریالی مدیریت می‌کند؛
- Online Backup API برای ساخت snapshot از دیتابیس فعال دارد؛
- WAL می‌تواند هم‌زمانی reader و writer را بهتر کند، اما خود WAL هم فایل و قواعد checkpoint/recovery دارد و برای فایل‌سیستم شبکه‌ای مناسب نیست.

نکتهٔ نگهداری مهم: مستندات رسمی SQLite یک اشکال نادر WAL را گزارش کرده‌اند که در SQLite 3.51.3 و نسخه‌های بعدی رفع شده است. اگر WAL انتخاب شود، نسخهٔ SQLite باید pin و بررسی شود و صرفاً به نسخهٔ پیش‌فرض یک dependency ناشناخته اعتماد نکنیم.

منابع رسمی:
- https://www.sqlite.org/transactional.html
- https://www.sqlite.org/lang_transaction.html
- https://www.sqlite.org/backup.html
- https://www.sqlite.org/wal.html

**وضعیت:** SQLite گزینهٔ ترجیحی برای prototype storage است، نه مجوز مهاجرت فوری. انتخاب driver/bridge، رمزنگاری، مسیر فایل، backup و migration باید در طراحی بعدی تثبیت شوند.

### ۱۹.۶ گام بعدی فنی

1. تعیین نسخهٔ دقیق Windows 10 دستگاه توسعه و نسخهٔ حداقلی هدف.
2. طراحی یک proof of concept بسیار کوچک و جدا از قابلیت‌های اصلی: پنجرهٔ مستقل، ذخیرهٔ یک رکورد در SQLite، بستن/بازکردن برنامه و بازیابی رکورد.
3. ساخت همان سناریوی حداقلی با Tauri و Electron یا دست‌کم نمونهٔ قابل‌اندازه‌گیری برای هر دو.
4. مقایسهٔ installer size، زمان اجرا، RAM پس از بازشدن، سهولت build روی دستگاه واقعی و مسیر backup.
5. انتخاب shell و storage فقط پس از نتیجهٔ آزمون و ثبت ADR.

تا پیش از این آزمون، migration یا تغییر گستردهٔ کد انجام نمی‌شود.

- Vira Planner محصولی دسکتاپ، مستقل و قابل نصب است؛ نه وب‌سایتی که کاربر برای استفادهٔ روزمره به مرورگر یا VS Code نیاز داشته باشد.
- معماری باید از ابتدا امکان انتشار برای Windows، macOS و Linux را فراهم کند.
- ترتیب اجرایی انتشار می‌تواند مرحله‌ای باشد: ابتدا Windows، سپس macOS و Linux پس از آزمون و آماده‌سازی بسته‌های هر پلتفرم.
- توسعهٔ فعلی روی Windows انجام می‌شود؛ سیستم توسعهٔ فعلی، محدودهٔ پلتفرم‌های مقصد را محدود نمی‌کند.

### اصول چندسکویی
1. Domain و Application نباید به APIهای اختصاصی Windows یا WebView وابسته شوند.
2. دسترسی به فایل، اعلان سیستم، پنجره، ذخیره‌سازی و قابلیت‌های سیستم‌عامل از طریق adapterهای Infrastructure انجام شود.
3. مسیرها، نام فایل‌ها، مجوزها، منطقهٔ زمانی و رفتار اعلان‌ها باید در هر سیستم‌عامل جداگانه آزمون شوند.
4. دادهٔ کاربر باید قابل پشتیبان‌گیری و انتقال بین نسخه‌های پشتیبانی‌شده باشد؛ تفاوت سیستم‌عامل نباید قالب داده را بی‌دلیل تغییر دهد.
5. معماری چندسکویی به معنی تضمین پشتیبانی از تمام نسخه‌های تاریخی سیستم‌عامل‌ها نیست؛ حداقل نسخه‌ها و معماری پردازنده برای هر انتشار باید در ماتریس سازگاری اعلام و آزمون شوند.

### گزینه‌های Desktop Shell
- **Tauri 2:** گزینهٔ نخست برای نمونهٔ فنی؛ رابط فعلی وب‌محور را می‌توان در WebView سیستم اجرا کرد. توسعهٔ Windows به Rust و Microsoft C++ Build Tools نیاز دارد؛ WebView2 در Windows 10 نسخهٔ 1803 به بعد و Windows 11 در دسترس است.
- **Electron:** گزینهٔ جایگزین برای مقایسه؛ مدل توسعهٔ JavaScript/Node.js برای تیم فعلی آشناتر است، اما بستهٔ نهایی معمولاً بزرگ‌تر است چون Chromium و Node.js را همراه می‌آورد.
- هیچ‌یک در این مرحله انتخاب قطعی نیست. معیارها: سازگاری Windows 10/11، macOS و Linux، اندازهٔ خروجی، مصرف حافظه، امنیت، پشتیبانی از قابلیت‌های native، تجربهٔ توسعه و هزینهٔ نگهداری.

### پایگاه دادهٔ محلی
SQLite گزینهٔ اولیهٔ بررسی است، نه انتخاب قطعی. پیش از مهاجرت باید نیازهای تراکنش، پشتیبان‌گیری، رمزنگاری، مهاجرت schema، بازیابی خرابی و دسترسی هم‌زمان بررسی شوند. LocalStorage فعلی فقط بخشی از نمونهٔ اولیه است و نباید بدون طراحی migration به‌عنوان ذخیره‌سازی نهایی دسکتاپ فرض شود.

### محیط توسعهٔ فعلی
آخرین اطلاعات ارائه‌شده از دستگاه توسعه:
- Windows 10 Pro
- Version 22H2
- OS Build 19045.6575

این دستگاه برای بررسی اولیهٔ مسیر Tauri مناسب است؛ WebView2 در Windows 10 نسخهٔ 1803 به بعد در دسترس است. معماری پردازنده/سیستم (x64 یا ARM64) هنوز تأیید نشده و باید پیش از انتخاب toolchain و تولید installer بررسی شود.
